# 覆盖率怎么量

这套系统有两层测试，量的是完全不同的东西，任何单独一个数字都会误导人：

- **进程内单测**（`go test -cover`）：只统计单测进程里执行到的语句。
- **三机 e2e**（`scripts/e2e/`）：跑的是编译好的真二进制，跨进程、跨机器。它执行的
  代码在普通覆盖率剖面里**一个字节都不会记**，因为生产二进制没有插桩。

所以「`cmd/nanotund` 单测覆盖 59.3%」的正确读法是「40.7% 的语句没有被单测覆盖」，
而不是「40.7% 从来没人验证过」。出口选择、ACL 快照、子网路由这些被 e2e 反复压过的
路径全在那 40.7% 里。反过来，e2e 也扫不到报文畸形、非 INET class、上游反投毒这类
分支——真实流量里几乎不出现，却正是攻击面所在。

要看清全貌，得把两笔账合起来。

## 合并账怎么出

### 一、单测这一侧（要在 Linux 上跑）

macOS 上跑单测会漏掉所有 `*_linux.go`——那些文件在 darwin 上根本不参与编译，
既不进分子也不进分母，得出的百分比虚高。交叉编译出测试二进制丢到 Linux 机器上跑：

```bash
# 本机交叉编译
mkdir -p /tmp/lt
for p in $(go list ./...); do
  GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
    go test -c -cover -covermode=set -o /tmp/lt/$(basename $p).test $p
done

# 传到 Linux 机器,连同源码树(有测试读相对路径文件,CWD 必须是各自的包目录)
rsync -az --exclude=.git --exclude=dist ./ root@<linux>:/root/nttest/src/
rsync -az /tmp/lt/ root@<linux>:/root/nttest/bin/

# 逐包跑,CWD = 包目录
cd /root/nttest/src/cmd/nanotund && /root/nttest/bin/nanotund.test \
  -test.count=1 -test.timeout=40m -test.coverprofile=/root/nttest/cov/nanotund.cov
```

各包的 `.cov` 拼成一份（保留一行 `mode:` 头即可）。

### 二、e2e 这一侧（插桩二进制）

用 `go build -cover` 编出带插桩的三个二进制，部署上去跑完整 e2e，进程退出时会把
计数写进 `GOCOVERDIR`：

```bash
go build -cover -covermode=atomic -coverpkg=github.com/nanotun/server/... \
  -o /tmp/cov-bin/nanotund ./cmd/nanotund      # nanotun-web / nanotun-admin 同理
```

部署时三件事：

1. 两个 systemd unit 加 drop-in `Environment=GOCOVERDIR=<目录>`；
2. `nanotun-admin` 是 CLI，e2e 通过 ssh 直接调，用一层 wrapper 脚本注入 `GOCOVERDIR`
   （放 `/usr/local/bin/nanotun-admin`，真二进制改名放旁边）；
3. 跑完 `systemctl stop` 让进程正常退出刷盘，再把 `GOCOVERDIR` 收回来。

```bash
go tool covdata textfmt -i=<收回的目录> -o=e2e.cov
```

### 三、合并

```bash
scripts/coverage/merge-coverage.py unit-linux.cov e2e.cov coverage-gaps.txt
```

输出按包分「两边都覆盖 / 仅单测 / 仅 e2e / 都没有」四类。**只有「都没有」那一列
才是真正该补的空白**，`coverage-gaps.txt` 里是精确到语句块的完整清单。

## 四个坑（都踩过）

**`GOCOVERDIR` 不能放 `/root`。** `nanotun.service` 和 `nanotun-web.service` 都开着
`ProtectHome=yes`，`/root` 在它们的 mount namespace 里根本不存在，覆盖数据被静默拒写，
日志里只留一行 `coverage meta-data emit failed: ... no such file or directory`。
必须放在 unit 的 `ReadWritePaths` 覆盖的路径下，例如 `/var/lib/nanotun/cov`。
第一次采集就是这么白跑了两轮 e2e 才发现。

**阶段 70 的 `kill -9` 会吞掉计数器。** 插桩数据是进程正常退出时才落盘的，SIGKILL
直接丢。若 00–70 一口气跑完，`nanotund` 在阶段 0–6 攒的覆盖会连同那条命一起没掉。
得拆成两次服务生命周期：先跑 00–60 → `systemctl stop` 刷盘归档 → 重启 → 单跑 70 →
再 stop 刷盘。两批数据放同一目录，`covdata` 会自动合并。

**改了源码，旧剖面就作废。** 合并是按 `文件:起止行.列` 匹配语句块的。哪怕只是在
文件中间插入一个函数，其后所有行号位移，那个文件的 key 全部对不上，合并结果会把它
整片误算成「仅单侧覆盖」。改完代码要两边重新采集，别拿旧剖面凑。校验很简单：两份
`.cov` 的行数应当完全相同（当前是 11953）。

**拼剖面的输出别落在 `*.cov` 的通配范围里。** `{ for f in $COV/*.cov; do tail -n +2
$f; done; } > $COV/unit-linux.cov` 看着没问题，实际上输出文件自己也匹配那个通配，
`tail` 读自己写自己，几分钟就把 23G 根分区写满了。更阴的是 `rm` 掉之后 `df` 还是
100% —— 有个 `sftp-server` 还开着那个已删除的句柄，`du` 只算出 7G 而 `df` 报 23G，
得 `lsof | grep deleted` 找出来杀掉才回收。输出放到 `$COV` 外面就没这事。

## 补空白的顺序

按「都没有」的条数排，但别只看数字——`main` 那 96 条是进程启动编排，写单测的性价比
远低于同样条数的 ACL 判决。挑的时候看这三条：

1. **判错了会静默出错吗**（ACL、出口选择、地址校验这类，判错不崩溃，只是悄悄放行或
   悄悄黑洞）优先；
2. **是不是 e2e 结构上够不着的**（畸形输入、并发、平台分支）；
3. **要不要为了可测性动生产代码**——需要动的，照 `health.go` 的 `isLoopbackHost`、
   `network_rules.go` 的路数把判定抽成纯函数，`FatalExit` / IO 留在薄壳里。

补完必须做变异验证：把被测逻辑定点改坏，确认测试真的会红。只跑一遍看行数变亮不算数
——`listen_addr` 那个校验漏洞就是变异逃逸暴露出来的，测试照过，一查才发现那个分支
从来没被自己的用例走到过。

第 14/15 轮把 `store` 从 79.8% 推到 95.4%(未覆盖 86 / 1879 条)。剩下的基本进不去:驱动层的
`LastInsertId()` / `Commit()` / `RowsAffected()` 失败、`listMigrations` 对 embed FS 的防御分支
(文件名非法 / 版本号重复 —— 编译期就固定了)、以及 `ProbeServerDialHost` 需要真 DNS + ICMP 回包
的那几条。要再动就得引一个注入故障的 `database/sql/driver` 包装,性价比不如去啃 `cmd/*`。

这两轮里真正抓到东西的用例(不是补行数的):

- **事务半途失败必须整体回滚**。删设备 / 删用户时,清孤儿 `port_forwards` 那步失败却照样把行删掉,
  剩下的转发会被下一个注册同 UUID 的账号静默继承——外网入口换了主人,两边界面都看不出来。
  `SetDeviceFixedVIP` 同理:`--force` 释放对方 lease 失败却把地址钉上去,就是双占。
- **`RotateUserPSKAndEnsureCredential` 的原子性**。补 `credential_id` 失败时 `psk_hash` 必须跟着回滚,
  否则旧 PSK 已作废、新 QR 又生成不出来,用户被锁在门外而 admin 只看到一句报错。
- **迁移出错时版本号不许前进**,而且「版本号读不出来」绝不能当成 0 ——当成 0 会把非幂等的历史迁移
  (`ALTER TABLE ADD COLUMN`)重放一遍,比启动失败严重得多。构造手法是把 `schema_version` 往回拨一格
  再跑 `Migrate`。
- **存量 VIP 归一的跨表撞车**:`leases.vip_v6` 归一后撞上别的设备已钉的 `devices.fixed_vip_v6` 时要跳过 +
  把完成标记留在 `'0'`,下次启动重跑。落 `'1'` 就等于永久 no-op,残留的非规范写法再不会被处理。
- **`SettingsSet` 的纵深校验**。`mesh_enabled` 拼成 `flase` 时读路径兜底是 **true**(fail-open),
  「想关 mesh」会静默保持互通;限速键写歪则被静默当 0(= 不限)。这些校验不能只留在 CLI 那一层。
- **列表读到坏行要整体报错**,不能少一行。管理员看不到某个账号 / 某条已批准的网段,就以为它不存在,
  而它照样在生效。

新增的两个手法:

- `abortOnWhen(table, op, when)` —— 带 `WHEN` 的 `RAISE(ABORT)` 触发器。用来分辨「同一事务里第几步失败」,
  比如 `SetRateDefaults` 三个键各失败一次,验的都是同一个不变量:三个键同生同死,不留撕裂态。
- 往 INTEGER 列写 **REAL**(而不是 TEXT)。TEXT 在 SQLite 里排在所有数字之后,`WHERE at >= ? AND at < ?`
  会把坏行直接滤掉,`Scan` 根本走不到;写 `1000.5` 则留在数值域内,过得了 WHERE、卡在 `Scan` ——
  这才是 `QueryAudit` 那条扫描错误分支的构造方式。

变异逃逸这次同样是**用例没隔离干净**:拿不到迁移锁、坏 `device_id`、读不出版本号这三条,报的错
都来自另一道闸(SQLite 自己的写失败 / 外键 / 后续语句),把断言收紧到「报错原因必须是这一道」之后
全部抓住。剩一条 `SetRateDefaults` 第一个键失败时提前 commit 是等价变异——那时还没写任何东西;
换成第二、第三个键失败就立刻被抓。

第 13 轮引入了两个可复用的手段,后面几轮都在用:

- **`Options{ReadOnly:true}` / 已 Close 的 store** 两级故障注入。只读库让第一条写语句失败,
  已关库让 `BeginTx` 就失败 —— 两者覆盖的错误分支不同。要验的不变量很朴素:库挂了或只读时
  **没有任何一个 DAL 函数报成功**,也不能把存储故障归一成 `ErrNotFound`(那会让 handler 显示
  「账号不存在」而不是「存储不可写」,排查方向全错)。
- **`RAISE(ABORT)` 触发器**做精准故障注入(`abortOn` 助手)。前两种手段都只能让**第一条**语句
  失败,而最该验的是「事务里第二条失败要整体回滚」:改密的 UPDATE 成了但撤销旧会话的 DELETE
  失败,不回滚就是「密码已改、旧 cookie 仍有效」—— 改密根本没把攻击者踢下线。在 `web_sessions`
  / `web_admin_recovery_codes` 上装 BEFORE DELETE/INSERT 触发器就能精确制造这种失败。
  注意 BEFORE 触发器在**匹配 0 行时不触发**,构造时要确认目标行真的存在。

另外用「往 INTEGER 列写 TEXT」(SQLite 非 STRICT 表允许)模拟手工改库 / 迁移写坏。这类用例
的价值不在覆盖率:`failed_logins` 扫不出来若被静默当成 0,等于把已锁定的账号自动解锁。

第 13 轮的变异逃逸值得记一笔,四条里三条是**用例没隔离干净**——报的错来自另一道闸:
`CreateFirstWebAdmin` 的空用户名撞的是 `ErrSetupClosed`(库里已有 admin)、
`SetWebAdminRoleEnsuringAdmin` 的非法 role 撞的是 `ErrLastAdmin`(只有一个 admin)、
`EnableWebAdminTOTP` 的空恢复码撞的是 CAS 的 `ErrNotFound`(没设过 secret)。
三条都拆成独立用例、先把「别的闸不会响」布置好再断言。**光看行数变亮完全发现不了这类问题。**
唯一的等价变异是 `CreateWebSession` 的 `AdminID<=0`:外键 `REFERENCES web_admins(id)` 兜住了

### 第 22 轮:`cmd/nanotun-admin`(80.5% → 96.7%)

CLI 的坏法与 handler 不同:它没有 HTTP 状态码,只有**退出码 + 两条流**。所以这一轮的
断言几乎都围绕三件事:

- **退出码不许随环境漂移**。`kick user`(参数敲错)在 server 可达与不可达时都必须是 2。
  此前有几条命令先拨 control socket 再校验参数,于是「用法错」被报成「连不上」(exit 1),
  脚本没法判断。
- **落库 ≠ 生效**。ACL / 限速 / mesh 这些键都缓存在 server 内存快照里,不通知就只是改了行 DB。
  这一轮在 `acl add --json` 上抓到一个真缺陷:`--json` 分支直接 return,把通知 server、
  reload 提示、缺回程告警一并跳过 —— 脚本化加规则拿到一条「已创建」的 JSON,而数据面
  的 ACL 快照从没刷过,规则静默不生效;同一文件里的 `acl del` 反倒一直通知,两条路口径相反。
  修法是把通知/提示移出分叉(它们全走 stderr,不污染 `--json` 的机器可读 stdout)。
- **确定性的输出失败必须发生在落库之前**。`credentials --rotate-psk` 一旦落库,旧 PSK 立刻作废;
  之后才发现 `--output` 的目录不存在 = PSK 已换、明文从未交付,用户当场断连而运维手里也没有新密钥。
  `preflightCredentialsOutput` 的每一条判定都对着这个不变量。

故障注入这一侧新加了两个手法:

- **只挡一个 key 的写**(`abortSettingWrite`)。整表挡 `app_settings` 的 INSERT 会先把
  migration 挡掉 —— 命令在到达被测那行之前就 exit 1,用例照样"通过",但验的其实是
  migration 失败。这正是 `init` 的 `setup_completed` 那条变异逃逸的原因。
- **放宽 NOT NULL 后塞 NULL**(`relaxAppSettingsValue`)。`SettingsGet` 往 `string` 扫会报错,
  这是模拟「真·读故障」的唯一办法 —— 与「这个 key 没设过」(`ok=false`,不是 error)是两回事。
  `route approve` 读不出 mesh 网段时必须**拒**(交叠检查是 fail-closed)就是靠它验的。

为可测性动的生产代码只有一处接缝:`cmd_setting.go` 把 DNS 与 ICMP 探测收进
`probeLookupIPAddr` / `probeDialHost` 两个包级变量。`probe-dial-host` 的价值全在
**结果分类**(DNS 硬错 / 无记录 / 解到不可拨的特殊地址 / ICMP 软失败)上,而真去查网络
会让用例随宿主网络红绿漂移。

`main()` 本体(读 `os.Args`、`os.Exit`)照 `nanotun-web` 的路数用子进程冒烟测试覆盖:
设了 `NANOTUN_SUBPROC_COVERDIR` 就用 `go build -cover` 编,计数落进 `GOCOVERDIR` 并进合并账。

剩下的 98 条基本进不去,分三类:`crypto/rand` / `json.Marshal` 一个固定结构失败这类
「机器已经坏了」的分支;`copyFileAtomic` 的 `Chmod`/`Sync`/`Close` 失败(要一个写满的
文件系统);以及**代码里就走不到的空分支** —— `confirm()` 永远返回 `nil` error、
`openProfileOutput()` 的 error 恒为 `nil`,它们的 `if err != nil` 判断有六七处调用点,
真正该做的是把这两个函数的签名收掉,不是给它们编测试。

唯一一条抓不住的变异是 `writeFileTight` 里 `os.Link` 换成 `os.Rename`:两者只在
「Lstat 与落盘之间被抢建」这个 race 窗口里有区别,没有可移植的确定性测法。它靠注释与 review 守。

第 5 轮为了可测性动了生产代码：`jump_host_firewall.go` 里所有 `exec.Command` 与

### 第 23 轮:`cmd/nanotund` 的「静默出错」那一档

按「补空白的顺序」第 1 条挑的:ACL 快照重建、出口裁决、出口列表。这三处判错都不报错、
不掉线,只表现成用户那头「网怪怪的」，所以优先级排在条数多得多的 `main` 启动编排前面。

真正值得记的是**断言该断在哪**:

- **「读不出设置」与「这个 key 没设过」必须分开。** `reloadACLSnapshotFromStore` 里两者
  的正确行为恰好相反 —— 前者要返回 err 且**原样保留旧快照**,后者落到内置默认 allow。
  只断 `err != nil` 是不够的:一个「先把快照换成空规则 + allow、再返回 err」的实现同样
  满足它,而那正是最坏的结果(default-deny 被一次 DB 抖动翻成全放行,且无告警)。用例断的
  是**快照指针不变** + 旧的 deny 规则仍在拦。
- **fail-closed 兜底只能由手抠 DB 触发。** `acl_default_action` 写路径自己就拒非法值,
  所以用例得直写 SQL 才进得去那条分支 —— 顺手把「写路径确实在拦」也钉成断言,这样两层
  防御各自的责任都写在测试里。
- **「查不动」不是「未批准」。** `resolveApprovedExitDeviceID` /
  `deviceHasApprovedExitRoute` 都返回 `(值, ok)`,ok=false 意味着无法判定。混为一谈的话,
  一次 DB 抖动就会撤销仍然有效的出口绑定,或把用户想避开的 server 自出口静默给他。
  三种入口(无 store、deviceID=0、DB 报错)分别钉。

两次变异逃逸都出在同一种写法上,值得当模板记住:**用例里让同一个对象同时满足正反两边,
去掉判定后结果不变**。第一次是「同一台设备既宣告了 LAN 段又宣告了出口」——去掉
`IsExitDefaultRoute` 过滤照样解析到同一个 device;改成「只批了 192.168 段的设备绝不能
被解析成出口」才抓得住。`buildExitsList` 第 ④ 步那条一模一样。

`isRunningExitConn` 是这一轮唯一动的产品代码:`buildExitsList` 的 ① 快照与 ③ 复核本来
手抄了两遍同一判据,而 ① 还多查一个 `deviceID != 0`,属于随时会漂移的重复。抽成一处之后
判据本身可以直测。

还剩一条变异逃逸,是结构性的:③ 复核守的是「② 查 DB 期间会话状态翻转」那个窗口,
单线程单测开不出来 —— 要么给生产代码加一个纯为开窗存在的钩子。判据抽出来后至少
「判据认不认这几种失效状态」钉住了,调用时序靠 e2e 里出口接管/重登那几条。

后半轮接着补 `route_advertise.go`(49 → 17)与 MagicDNS 一家四个文件
(`magic_dns.go` 93 → 42、`_exit.go` 36 → 19、`_cache.go` 30 → 12、`_intercept.go` 15 → 7),
包覆盖 80.3% → 81.6%。这半轮的教训集中在**「用例形状对不对」**上,变异测试基本全是替我
指出这一点:

- **重名裁决必须绕开去重那道口子才测得到。** `lookupMagicHost` 对同名设备取 device_id
  最小的那台,但 `UpsertDevice` 会给撞名的自动追 `-1`,走它根本造不出两台同名。得直写
  SQL —— 而这恰好也是这段代码真正服务的场景:唯一性强制生效**之前**登记的存量重名。
  断言还要跑多次,因为「取遍历顺序第一个」的实现会随两台机器 last_seen 的更新来回漂移。
- **「返回了 cleanup」证不了「没起 listener」。** `startMagicDNS` 的六条 no-op 路径,
  只断 cleanup 非 nil 的话,一个「非法 listen_addr 照样绑」的实现也能过 —— 而
  `addr.IP=nil` 会被 `ListenUDP` 当成 `0.0.0.0`,把本该只在 TUN 上听的内网 DNS 摆到
  所有网卡,包括公网口。改成调完立刻去 bind 那个端口:绑得上才说明真的没起。
  「未启用」那条还得把端口显式写成探测端口 —— 留空会走默认 53,而「绑 53 需要 root」
  会让「其实起了 listener」的实现**碰巧**也失败,用例就空过了。
- **验「取最小」的用例里,几个值必须不相等。** `parseExitDNSResult` /
  `parseRawDNSMeta` 都取答复区最小 TTL,原来的用例每条答复给同一个 TTL,于是取最大的
  实现结果一样。改成 300/45/90 三条、最小值刻意放中间,顺带排除「取最后一条」。
- **越界检查要在**足够长**的包上验。** `dnsQuestionEnd` 拒绝 question 段里的压缩指针;
  短包里去掉这道检查,`0xc0` 会被当成长度 192、一步跨过包尾,照样落到「越界」那条
  `return false` —— 两种实现结果相同。得给一个 220 字节的包、让指针跳到的位置恰好是
  0 字节,缺检查的实现才会返回一个在界内的**假**偏移。

两条判定为等价、不再追的:`tryResolvePublicViaExit` 里对 fail-closed 哨兵的显式判定
(去掉后 `lookupRunningExitConnByDevice(-1)` 也查不到,结果相同 —— 它是可读性分支,
不是唯一防线),以及拦截路径上关联端口的区间预筛(waiter 只可能登记在区间内,真正的
门是那次 map 查找)。

`route_advertise` 那半轮还暴露了一个**测试自身**的 data race:撤回出口会
fire-and-forget 一条 `broadcastExitsList`,它读 `gatewayInstance`,而子测试的
`t.Cleanup` 同时把值改回去。修法不是加 sleep,而是挂一条只收广播的 exit_allowed 会话、
等那一帧到达 —— 既建立了 happens-before,又顺带把「撤回后必须立刻重算并推送」钉成
断言(否则已撤回的出口要留在别人的下拉里直到它下线)。

### 第 24 轮:两个入站监听器(REALITY / hy2)

原以为这两块「要真握手所以测不了」,实际只有握手本身测不了 —— 外面的启动编排、accept
循环、环回桥接全都能在进程内跑通。`reality_listen.go` 64 → 6、`hysteria.go` 44 → 19,
包覆盖 81.6% → 82.8%,变异 32 项全抓。

能测到这个程度靠两件事。一是既有测试里已经有一份 **WS + smux 回声服务端**的脚手架
(`loopback_smux_test.go`),把它抽成 helper 之后,「桥接到环回数据面」这条主路就能整条
跑起来 —— 而这条路上此前一条断言都没有,失败面倒是钉得挺全。二是把埋在闭包里的
accept 循环抽成 `runRealityAcceptLoop(ln, handle)`,注入假 listener 才能造出 EMFILE。

这一轮钉住的、错了又完全不报错的性质:

- **可恢复的 Accept 错误不能当致命。** fd 耗尽(EMFILE)、客户端在 backlog 里就 RST
  (ECONNABORTED)过几秒就好;当成致命退出循环,整个 REALITY 入口对所有客户端**永久**
  消失 —— 进程还活着、别的入口还在服务,监控大概也不会响。唯一的致命错误是自己
  `Close` 后的 `net.ErrClosed`。
- **退避要归零,而且不能是 0。** 返回 0 会让持续报错变成 hot-spin 吃满 CPU;成功一次
  之后不归零,则一段早已过去的抖动会长期给每次接入加上封顶延迟。后者的断言得量
  「出错到下次 Accept」的实际间隔 —— 只看「循环还活着」是抓不住的。
- **上报的端口必须是真在听的那个。** `listen_addr` 用 `:0` 时内核分配端口,这个值经
  node_login 发给客户端。报错了的现象是「服务一切正常但没人连得上」,服务端日志里
  什么错都没有。断言方式是拿上报的端口去 bind,占不上才算对。
- **失败路径必须把已绑的端口还回去。** hy2 启动的后半段(建 server config / NewServer)
  失败时若不关 packetConn,后续重试会看到「端口已被占用」的假象,排查方向直接被带偏。
- **真实客户端地址必须透传到环回。** hy2 拿不到客户端地址(hysteria 的
  `Outbound.TCP(reqAddr)` 不透出),靠 relay 在 RequestHook→EventLogger→Outbound 三步间
  用一次性 token 传递。传不到不报错,只是**所有** hy2 客户端塌进 127.0.0.1 这一个桶:
  `loginIPLimiter` / `powIPLimiter` 都按 remoteAddr 的 host 分桶,单个滥用者就能把全部
  hy2 用户一起限死,而客户端 `transport=auto` 优先选的正是 hy2。
- **reqAddr 绝不能当 dial 目标。** 这是「hy2 不得退化成任意 TCP 开放代理」的硬约束。
  既有用例只验了「pool 为 nil 时报错」—— 那条路上 reqAddr 压根没机会被使用。新用例在
  reqAddr 里放一个**活着**的诱饵监听:一旦实现拿它去拨,诱饵就会收到连接。
- **握手 deadline 进桥接后必须清掉。** `realityAcceptDeadlineListener` 给每条 conn 套了
  15s,不清的话业务数据一旦有 15s 空闲就被砍 —— 表现成「连上能用一会儿然后莫名断线」。
  断言方式是进桥接前故意套一个 300ms 的短 deadline,再等过它才收发。

两条形状教训(又是变异测试指出来的):**假 listener 报错时也返回 nil conn,那么「返回 c」
与「返回 nil」就无从区分**,得让剧本同时给出 conn 和错误;以及**验「成功后重置」的剧本,
成功之后不能紧接就是关机** —— 那条路径上退避有没有归零看不出来。

剩下的 25 条(reality 6 / hysteria 19)分三类:握手后才走到的桥接调用(归 e2e)、被
`Validate` 挡在前面的防御分支、以及需要 Linux + root 的端口跳跃 iptables 路径。还有两处
是「OpenStream 成功之后、写 PROXY 头之前断链」那个瞬间窗口,单测开不出来。

### 第 25 轮:hy2 与 REALITY 共用的那条环回承载

`loopback_smux.go` 29 → 9,包 82.8% → 83.2%,变异 17 项抓 16(第 17 条等价:拨号失败时
`sess` 恒为 nil,写不写进池没有可观测差异)。这一轮翻出两个真缺陷,都属于「功能完全正常
直到某个配置组合被用上」那类。

**HIGH:启用 `[smux]` + hy2/REALITY 时,所有直连原生客户端都登不进来。**
识别一条入站连接是「环回 smux 承载」还是「直连链路帧」靠 4 字节魔法前缀 `VPN1`,原实现
直接 `br.Peek(4)`。但直连客户端的首帧是 `PoWChallengeReq`,协议明文规定 body 必须为空,
线上恒为 **3 字节**(2 长度 + 1 类型)。于是服务端等第 4 个字节、客户端等 `PoWChallenge`
回复,双方干等到超时 —— 而 `[smux]` 就在发布的 `config.toml` 里,只要同时配了 hy2 或
REALITY 就会触发。三机 e2e 从来没配过这两个入站,所以这个组合一直没被跑到。改成「先看
一个字节,只有它等于 `'V'` 才允许要求看满 4 字节」:链路帧的首字节是长度高位,只有帧长
≥0x5600 时才可能撞上 `'V'`,而那时后续字节早已到齐,不会多等。顺带给识别期加了读超时
(未认证对端一个字节都不发就白占一个 goroutine 和一块读缓冲),并在识别完立刻撤掉 ——
不撤的话每条承载最多活 30s,之后所有多路复用连接一起断。

**MED:环回承载闪断后,新流会连续失败长达半分钟。**
两个事实叠在一起:① smux 只在 keepalive 超时(`DefaultConfig` 30s)后才把会话标记为死,
在那之前 `IsClosed()` 恒 false;② 断线那一刻 `OpenStream` 往往仍然成功(SYN 由 shaper
异步写出),错误要到第一次读写才浮出来。原实现只看 `IsClosed()`,于是这半分钟里每条新
hy2 / REALITY 流都开在同一具尸体上、全部 broken pipe,而重拨一条环回只要几毫秒。修法是
两道:`OpenStream` 报错即摘掉会话并重建(主路),以及给复用出去的 stream 包一层,把承载级
I/O 错误回报给池(兜住 smux 还没察觉的那个窗口)。代价从「半分钟内全灭」收敛成「撞上断线
的那一条流失败」。

包装层的判据是这一轮最需要小心的地方:`io.EOF` / `io.ErrClosedPipe` / deadline /
`smux.ErrTimeout` 都是 **stream 自己的生命周期**,拿它们拆共享承载的话,每条正常结束的
连接都会把别人的隧道一起带走。同理 `retireSession` 只摘不关 —— 判据可能误判,误判的代价
必须是「多出一条承载」,不能是「掐断在跑的流」。这两条都各自有一条反面用例钉住。

方法上有两处值得记:
- **断言要落在「这条连接被当成了什么」上。** 路由走错时连接一样会断、日志也差不多,所以
  最初写的「会话还活着吗」根本区分不了两条路 —— `handleVPNLink` 有 30s 握手期,走错了也
  能撑住。换成「同一份 `PoWChallengeReq`,回复落在裸连接上还是 stream 里」才把两个方向
  同时钉死,而且顺带覆盖了「Peek 过的字节必须原样交下去」。
- **复用有没有生效,只有数「建了几条承载」才看得见。** 退化成每流一条 WSS 时功能完全正常,
  单测不数上游握手次数就永远发现不了;singleflight 失效同理(环回一慢就是 N×15s 串行放大)。

余下 9 条:识别期与拨号的几处防御返回、`smux.Client` 之前写魔法失败那个瞬间窗口,以及
singleflight 里「等到的会话又刚好失效」这条要靠时序凑的分支。

### 第 26 轮:无鉴权控制面的那道门

`control_socket.go` 40 → 8,包 83.2% → 83.7%,变异 21 项抓 20(剩一条等价,下面说)。这个文件
的全部安全性压在一句前提上:**只有能读这个 unix socket 的本地用户才是管理员**。kick / reload /
rate-refresh 都不做任何鉴权,所以「权限没收紧却照样开门」等于本地提权,而除了一行日志之外没有
任何迹象 —— 这一轮主要就是把那几条 fail-closed 分支钉死。

未覆盖的正是它们:chmod 失败、chmod 报成功但实测权限没落到 0600、复核时 Stat 本身失败。第二条
用真实文件系统构造不出来(只在个别容器 overlay 上出现),给那一次 `Stat` 留了个仅测试替换的接缝;
另外把 chmod + 复核那一段抽成 `enforceControlSocketPerm`,于是「失败时不只是不启动,还要关掉监听
并删掉那个文件」可以直接断言 —— 留着一个 group/other 可访问的 socket 挂在那里等人来连,是这里
最坏的形状。

**覆盖率读出了一处死代码。** kick 原本是两个 switch:前一个给 session / device / user 三种形状各
建一个 picker,后一个再挑受害者。但 session 和 user 在后一个 switch 里走的是 O(1) 索引,它们的
picker 从来没被调用过 —— 那两行恒为 0 才看出来。死掉的匹配逻辑是个陷阱:改 kick 语义的人很可能
只改那两行,而真正生效的是索引那一侧。已合并成一个 switch。

**测「命中」和测「拒绝」是两件事。** 既有用例把参数校验(空 id、未知 kind、user 不存在)覆盖得很
全,却没有一条验证过 `kick session <id>` 真的踢到了那条会话 —— 而这是最常用的管理操作。算错目标
不会报错,只会回 200 加一个好看的 `kicked` 计数。现在三种形状各有一条用例钉住「只踢目标、旁站
会话必须还活着」,外加一条「追不到活会话时必须回报 0」。

限速那两个 helper 的回落方向也补上了断言:读不到当前值时必须回落到调用方给的登录快照,**绝不能
回落到 0** —— 0 在 `effectiveLinkRates` 里表示「这一层不限速」,回落成 0 就是把配额悄悄取消,而
限速看起来「生效了」。

余下 8 条:`Serve` 非正常退出那行日志、新建目录 chmod 失败与随后 Stat 失败这两个 TOCTOU 窗口,
以及 kick 里一条前置守卫(by-user 索引的键就是 `c.userID`,所以「索引里捞出来的 conn 解析不出
uid」当前不可达;留着是为了哪天索引改成按数字 id 存时审计不会把处置记到 user 0 名下)。

**变异工具本身修了两个假绿**,这一轮是被它咬了才发现的:
- 它原先每条变异各自读一遍磁盘、再从内存快照还原。一次还原失手就会连环出错:后一条变异的锚点
  在被改过的文件里找不到,报成「锚点失效」(看起来是清单写错,其实是工具漏了),而它随手拍下的
  「原始内容」已经带着上一条变异,一路传下去 —— 最后真把一条变异留在了工作树里,那是会被当成
  真代码提交掉的。改成一律以开跑那一刻的原始内容为基准施加与还原,并在收尾复核每个文件。
- 构建坏掉时,每条变异都因为「go test 返回非 0」被记成抓住。第一次跑出来的 21/21 就是这么来的,
  底下一条断言都没跑。现在开跑前先 `go build` 一遍,并把「编不过」单独分桶,不计入抓住数。

那条等价变异是 cleanup 里的 `os.Remove(path)`:Go 的 `UnixListener.Close()` 自己就会 unlink
(`SetUnlinkOnClose` 默认开),删不删没有可观测差异。生产代码里原来的注释把因果说成「靠这次
Remove 避免下次 bind 撞 EADDRINUSE」,已改准 —— 它只是为「将来换成从 fd 接管的 listener」留的保险。

### 第 27 轮:把历史上所有变异重跑一遍(审计,不加覆盖)

上一轮修掉工具的两个假绿之后,前面二十几轮的成绩单就都不可信了 —— 尤其是那些被记成「锚点失效」

**判定函数有测试,不等于调用点接上了它。** 现在补的用例走完整路径 —— 注入查询、拿到关联端口、以
正主身份投递一份 question 是另一个域名(以及一份 QR=0 的回显)的应答 —— 断言只能换来 SERVFAIL、

### 第 28 轮:SIGHUP 与登录前的那道闸门

`reload.go` 30 → 11、`pow.go` 29 → 9,包 83.7% → 84.3%,变异 16 项全抓。

**SIGHUP 这条路上,「回报成功」本身就是故障模式。** 它没有返回值,运维唯一的反馈是日志和
applied/deferred 两个列表 —— 所以把一次失败记成 applied,比崩溃更糟:崩溃会被发现。第二十三轮
在跳板机防火墙这条路上修过两处(一处 HIGH、一处 MED),但两处**都没有回归测试**,覆盖率报告里
那几行一直是空的。这轮先把它们钉住:

- 刷 ipset 失败时不许标成已应用,而且**内存里的旧名单不能跟着改**。旧名单一改,下一次同样的
  SIGHUP 会因为「集合相等」整段跳过 —— 受保护端口敞开着,运维手里是一份「已热更新」的成功
  回报,再 reload 多少次都不会重试,一直维持到重启。用例连做两次同样的 SIGHUP,断言第二次
  仍在重试。
- SIGHUP 必须自己重跑 `ValidateJumpHostFirewall`。它走的 `loadConfig` 只做 `Validate()`,不含
  这条启动期校验;于是把名单改成一堆非法项(误写 CIDR / 主机名 / 拼错)之后 reload,runtime 的
  sanitize 会把它们全丢掉,只剩自动补的 127.0.0.1 —— 真跳板机在受保护端口上被静默挡死。同一份
  配置冷启动会直接 Fatal,热更新却悄悄生效。用例额外断言此时**根本没碰过 ipset**:碰了就意味着
  「只剩 127.0.0.1」已经落到内核,人已经进不来了。

写这两条时踩了个坑值得记:一开始自己写了个「一律返回成功」的假 ipset/iptables,结果测试挂死 ——
生产代码里有「`-C` 查得到就继续 `-D`」的删除循环,假命令永远说"查得到"就转不出来。既有的
`fakeIPT` 早就把这件事模型好了(它维护集合/链/规则的状态,注释里也写明了原因),换回复用它即可;
顺手给它补了个 `failOn` 方法,替掉调用处的匿名结构体字面量。

**PoW 这一侧盯的是七道拒绝理由和它们的顺序。** 少一道就是闸门被绕开,而且悄无声息:不查过期 →
一道题永久有效;不防重放 → 一道题算一次能用无限次;签名不校 → 客户端自己给自己出 4-bit 的题。
顺序同样是安全属性 —— 防重放的登记必须在验算 nonce **之后**,否则拿到别人 cid 的人可以反复提交
垃圾 nonce 把对方的题烧光,闸门本身成了拒绝服务的工具。

入口那道「签名/难度/过期时间为空」的闸门单看结果是冗余的(伪造者过不了后面的 HMAC,同样得
`ErrPoWBadSignature`、同样记 `FailBadSig`),第一遍变异因此逃逸。它唯一不冗余的地方是**顺序**:
缺字段要在解 salt 之前被拦下。补了一条「缺字段 + salt 也不合法」的用例钉住这个顺序 —— 这类
「结果相同、只有顺序不同」的判据,是变异测试最容易暴露、而读代码最容易漏掉的一类。

### 第 29 轮:登录的分档,与子网路由的两类闸门

`auth_login.go` 28 → 3、`subnet_route.go` 28 → 13,包 84.3% → 84.8%,变异 24 项抓 23(1 等价)。

**登录那两张 code→文案 / code→action 的表,看着像文案,实际是运维唯一的抓手。** 文件顶部记着
2026-05-21 那次:安装脚本换了 DB 路径没迁用户,所有客户端登录返回 403,而 audit_logs 里只有一行
扁平的 `action=login.fail`,既不能按子类聚合、又不在 ERROR 级别,等用户感知已经 11 小时。修法是
「每个失败原因一个独立 action,全挂在 `login.fail.` 前缀下」——**修完没有任何断言守着它**,14 个码
里当时只测了 5 个。这轮改成整表驱动,并且不止比对字符串,还钉住三条结构性要求:每个码有自己的
action(复制粘贴漏改会让两类失败在报表里并成一类)、失败一律在 `login.fail` 前缀下而成功一律不在
(否则失败率报表把成功也算成失败)、对外文案里不许出现 SQL / 内部标识。

PSK 校验的失败分档同理,而且坏法是双向的:把「用户不存在」报成 500,运维去查服务器而不查用户表;
反过来把内部错误(库读不动)报成 401「用户名或密钥错误」,用户一直重输密码,而真正的故障——数据库
——没有任何人看见。后一条用改表名造出真实的读失败来钉住。

**子网路由这边是两类闸门,此前一条断言都没有。**

一是**载入时的过滤**:转发表从 DB 里 approved 的行重建,但「approved」不等于「可转发」——批准发生
在过去,而校验规则会变严。第十一轮修的那条 MED(放行公网/宽段 CIDR 等于绕过出口闸和出口 ACL,
confused deputy)至今没有回归测试;它不报错、`route list` 里照样显示 approved,只能靠转发表里没有
它来判断。用直写 DB 绕过归一来复现「历史批准 / 手工 SQL」这条真实路径。同批还钉住:DB 读不动时
保留旧表(清空等于所有内网路由同时黑洞,而原因只是一次 DB 抖动)。

二是**表未加载时的方向**。这几个判据在启动瞬间和 reload 窗口里会读到空表,「不属于」和「暂时不
知道」无法区分,于是每处都得显式选一个方向,而且方向不能选反:投递门控 fail-closed(选反 = 撤销
审批后 FRP 仍能打进 LAN),4via6 反源收窄 fail-open(选反 = 每次 reload 抖一下就断掉一批合法回程)。
两个方向相反、各有各的事故形状,现在各有用例。

两条值得记的返工:`deviceID=0 不该匹配任何网段` 第一遍逃逸,因为表里根本没有零值行,断言等于没测;
在表里塞一条 `device_id=0` 才真正钉住(正常 DB 有外键造不出它,但这个函数收的是任意一张表)。另一条
`0/0 与 ::/0 也收进表` 判定为等价——紧随其后的 `PrefixWithinAdvertisable` 同样会挡掉默认路由,两道
闸重叠,无可观测差异。

### 第 30 轮:出口选择与公网端口的拒绝路径

`egress_select.go` 38 → 29、`port_forward.go` 33 → 18,包 84.8% → 85.2%,变异 15 项抓 12(3 等价)。

**出口选择这条路上,「拒绝」有两种写法,差别是安全性的。** 一种是明确拒绝(回 ack、把绑定置成
fail-closed 哨兵,数据面就地丢包),另一种是静默回落 server 自出口。后者曾经真实存在:用户点名经 C
出网、服务器答「不行」,然后把他的公网流量从 server 自己的公网 IP 送出去 —— 三机实测(2026-07-25)
复现到出网 IP 变成 server 的地址,用户侧唯一线索是客户端一行日志。这轮补的是尚无断言的两个分支,
它们方向相反、都不能错:没有出口权限 → 明确拒绝;DB 暂时查不动 → **一个字都不改**、回 try_again
让客户端重试(当成「未批准」就是一次库抖动把人从选定出口踢回 server)。另外钉住「每次重新选择都
复位那两个一次性闸」——不复位的话,换到新出口后它离线不再通知(用户干等),换出口也不再进审计。

**端口转发这边同一个母题:不改现状、不假装成功。** reload 读不到映射表时保留现有监听(清空等于把
所有公网入口一次性关掉);Accept 遇瞬时错误退避重试而不是退出循环(退出就是那个端口从此不接客,而
运行态里它仍是 running,只有用户会发现连不上);解析不出目标就关连接,绝不盲拨陈旧 vIP。

三条判为等价,都值得记下原因:`parsePacketTuple` 失败时一律返回零值 tuple,零地址不可能是公网 v6,
所以 v6 快失败里那道 `!ok` 是防御性冗余(将来它若返回部分结果就不冗余了);`sendEgressSelectAck`
入口的 `safeLinkConn()` 只是 race-free 预筛,写锁内还有一次复核;`resolveDeviceID` 的空 UUID 闸只
省一次 DB 查询。

两条逃逸暴露出**同一个毛病**,跟上一轮 `deviceID=0` 那条一模一样:断言里的表根本不含能触发该闸的
表项,于是断言等于没测。`frpLANReplyFromDevice` 要塞一条 `deviceID=0` 的表项才真正钉住匿名会话那道
闸;reload 的第 ③ 段清理要拿一个 **bind_failed** 的端口才测得到 —— 在跑的映射被删时,停监听那条路
顺手就把状态清了,只有压根没进 active 的失败态才需要这段扫描。这类「断言的前提没建立起来」是变异
测试最常揪出的一类,读代码时几乎看不出来。

还有一次返工是测试自己造的数据竞争:用「拨一下看通不通」证明监听还活着,会催生一个连接 goroutine
去拨那个不可达目标,挂满 10s 拨号超时、活得比用例还久,而它一路读的 `globalContext` 会在 harness
收尾时被还原。改成「试着重新绑同一个端口,绑得上才说明监听被关了」——不催生 goroutine、也更直接。

### 第 31 轮:虚拟 IP 的分配与占用

`alloc.go` 20 → 2、`alloc_lease.go` 21 → 0,包 85.2% → 85.7%,变异 20 项抓 17(3 等价)。

**这一块出错只有一种形状:两台设备拿到同一个地址,或者拿到一个不属于本网段的地址。** 两者都不
报错 —— 登录成功、审计正常、后台一切正常,数据面表现是「其中一台时通时不通」,查到根因通常要很久。
分配器此前只被测过 IPv4 /24 的顺序分配:**v6 整条路径从未跑过**,而配了 `subnets_v6` 的部署走的
就是它;第八轮修掉的那条(前缀长于 /112 时算术把网络位写脏,生成前缀外地址)也一直没有回归测试。

**顺手挖出一个真缺陷,而且是 panic。** `[tun].subnets` 写成 v4-mapped 形态(`::ffff:10.0.0.1/24`)
能过配置校验 —— 地址解析出来是 v4,族检查看不出问题。但分配器里网关做了 `Unmap()`、网络地址是
`Masked()` 的产物(`::ffff` 那几个字节被一起掩掉,退不回 v4),于是族一分岔:走 v4 分支却对 v6 形态
调 `As4()`,**直接 panic**。发作时机是第一个客户端登录,不是启动,所以 `config lint` 和开机自检都
照不出来。两侧都修了:分配器开头显式拒绝族不一致并报清原因,配置校验直接拒掉这种写法(掩码会按
128 位解释、下发成 `0.0.0.0`,地址池一个都分不出来)。

**「偏好 vIP」这条快路一直是缺陷高发区,这轮把它的过滤面钉全了。** 自动分配从主机位 2 起扫,天然
避开网关 / 网络 / 广播地址;而直接采用偏好 vIP 没有那层过滤 —— 管理员把 `fixed_vip` 手钉成网关或
定向广播地址时,网段检查会通过、`used` 里也没有,客户端就拿到一个用不了的地址。前者与 server 网关
撞车整条路由断,后者部分内核直接丢弃以广播为源的报文。两条都是修过的缺陷,现在各有断言。

落 lease 的两类错误也钉住了方向相反的取舍:撞 vIP UNIQUE **必须拒登**(说明 alloc 漏算了库里的
离线 lease,放过去就是两台设备同一个地址),其它 DB 故障只 warn 并**放行**(lease 存不下只影响下次
能不能拿回同一个地址,不值得让人登不进来)。混在一起处理的两种坏法方向也相反:都当致命 → 一次
库抖动全员登不进;都当无害 → 两台设备带同一个 vIP 上线。

三条判为等价,原因值得记:上界夹取与 `prefix.Contains` 兜底**互为冗余防线**,单拆一层另一层就补上,
行为不变 —— 但「两层同时拆掉」的组合变异被精确抓住(报出「第 255 次分配给出 `fd00:80::100`,落在
`/120` 之外」),说明这对防线真实存在而不是两层都空。第三条 `maxIter < 1 → 1` 的夹取则是真正不可
观测:循环从 `i = 2` 起,maxIter 取 -1 / 0 / 1 都是零次迭代。**冗余防线这个母题以后会反复遇到 ——
单拆不可观测不等于没测,要用组合变异证明「至少一层在」。**

还有一次是测试自己写崩:把 `/64`、`/112` 这种 65534 容量的池子整个分光,而分配器每次都线性扫描,
总复杂度 O(n²),四分钟都跑不完。大池子只抽查前几百个 —— 那条修复只在主机位少于 16 的小前缀上才
改变行为,小前缀才需要分光。

HEAD 上的提交是完整的,已 stash 收起备查后恢复。**教训:每轮开工前先 `git status` 确认工作树干净。**

### 第 32 轮:TUN 数据面、双栈登录、连接接管

`server.go` 587 → 486,包 85.7% → 87.2%,变异 32 项全抓(含 7 项配置 / 下线广播)。

`server.go` 一家占了全包未覆盖的 58%,但里头 379 条是 `main` 的守护进程启动编排(只能在真实
进程里跑,由 e2e 插桩那侧补,这也是合并后 92.6% 远高于单测数的原因)。真正的缺口是**数据面两条
循环整个函数一行没跑过**:`tunReadLoop`、`tunWriteLoop` 各 33 条。这两条循环是所有流量的必经
之路,而它们的坏法全是静默的。

**丢包路径不还池子是典型的慢性泄漏。** 队列满时丢包是**有意的**(宁可丢也不阻塞整条上行),但丢
之前必须把 buffer 与包结构还回 `sync.Pool`。不还就是每丢一个漏一个 2KB,一次拥塞几万个 ——
内存一路涨到 OOM,而现场只看得到「丢过一些包」。`drainAndCloseTunChan` 同理:每次 shutdown /
重建队列漏掉队列里那上千个在途包。

**写循环的坏法方向相反:一次写失败就退出循环 = 全服下行静默变黑洞,而所有会话仍显示在线。**
所以写错误只记日志继续跑;而 ctx 取消与队列关闭两条退出路径必须都通,否则 shutdown 挂住。
另外 Linux 的 `IFF_VNET_HDR` 要求写时前留 virtio 头,少留几个字节内核就把包头当 virtio 头解析
—— 每个下行包都被丢弃,链路层看起来完全正常。

**登录侧这轮补的是双栈。** v6 地址池耗尽必须**只降级不拒登**(v4 还能用,拒登等于因为 v6 满了
把整台设备赶下线);重连要能拿回同一个 lease(拿不回就是 MagicDNS / 已装路由全部指向旧地址)。

**接管(takeover)是这轮最值得写的一块:它要在换链路的同时把会话状态整套搬过去。** 漏搬任何一项

失效、漏 vIP 就是登录成功但数据面全黑。secret 必须轮换,且**熵源故障时保守拒绝而不是降级用旧
secret**(降级会静默削弱一次性语义);为了能验这条,给 `generateTakeoverSecret` 加了随机源接缝。

  足以反复触发 GC)。压掉这两处噪声后还剩一处压不掉:**`-race` 下 `sync.Pool.Put` 会故意随机丢掉

**顺手修掉两处测试自身的缺陷,都是这轮全量 `-race` 才暴露的。** 一是上面那个池化门槛;二是

### 第 33 轮:MagicDNS 的 ACL 口径、路由批准广播、ACL 裁决与丢包审计

`acl_drop_audit.go` 15 → 1、`acl_runtime.go` 28 → 9、`route_advertise.go` 17 → 9、
`magic_dns.go` 42 → 35,包 87.7% → 88.0%(全包未覆盖 903 → 846),变异 34 项全抓、零逃逸。

到这一轮,剩下的缺口已经很碎:最大的几块(`startEmbeddedHysteria` 16、`startPortForwardManager` 11、
`verifyServerIPv6RoundTrip` 10)都要真监听 / 真网络,归 e2e。所以这轮挑的是三块纯进程内的。

**MagicDNS 的 ACL 口径是一处「五个兜底都必须 fail-open,但最后那一下必须真的拦」的组合。**
这道闸堵的是信息泄漏:ACL 判定 A→B 完全不可达时,A 不该能用 MagicDNS 把 B 的设备名解析成 vIP
(否则等于提供了一个探测对方存在性与地址的接口,尽管数据面随后会丢包)。但它每一处「查不到」都
必须放行 —— 判错方向的代价是**同用户自己的设备名突然解析不出来**,现场只看得到「DNS 挂了」。
所以五条 fail-open(快照未装好 / 查询方 vIP 不在归属表 / 名字查不出归属 / peer 地址畸形 / 同用户
自查)与一条「ACL 真判不可达时必须拦」各有断言,少了后者前面那些兜底就等于把闸拆了。

**应答构造那条与第 31 轮 alloc 里的 panic 同一族问题。** 双栈设备两族地址都有,而一次查询只问
一族。A 查询里遇到 v6 地址若不跳过,就会对它调 `As4()` —— 直接 panic,一次查询打掉整个 DNS
goroutine;AAAA 里塞进 v4-mapped 则答出 `::ffff:10.x`,客户端拿它发 v6 必然不通。

**路由批准广播做的两件事表面无关,漏掉任何一件都不报错。** 一是推 RouteApproveStatus 让宣告方
UI 的「待审批 → 已批准」实时翻转(不推就一直显示 pending,用户以为没批而反复重发声明);二是刷新
会话上的**源地址伪装豁免闸** —— 批准后不刷,宣告方合法的回程流量会被一路丢到它下次重连;撤销后
不刷,则是特权多留了同样久。这两条方向相反,所以「只敢开不敢关」也单独钉了一条变异。

**ACL 裁决这侧最容易写反的是白名单语义。** 整段裁决有个 fast-path:user 规则集为空时跳过引擎 ——
但**跳过引擎不等于放行**。`default=deny` 的语义是白名单,规则集为空意味着「谁都不在白名单里」,
必须全丢。写反的后果完全静默:管理员切到白名单模式、还没加 allow 例外,以为已经全锁,实际全网
互通照旧。同一函数里还有一对方向相反的收敛:快照未装好 → fail-open(不然服务刚起来那一下全网
不通),包解析不出 → fail-closed(它已过 ValidIPPacket 仍解不出,放过去就是绕过整个裁决)。

**端口封锁的分片绕过与源地址反欺骗的优先级,是这轮两条真正的安全属性。** 非首片分片里没有 TCP
头,拿不到端口;若判「规则不匹配」就落 default=allow 放行,而目的端会重组出完整的 22 端口连接 ——
攻击者只要分片就能穿过 `deny tcp:22`,日志上什么都看不到。反欺骗那侧钉的是顺序:「冒充另一在线
会话的 vIP」必须判在「已批准出口 / 子网转发者豁免」**之前**。顺序写反就是可利用的漏洞 —— 出口
宣告方本来被允许用任意非 vIP 源地址(它要中继外网回程),豁免若先判,它就能以另一个客户端的 vIP
作源注入伪造回包,对受害者来说那些包看起来来自它信任的对端。

**丢包审计的失效方式是把服务拖垮,而不是少记一条日志。** 它跑在数据面热路径上,每个
(src,dst,proto,port,kind) 组合一个桶 —— 一次端口扫描就能塞进六万多个,而 flush 周期是 60s。
所以有基数上限,超了折叠进单一 overflow 桶:维度信息丢了(target 变 `<overflow>`),但丢包数目仍
准确,而这种情形本身就说明「有人在扫端口」,细分维度也没有排障价值。另外 `interval <= 0` 的夹取
是防 `time.NewTicker(0)` panic —— 那个值来自配置,不夹取就是一条配置项能带走整个进程。

### 第 34 轮:真实客户端 IP 的透传、闲置租约回收、出口 DNS 解析、子网路由的丢包路径

`loopback_proxyproto.go` 14 → 0、`lease_gc.go` 12 → 2、`magic_dns_cache.go` 12 → 10、
`subnet_route.go` 13 → 4,包 88.0% → 88.6%(全包未覆盖 846 → 810),变异 21 项全抓、零逃逸。

**PROXY 头那块的失效方式是静默退化成 server 自己的 IP。** 它把承载层看到的真实客户端地址透传给
上层,而上层拿这个地址做限流、封禁、审计。`normalizeProxyAddr` 要把 hy2 的 `*net.UDPAddr` 转成
`go-proxyproto` 认的 `*net.TCPAddr`(转不动就整段跳过写头),所以一旦这里认错类型,现象是**所有
QUIC 客户端在风控看来都来自同一个 IP** —— 封一个等于封全部,而日志里的地址字段仍然填得满满的。
反方向那条是安全边界:`isLoopbackConnPeer` 限定只有回环对端能带 PROXY 头,否则任何外部连接都能
自己声明一个源 IP,把封禁与限流一起绕过。

**租约回收的危险不在「没回收」而在「回收了正在用的地址」。** GC 按闲置天数删租约,但一台连着
好几天没断的机器同样「很久没更新过租约」—— 判据写宽一点就会把在线会话的地址收走,回收后它被分给
新设备,两台机器同一个 vIP。所以钉了一条「长会话的地址永远不许被收」。另外两条是配置面的:
`idle_days <= 0` 必须彻底关掉这个循环(不是当成 0 天,那会秒清全部租约),`interval_hours <= 0`
要夹到默认值(防 `NewTicker(0)` panic)。GC 循环还必须能扛住一次 DB 失败继续跑,不然一个瞬时
错误就永久停掉回收。

**出口 DNS 解析这块的观测量是 TTL,写错就是缓存污染的时长。** 一条应答里多个 A/AAAA 记录 TTL 不
同,缓存必须取**最小**那个;取最大就是让已经失效的地址在缓存里多活一段。CNAME 的 TTL 不能参与
(它描述的是别名的有效期,不是地址),NXDOMAIN / NODATA 这两种「没有答案」的应答要按 RCODE 区分
缓存,而畸形 / 截断的应答必须整条拒掉 —— 半条解析出来的答案进了共享缓存,受害面是所有客户端。

**子网路由的丢包路径,「丢」与「不丢」都不能回退。** 这个函数的返回值决定调用方还走不走后面的
出口 / server 链路,所以「按策略丢弃」必须报告已处理:报告未处理意味着一个发往 `192.168.x` 的包
继续往下走,最后从 server 的公网网卡发出去 —— 内网地址与内网访问意图一起泄漏到公网上,而触发条件
是「宣告方队列满」「包超长」这类临时状况,现象间歇、极难查。反过来「不归我管」的两种(nil 会话、
解析不出五元组)必须放回原链路,否则这些包被这条路吞掉。server 主动发起那条另有一道:目的必须落在
宣告方**当前**宣告的前缀集里 —— 库里批准过不等于它现在还在宣告。

顺带修了一处 `tunReadLoop` 里的共享读:ctx watchdog 是分离 goroutine,它与主循环各自去读全局
`globalContext`。两者本该看同一个 ctx,否则「谁关的 dev」与「退出日志算不算预期路径」会参照不同
的 ctx。改成入口一次取定的局部变量(`-race` 下由 TUN 数据面用例报出来的)。

### 第 35 轮:经出口解析的失败分支、ICMPv6 秒回落、端口转发的启动编排

`magic_dns_exit.go` 17 → 4、`port_forward.go` 18 → 3、`egress_select.go` 29 → 24、
`magic_dns.go` 35 → 33,包 88.6% → 89.1%(全包未覆盖 810 → 773),变异 17 项全抓、零逃逸。

**经出口解析这条路的失效方式不是「查不到」,而是悄悄回退成 server 本地上游的答案。** 一个绑了
peer 出口的会话,公网流量全从出口走;DNS 若由 server 本地解析,CDN 会按 server 的地理位置给边缘
节点 —— 那些节点对出口可能是烂路由甚至不可达,而客户端 OS 已经把答案缓存起来,换回直连后还要继续
误导它一段。所以口径是「确定绑了出口就必须由出口作答,出口给不出答案就 SERVFAIL」。这轮把四种
「给不出」逐条钉住:应答的答复区截断(A/AAAA 与 HTTPS 两条路各一份)、server 无 v4 网关构不出注入包、
出口迟迟不答(超时)、以及关联端口耗尽。最后那条尤其要拒不要凑:关联端口是「回包属于哪条在途查询」
的唯一凭据,复用一个已占用的端口会让两条查询的应答互串,而两边看起来都成功了。这些失败都不许落
缓存 —— 缓存是全 egress 共享的,一份解析不出的应答进去,受害面是这台出口上所有客户端。

**HTTPS/SVCB 必须与 A/AAAA 同路。** 浏览器现在对每个站点并发查 A/AAAA 与 HTTPS(65)/SVCB(64),
而 HTTPS RR 里的 ipv4hint/ipv6hint 同样被 CDN 按解析位置就近下发。只把 A/AAAA 引到出口就留了一条
同病的旁路:浏览器优先用 hint 直连,拿到的还是 server 地理的边缘节点。反方向也钉了一条 —— MX 这类
没有「按解析位置就近」语义的类型不该多绕一趟出口(每条最多占位 2s 在途位)。

**那帧 ICMPv6 的作用是让客户端立刻失败,而不是让它通。** server 无 v6 公网出网时,使用方发往公网
v6 的包无处可去;什么都不回,Happy Eyeballs 要等、QUIC 更要等十几秒才回落,用户看到的是「网页转
半分钟」。所以每处细节都是「能不能被内核采纳」:整包必须裁进 IPv6 最小 MTU 1280(超了在路上被丢
等于没回),校验和必须对(错了内核静默丢弃),而构造不出来时绝不能投一段半成品占掉一次下行。

**端口转发的启动这一步做了三件互不相干的事,失效都不报错。** 一是解析 mesh 网段 —— 这是「target_ip
是 mesh vIP 还是节点 LAN 后的设备」唯一判据,v6 那段漏解析会让 v6 vIP 目标进 LAN 精确路由表,数据面
的源反欺骗放行表跟着跑偏;二是清掉上次崩溃残留的放行规则,不清则那些端口一直对公网开着,而 web 上
看不到任何映射;三是把自己发布成全局单例,没发布则之后所有 reload 都是 no-op,表现为「改了映射要
重启才生效」。另外主机路由是按引用计数共享的(同一台 LAN 设备的 80 与 443 共用一条 /32),删映射时
不看计数就删,另一条映射当场断而它自己什么都没改。iptables 那侧则相反 —— 系统命令失败只 Warn:
容器里没 CAP_NET_ADMIN、机器没 ip6tables 都很常见,当成致命错误就是 v4 一切正常的机器整个特性起不来。

### 第 36 轮:PoW 出题限速表、审计回收循环、SIGHUP 延迟字段、账号失效扫描、子网路由列表

**PoW 出题限速表的键来自未认证的对端地址,所以它有两个反向的失效方式。** 限得太松:单 IP 可以

本身。反方向同样要钉:把「效果不变」的改动误报成 deferred 也在毁掉这个信号,一旦列表常年有噪声
运维就不再看它。exit_mode / exit_deny_private / exit_dns_redirect 都有归一化语义(空值、大小写),
归一化前后必须一致对待 —— 注意 exit_dns_redirect 的空值归一到 **auto** 而不是 off。

**账号失效扫描手里握着「把在线会话踢下线」的权力,所以每个不确定分支都必须收敛到不踢。** 代价

一个持锁反复读表的死循环,把整条扫描 goroutine 卡住、所有账号级失效判定一起停摆。

**子网路由列表的 Online 位不能只看「设备有会话」。** 一台机器可以连上来但这次没带
`--advertise-routes`(或重连时收窄了宣告集),而 DB 里的批准还在。此时标成在线,用户会看到一条
标着「可用」的网段而流量在数据面被丢 —— 数据面丢包的判据恰恰是同一份当前宣告集。UI 说能走、包却
不通,是最难查的一类:两侧都"正常"。同时保留「宣告集未知 → 保守放行」与数据面的 nil 兜底同口径,
否则老客户端的全部网段一律显示离线。

`broadcastExitsList` 同一族问题,补了个等广播落地的同步点(它同时也是「宣告方晚于请求方上线时
必须当场刷新 online」这条断言)。

### 第 37 轮:上游 DNS 转发、限速连接计数、路由审批细节、ACL 快照构建、管理面定向刷新

`rate_conn.go` 8 → 0、`route_advertise.go` 9 → 1、`acl_runtime.go` 9 → 1、`control_socket.go` 8 → 5、
`magic_dns.go` 上游侧收口,包 89.7% → 90.1%(全包未覆盖 732 → 699),变异 21 抓 + 1 条等价。

**会话刚连上的那一两秒里,公网名解析拿到的答案会被客户端连同 TTL 一起缓存下来。** 那一刻 mesh 路由 /
iptables 可能还没就位,答案反映的是「还没配好」时的可达性,而 CDN 的 A 记录 TTL 常是几百到几千秒 ——
于是「刚连上打不开某站」会一直持续到 TTL 过期,那时链路早就正常了。这类现象只在刚连上的窗口里出现、
复现时又已经好了,是最难归因的一种。早期窗口内钳短 TTL 这件事本轮才第一次有断言,连同「钳了要记计数」
一起钉住(没有计数,排查时看不出它发生过)。

**上游应答的反投毒校验此前只有单元测试,没有一条走过真实转发路径。** UDP 上任何能伪造 upstream 源地址
的人都能在真应答前抢注一包;连接态 socket 只按 5-tuple 过滤,挡不住这个。收下一包错答,污染的是 server
给**所有**客户端的答案。同时钉住反方向:查询本身解析不出 TXID/question 时要退回「收第一包即返回」——
安全加固不该顺手砍掉一条既有的可用路径。另外读循环的 2 秒读超时是用来回头看 ctx 的,把它当致命错误
退出就是空闲两秒后 MagicDNS 整体停摆,而进程还活着、监控上一切正常。

**限速连接是每个字节的必经之路,它的计数器就是「客户端上传/下载」的唯一读数。** io 协议允许 Read 返回
`(n>0, err)`,连接关闭那一帧通常正是 `(n>0, io.EOF)`;漏掉它的现象是统计悄悄少算 —— 单连接看不出来,
smux 子流 / PoW / keepalive 这类高频短连接累积起来就把读数拉歪,而没人会怀疑一个一直在涨的计数器。
Write 侧的部分写同理。反过来,关闭那一帧**不该**再去等令牌:这一帧之后不会再有 Read,低速限制下白等
几百秒,期间 linkWrMu 一直被占着。(写这条断言时踩到一个陷阱:桶容量小于单帧字节数时 `WaitN` 会以
「超过 burst」立即报错,等待根本不会发生,断言观测不到任何东西 —— 桶必须开得比帧大。)

**「admin 先批准、客户端后重发声明」这个时序此前没有覆盖。** 走到的是另一半代码:宣告帧到达时若该设备
已经批准过,要当场打开源地址伪装豁免闸并广播出口列表。不做的话宣告方的出口回程流量被当伪装丢掉,
而使用方的下拉里看不到这台在线出口 —— 两侧都表现为「批了但用不了」。子网侧还多一个前提:只在路由表
确已加载时才据其改写豁免闸,否则启动初 / reload 瞬间会把一个其实已批准的宣告方的豁免误清成 false。
审批项的时间戳取「宣告」与「批准」里更晚的那个;两个时间戳都是秒级,同一秒落库会相等,所以断言里
必须把宣告时间显式推早,否则取错字段根本看不出来。

**ACL 快照是数据面每个包唯一看的东西,构建时放错桶后面全错,而 `acl list` 显示的仍是库里那份正确配置。**
未知的 default 值必须收敛成 deny —— 方向错了就是整台 server 默认放行,一次配置笔误即可触发。出口规则里
`src_user_id=0` 是「对所有用户生效」的通配写法,落进 by-src[0] 就永远没人命中,管理员配的限制静默失效。
另外 `aclAllows`(CLI 问答口)在快照未加载时必须 fail-open,与数据面同口径,否则运维会看到一屏「全都不通」
并据此改配置,而数据面那侧其实在放行。

「带端口的规则不压到无端口流量上」这条又是**冗余防线单拆不可观测**的老母题:proto 判断与 `hasL4Ports`
判断各自都足以挡住 ICMP,拆掉任一层另一层就补上。按第 31 轮的做法用一条「两层同拆」的组合变异证明
至少一层在;单拆那条在归档里标为等价变异。

顺带修了一处我自己写的测试污染:`/reload?what=routes` 会把子网路由表装进全局并留在那儿,不还原的话
后面任何跑登录的用例都会在握手中间收到一帧 RoutesList(`pushInitialRoutesList` 的正常行为),读帧断言
随即对不上 —— 现象是一个与改动毫无关系的登录用例失败,排查成本远高于加这四行还原。

全都不报错:空 IP 若当成正常键,所有「取不到对端地址」的失败会堆到一个不属于任何人的键上,真正的攻击 IP

待查项:这一轮的第一次全仓 `-race` 里 `TestLoginStorm_MaxSessionsNotExceeded` 失败过一次(1.53s 就失败,

再筛,不要在管道里丢掉上下文。下轮开工时先带着这条跑一次全包 race。

**`/health` 反射的是 TUN / store 的就绪状态,对扫描器很有用:** 它标出这台机器什么时候处在故障窗口里
(故障期更容易被撞开),也直接给出「这是一台 nanotun server」的指纹。所以非环回地址默认拒启,只留一个
显式环境变量作逃生口 —— 曾有运维把它误配成 `0.0.0.0`。另外三种输入各有各的正确行为:空地址是「运维
明确关掉」而不是「用默认端口启动」;解析不出的地址只是不启动,不能让整台 server 起不来;每种情况都必须
返回一个可调用的 cleanup,因为 main 里那条 defer 链拿到 nil 会当场 panic —— 一个可选的探活端点把整台
server 带下去。

### 第 39 轮:WSS 入站握手收尾、上次网段探测、HTTPS 经出口中继

**Upgrade 成功之后 handler 还要撤掉 accept 时设的握手超时。** 那个截止时间是给「连上却迟迟不发握手」的
慢连接用的,可它是设在底层 conn 上的绝对时间,Upgrade 之后不会自动消失 —— 不撤的话,一条完全正常的
数据面长连接会在握手超时那一刻突然读失败断开,客户端表现为「连上就用、十几秒必掉线」,而服务端日志里

探测失败拦住启动,等于一次 restore 写坏文件就再也起不来。反面同样重要:探测到什么就必须沿用,换网段会让
所有客户端手里的 vIP、ACL 目标、端口转发目标全部指向旧网段,表现是重启后全站不通而每条日志都正常。

顺带钉住了 fixed vIP 掉出网段的**告警去重**。数据面在这种情况下会静默改走自动分配(对的:钉的地址在新网段

就把唯一的线索埋进自己刷出的噪声里;而在网段内也打,则是把本来对的配置报成异常。

### 第 40 轮:panic 兜底、supersede 等待、出口列表推送

`safego.go` 4 → 0、`supersede.go` 4 → 0、`exits_list.go` 4 → 2,包 90.6% → 90.8%,变异 12/12 全抓
(含一条「两层同拆」的组合变异)。

**panic 兜底这一层是「一条连接挂掉」与「整机瞬断」之间唯一的隔离,而它两个方向都不能错。**
per-connection 的 panic 不许升级成进程退出:Go 的默认行为是任一 goroutine panic 直接终止进程,
一个畸形包打崩一条连接的处理 goroutine,全部在线用户同时掉线,而且 `cleanupConnection` 也不会跑 ——
vIP 占用位、`connIDMap`、TunChan 全留在内存里陪进程一起死。反方向:关键全局 goroutine(TUN 读写、
demux、保活)的 panic **必须**升级成 graceful shutdown。只 recover 不做别的更糟 —— 进程还活着、监控
绿着、systemd 不会拉起新实例,而数据面已经停了:客户端连得上、包不通,没有任何一条日志说破。
第三个方向也钉了:正常返回不许触发关机,否则每个正常收尾的后台循环都会顺手把整机带下来。

**supersede 存在的全部意义是「同一台设备重登,vIP 不变」**,为此新连接要等老连接彻底清理完才去分配
地址。这段等待有三条边界:victim 列表里的 `nil` 会在解引用时 panic,而这段跑在登录路径上,炸的是正在
登录的那个用户;重复项会让同一条连接被 close 两次、被等两次;总等待必须硬顶在 `supersedeWaitTimeout`
内 —— 这里曾是「逐条各等 5s」,多条 victim 同时卡在 `takeoverMu` 时退化成 5s×N,新连接的握手响应被拖到
客户端超时,用户看到的是「重连要等半分钟甚至失败」而服务端一切正常。到点未清完要继续登录(退化成
无 supersede:可能换个 vIP)并打 WARN,而不是拒登 —— 拒登比换地址更糟,设备得等那条卡住的老连接自己超时。

为了把等待时间调到几百毫秒,`supersedeWaitTimeout` 从 const 改成 var(生产不改这个值)。

**出口列表是情报**:它告诉对方这个 mesh 里有哪些设备能当出口、此刻谁在线。所以没有 `exit_allowed`
的会话一个字节都不能收。这条闸有两层(初始推送入口 + 单条推送),单拆任一层另一层都补得上,于是单条变异
永远逃逸 —— 这正是第 31 轮记下的「冗余防线」母题。这轮顺手给变异脚本加了 `also` 字段:一条变异可以带
若干附加改动,一次同时拆掉多层,从而证明这对防线真实存在而不是两层都是空的。

推送还必须带写超时并在写完撤掉:这条链路写在持 `exitsBroadcastMu` 期间,一个 TCP 窗口写满的客户端
没有写超时就会一直占着这把锁,拖住**所有**出口列表广播与初始推送 —— 现象是别人的出口下拉长时间不更新。

`exits_list.go` 剩的 2 条是 `MarshalExitsList` 失败与写锁内的 nil 复核,都是不可达兜底。另有一条
「查 DB 按 device 去重」的效率闸没能变异验证:`gatewayState.store` 是具体类型,进程内无法数 DB 调用次数,
而它的效果只体现在开销上(同设备 N 条会话 → 每次广播乘 N 次查询),不改变任何可观测的输出。

### 第 41 轮:server 自身 v6 出网探测、PoW 清扫、非 Linux 桩

### 第 42 轮:DNS 闸的 fail-open、畸形应答、hy2 地址中转、僵尸 smux

`magic_dns.go` 27 → 19、`magic_dns_cache.go` 10 → 1、`loopback_smux.go` 9 → 7、`hysteria_clientaddr.go`
补齐、加上一批小函数(匿名设备索引、isolate 提醒、非 Linux sweep 桩、drain 超时兜底),包 91.0% → 91.4%
(未覆盖 612 条),变异 25/25 全抓(含两条「两层同拆」的组合变异)。

**MagicDNS 的每一道闸都必须 fail-open,因为 fail-close 的表现是「域名解析不了」而不是「拒绝访问」。**
mesh 总开关、ACL、isolate 三道闸都要先认出查询方是谁,而查询方地址可能压根拿不到(nil peer、无 IP、
长度畸形)。这时候拦下来最省事,但 server 本机自查、健康探测同样从这条路进来,拿到的是 NXDOMAIN ——
运维会去查 DNS 配置,而真正的原因是一道安全闸在信息不足时选择了拒绝。同理,4via6 站点映射指向一台
已删除的设备时不能推出一个「无主」的 user id 去比对(那会误判成同用户放行),设备表读不动时也不能当成
「没这台设备」继续往下走 —— 前者是越权,后者是把一次 DB 抖动变成整片名字的 NXDOMAIN。

**畸形应答的唯一正确处置是整条丢掉,不能半条入缓存。** 出口 DNS 结果是**共享**缓存:A/AAAA 的 rdata
被截断、答复区里混进未知类型、question 段的标签越过报文末尾,只要有一处「解析到哪儿算哪儿」,残缺的那
半条就会被后续所有查询命中,直到 TTL 结束。改写不出来时必须 SERVFAIL —— 客户端会重试或回落,而返回一个
自认为「差不多对」的应答等于把错误答案钉死。question 偏移那条还是一对冗余防线(循环顶部的 `pos >= len`
与末尾的 `pos > len`),单拆任一层另一层都接得住,要靠组合变异才能证明它们真在。

**读循环在 in-flight 打满时必须就地丢包并记数,不能排队等位。** 阻塞等位会把内核接收队列堵满,于是
攻击者用几十条慢查询就能让整台 server 的 MagicDNS 停摆;而丢包不记数则让「偶发查不到」永远查不出来。
写这条断言时踩了一次假绿:只断言「池满时没有立即回应」的话,阻塞版本会在腾出位子后把那条查询补答上去,
一样是绿的。给两条查询各一个 txn id、分别在「池满时」和「腾空后」发出,才能区分「丢了」和「晚答了」。

**hy2 真实客户端地址中转表**的 token 撞号被断言抓住了,是个真缺陷:熵源故障时降级用时间戳串,而 macOS
的 `time.Now()` 只有微秒分辨率 —— 同一微秒内的两次调用拿到同一个 token,两个客户端的真实地址互串,
之后限速、IP 失败计数、审计全部记到对方头上。修法是给降级路径挂一个原子单调序号。

**smux 僵尸会话**:承载连接死了而 `Session.IsClosed()` 仍是 false(keepalive 还没到期),这时池子必须靠
`OpenStream` 的失败自己摘掉会话并重建,否则新流会连续失败到 keepalive 超时为止。

顺带把两处 const 改成 var 接缝:`shutdownDrainTimeout`(否则「负超时要回落成默认」这条无法在秒级观察)。

**终于定位到挂了两轮的那条偶发失败,而且两条是同一形状、都在测试侧:**上一个用例 `go handleVPNLink`
派生的 goroutine 还在跑,下一个用例的 setup/cleanup 就已经在写 `sharedTUNGateway` / `globalContext`
了。测试用例自己不会失败在正确的地方 —— 报错落在毫无关系的下一个用例上,所以前两轮都误判成「harness
读超时余量不够」。修法是给 harness 一个 `vpnLinkHandlers` WaitGroup,派生走 `goHandleVPNLink`,
并在 **demux 收尾里**先等 handler 退干净:顺序是硬要求,handler 退出要走 `cleanupConnection`,而那一步
要往 `registerTunReadChan` 投递并等确认 —— demux 先停的话 handler 永远卡在清理里。修完之后这组用例
`-race -count=2` 从 693s 降到 66s(此前大量时间就耗在那些卡死的 handler 上),全包 `-race` 零竞态。

### 第 43 轮:熵源故障的拒登面、宣告方下线、端口跳跃回滚

`pow.go` 6 → 1、`server.go` 478 → 465、`hysteria.go` 19 → 16、`egress_select.go` 21 → 20、
`loopback_smux.go` 7 → 6,包 91.4% → 91.7%(未覆盖 588 条),变异 22/22 全抓。

**熵源坏掉时,拒绝比放行安全得多,而两者都不报错。** 这一轮把登录握手上三条熵源分支全钉住了:出题失败
必须回 500 并断开(继续走下去,客户端拿到的是一道 `challenge_id`/`salt` 全零的题:所有人算同一道题,

放行的后果不是"少一个 ID",而是所有这类会话都以 `""` 为键挤在 `connIDMap` 的同一格里后来顶掉先来的,

(`powRandRead`、`util.IDRandRead`),与既有的 `takeoverSecretRandRead` / `hy2TokenRandRead` 同款。

反方向也钉了一条:**题写不出去(客户端半途走了)不许给这个 IP 记 PoW 失败** —— 记了的话下一次真正的

同出口的所有人跟着变难。难度本身也必须夹在 `[powMinDifficulty, powMaxDifficulty]`:它是**写进链路帧
给客户端算**的,越上界 → 客户端算到超时(现象是全站登不进来),越下界 → 一次就过(防护形同未做)。

重算,宣告方自己下线不重算 → 已连着的请求方停在旧的 `online=true`:UI 说这条网段能走,数据面(判据是
当前宣告集)照旧丢包,两侧都"正常"。反方向同样要钉:门控去掉的话每个普通客户端断线都要全站重播一次。

**hy2 的端口跳跃规则装上之后启动失败,规则必须撤掉。** 已有用例只钉了「失败时把 UDP 端口还回去」,而
端口跳跃是一组 PREROUTING REDIRECT:进程退出后机器上留着一段「REDIRECT 到没人监听的端口」,那段端口
的入包被内核吞掉而 nanotun 根本没起来 —— 下次启动的幂等 sweep 会清掉它,但那可能是几小时之后,期间
只表现为「换端口就连不上」。装不上时也一样要先把已绑的 UDP 端口还回去,否则 systemd 拉起的新实例撞上
`address already in use`,排查方向被带到「端口被谁占了」,而真正的原因是缺 `CAP_NET_ADMIN`。

三条变异逃逸,原因都值得记,而且都是同一类:**断言的观测点没落在被测那道闸上。**

- 写题失败那条:记账发生在写失败之后,而我查 IP 失败计数时 handler 还没跑到那儿 —— 不管记不记都还没
  发生。改成等 handler 退出再断言。
- `challenge_id` 熵源那条:我让「第 n 次起全都失败」,于是 n=1 时 salt 也失败,错误是 **salt 那道检查**
  报出来的,`challenge_id` 自己那道在不在根本看不出来。改成只让第 n 次失败。
- 「关机中不许死等 demux 回执」那条:我一开始就把 ctx 取消了,于是**投递**那段的 ctx 分支先短路返回,
  等回执那道闸压根没被跑到。改成先让投递成功(一个只收不答的消费者),之后才拉关机信号。

这一轮还顺手修掉两处测试自身的毛病:一是我的观测对端用了 `fakeLinkConn`(裸切片),而重播是在别的
goroutine 里写的,边写边读被 `-race` 抓住 —— 换成带锁的观测 conn;二是 `freePort`/`pickFreeUDPPort`
的「先绑再关、把号交给被测代码稍后重绑」在 `-race` 下撞过一次 `bind: address already in use`
(`TestPortForwardReload_KeepsListenersWhenTheDBIsUnreadable`),因为 `:0` 拿到的号落在临时端口区间,
中间窗口里同进程的任何外发 socket 都可能被分到它。改成在临时端口区间之外随机挑并确认当下能绑。

- **`go build` 需要模块缓存，而目标机的出站可能绕着 VPN 走。** 主机 A 的默认路由在
  `nanotun0` 上（它拿 C 当出口），从它下载 Go 发行包只有 ~110 KB/s。临时
  `systemctl stop` 掉客户端会话、让流量走自己的 WAN，`go mod download` 从 20 分钟
  变成 37 秒。注意 e2e 的客户端是 `systemd-run` 建的**临时 unit**，停掉即消失，
  不能用 `systemctl start` 拉回来 —— 交给阶段 00 自己重建。
- **子进程冒烟测试的超时预算别把编译算进去。** `runWebBinary` / `runAdminBinary`
  原本先 `context.WithTimeout(60s)` 再调 `buildXxxBinary()`，于是那次**整轮只做一次**
  的编译占用了「跑一次二进制」的预算。开了 `-cover` 要插桩整个 module，在 1 核机器上
  编一次将近 3 分钟，第一条子测试就以 `context deadline exceeded` 假失败（本轮实际
  撞上了，`nanotun-admin` 因此 rc=1）。改成先编、再开始计时。

跑全量回归时注意 `-race` 下 `cmd/nanotun-web` 要 **12 分钟**（子进程编译 + 探测等待），
超过 `go test` 默认的 10 分钟 timeout。用 `go test ./... -race -timeout 25m`，
否则会看到一个纯粹由 timeout 造成的假失败。

只有 `cmd/nanotund` 两边差得明显：macOS 上 `*_linux.go` 根本不参与编译，那 700 多条
语句既不进分子也不进分母。**报数要报 Linux 的那一列**，macOS 的数偏乐观。

那些 Linux-only 的空白基本都被 e2e 接住了（合并后 `cmd/nanotund` 到 86.6%）：

| 文件 | 单测 | 说明 |
|---|---:|---|
| `network_setup_linux.go` | 大部分 0% | 启动期 iptables / sysctl 编排，e2e 每次起服务都走 |
| `iptables_sweep_linux.go` | 0% | 启动 sweep，阶段 70 专门验它 |
| `sdnotify_linux.go` | 0% | 只在 systemd 下有意义 |
| `exit_guard_linux.go` | 0% | 出口私网守卫，需要真 WAN 网卡 |

为可测性动过的生产代码（都是薄壳/接缝，不改行为）：`cmd/nanotund/port_forward.go`
的 `pfExec`（`ip route` / `iptables` 收进一个变量）、`cmd/nanotun-web/main.go` 的
`sessionGCInterval`（原本硬编码 10 分钟，测不到清理体）、`auth` 侧的 `ResetForTest`。

## 采集脚本

`scripts/coverage/` 下三个脚本把上面的流程固化了：

| 脚本 | 在哪跑 | 干什么 |
|---|---|---|
| `run-linux-unit.sh` | Linux 机 | 逐包跑交叉编译好的测试二进制，拼出 `unit-linux.cov`；顺带把子进程插桩计数转成 `subproc.cov`，两者合成 `unit-side.cov`（合并时要用的是它） |
| `deploy-instrumented.sh` | SRV | 换插桩二进制 + 接好 `GOCOVERDIR` + admin wrapper |
| `restore-plain.sh` | SRV | 上一条的逆操作，采集完务必执行 |
| `merge-coverage.py` | 本机 | 合并两侧，出四象限表和精确空白清单 |
