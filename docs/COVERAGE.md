# 覆盖率怎么量

这套系统有两层测试，量的是完全不同的东西，任何单独一个数字都会误导人：

- **进程内单测**（`go test -cover`）：只统计单测进程里执行到的语句。
- **三机 e2e**（`scripts/e2e/`）：跑的是编译好的真二进制，跨进程、跨机器。它执行的
  代码在普通覆盖率剖面里**一个字节都不会记**，因为生产二进制没有插桩。

所以「`cmd/nanotund` 单测覆盖 59.3%」的正确读法是「40.7% 的语句没有被单测覆盖」，
而不是「40.7% 从来没人验证过」。出口选择、ACL 快照、子网路由这些被 e2e 反复压过的
路径全在那 40.7% 里。反过来，e2e 也扫不到报文畸形、非 INET class、上游反投毒这类
分支——真实流量里几乎不出现，却正是攻击面所在。

要看清全貌，得把两笔账合起来。

## 合并账怎么出

### 一、单测这一侧（要在 Linux 上跑）

macOS 上跑单测会漏掉所有 `*_linux.go`——那些文件在 darwin 上根本不参与编译，
既不进分子也不进分母，得出的百分比虚高。交叉编译出测试二进制丢到 Linux 机器上跑：

```bash
# 本机交叉编译
mkdir -p /tmp/lt
for p in $(go list ./...); do
  GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
    go test -c -cover -covermode=set -o /tmp/lt/$(basename $p).test $p
done

# 传到 Linux 机器,连同源码树(有测试读相对路径文件,CWD 必须是各自的包目录)
rsync -az --exclude=.git --exclude=dist ./ root@<linux>:/root/nttest/src/
rsync -az /tmp/lt/ root@<linux>:/root/nttest/bin/

# 逐包跑,CWD = 包目录
cd /root/nttest/src/cmd/nanotund && /root/nttest/bin/nanotund.test \
  -test.count=1 -test.timeout=40m -test.coverprofile=/root/nttest/cov/nanotund.cov
```

各包的 `.cov` 拼成一份（保留一行 `mode:` 头即可）。

### 二、e2e 这一侧（插桩二进制）

用 `go build -cover` 编出带插桩的三个二进制，部署上去跑完整 e2e，进程退出时会把
计数写进 `GOCOVERDIR`：

```bash
go build -cover -covermode=atomic -coverpkg=github.com/nanotun/server/... \
  -o /tmp/cov-bin/nanotund ./cmd/nanotund      # nanotun-web / nanotun-admin 同理
```

部署时三件事：

1. 两个 systemd unit 加 drop-in `Environment=GOCOVERDIR=<目录>`；
2. `nanotun-admin` 是 CLI，e2e 通过 ssh 直接调，用一层 wrapper 脚本注入 `GOCOVERDIR`
   （放 `/usr/local/bin/nanotun-admin`，真二进制改名放旁边）；
3. 跑完 `systemctl stop` 让进程正常退出刷盘，再把 `GOCOVERDIR` 收回来。

```bash
go tool covdata textfmt -i=<收回的目录> -o=e2e.cov
```

### 三、合并

```bash
scripts/coverage/merge-coverage.py unit-linux.cov e2e.cov coverage-gaps.txt
```

输出按包分「两边都覆盖 / 仅单测 / 仅 e2e / 都没有」四类。**只有「都没有」那一列
才是真正该补的空白**，`coverage-gaps.txt` 里是精确到语句块的完整清单。

## 四个坑（都踩过）

**`GOCOVERDIR` 不能放 `/root`。** `nanotun.service` 和 `nanotun-web.service` 都开着
`ProtectHome=yes`，`/root` 在它们的 mount namespace 里根本不存在，覆盖数据被静默拒写，
日志里只留一行 `coverage meta-data emit failed: ... no such file or directory`。
必须放在 unit 的 `ReadWritePaths` 覆盖的路径下，例如 `/var/lib/nanotun/cov`。
第一次采集就是这么白跑了两轮 e2e 才发现。

**阶段 70 的 `kill -9` 会吞掉计数器。** 插桩数据是进程正常退出时才落盘的，SIGKILL
直接丢。若 00–70 一口气跑完，`nanotund` 在阶段 0–6 攒的覆盖会连同那条命一起没掉。
得拆成两次服务生命周期：先跑 00–60 → `systemctl stop` 刷盘归档 → 重启 → 单跑 70 →
再 stop 刷盘。两批数据放同一目录，`covdata` 会自动合并。

**改了源码，旧剖面就作废。** 合并是按 `文件:起止行.列` 匹配语句块的。哪怕只是在
文件中间插入一个函数，其后所有行号位移，那个文件的 key 全部对不上，合并结果会把它
整片误算成「仅单侧覆盖」。改完代码要两边重新采集，别拿旧剖面凑。校验很简单：两份
`.cov` 的行数应当完全相同（07-31 重采时两边都是 12039）。

**拼剖面的输出别落在 `*.cov` 的通配范围里。** `{ for f in $COV/*.cov; do tail -n +2
$f; done; } > $COV/unit-linux.cov` 看着没问题，实际上输出文件自己也匹配那个通配，
`tail` 读自己写自己，几分钟就把 23G 根分区写满了。更阴的是 `rm` 掉之后 `df` 还是
100% —— 有个 `sftp-server` 还开着那个已删除的句柄，`du` 只算出 7G 而 `df` 报 23G，
得 `lsof | grep deleted` 找出来杀掉才回收。输出放到 `$COV` 外面就没这事。

## 补空白的顺序

按「都没有」的条数排，但别只看数字——`main` 那 96 条是进程启动编排，写单测的性价比
远低于同样条数的 ACL 判决。挑的时候看这三条：

1. **判错了会静默出错吗**（ACL、出口选择、地址校验这类，判错不崩溃，只是悄悄放行或
   悄悄黑洞）优先；
2. **是不是 e2e 结构上够不着的**（畸形输入、并发、平台分支）；
3. **要不要为了可测性动生产代码**——需要动的，照 `health.go` 的 `isLoopbackHost`、
   `network_rules.go` 的路数把判定抽成纯函数，`FatalExit` / IO 留在薄壳里。

补完必须做变异验证：把被测逻辑定点改坏，确认测试真的会红。只跑一遍看行数变亮不算数
——`listen_addr` 那个校验漏洞就是变异逃逸暴露出来的，测试照过，一查才发现那个分支
从来没被自己的用例走到过。

第 14/15 轮把 `store` 从 79.8% 推到 95.4%(未覆盖 86 / 1879 条)。剩下的基本进不去:驱动层的
`LastInsertId()` / `Commit()` / `RowsAffected()` 失败、`listMigrations` 对 embed FS 的防御分支
(文件名非法 / 版本号重复 —— 编译期就固定了)、以及 `ProbeServerDialHost` 需要真 DNS + ICMP 回包
的那几条。要再动就得引一个注入故障的 `database/sql/driver` 包装,性价比不如去啃 `cmd/*`。

这两轮里真正抓到东西的用例(不是补行数的):

- **事务半途失败必须整体回滚**。删设备 / 删用户时,清孤儿 `port_forwards` 那步失败却照样把行删掉,
  剩下的转发会被下一个注册同 UUID 的账号静默继承——外网入口换了主人,两边界面都看不出来。
  `SetDeviceFixedVIP` 同理:`--force` 释放对方 lease 失败却把地址钉上去,就是双占。
- **`RotateUserPSKAndEnsureCredential` 的原子性**。补 `credential_id` 失败时 `psk_hash` 必须跟着回滚,
  否则旧 PSK 已作废、新 QR 又生成不出来,用户被锁在门外而 admin 只看到一句报错。
- **迁移出错时版本号不许前进**,而且「版本号读不出来」绝不能当成 0 ——当成 0 会把非幂等的历史迁移
  (`ALTER TABLE ADD COLUMN`)重放一遍,比启动失败严重得多。构造手法是把 `schema_version` 往回拨一格
  再跑 `Migrate`。
- **存量 VIP 归一的跨表撞车**:`leases.vip_v6` 归一后撞上别的设备已钉的 `devices.fixed_vip_v6` 时要跳过 +
  把完成标记留在 `'0'`,下次启动重跑。落 `'1'` 就等于永久 no-op,残留的非规范写法再不会被处理。
- **`SettingsSet` 的纵深校验**。`mesh_enabled` 拼成 `flase` 时读路径兜底是 **true**(fail-open),
  「想关 mesh」会静默保持互通;限速键写歪则被静默当 0(= 不限)。这些校验不能只留在 CLI 那一层。
- **列表读到坏行要整体报错**,不能少一行。管理员看不到某个账号 / 某条已批准的网段,就以为它不存在,
  而它照样在生效。

新增的两个手法:

- `abortOnWhen(table, op, when)` —— 带 `WHEN` 的 `RAISE(ABORT)` 触发器。用来分辨「同一事务里第几步失败」,
  比如 `SetRateDefaults` 三个键各失败一次,验的都是同一个不变量:三个键同生同死,不留撕裂态。
- 往 INTEGER 列写 **REAL**(而不是 TEXT)。TEXT 在 SQLite 里排在所有数字之后,`WHERE at >= ? AND at < ?`
  会把坏行直接滤掉,`Scan` 根本走不到;写 `1000.5` 则留在数值域内,过得了 WHERE、卡在 `Scan` ——
  这才是 `QueryAudit` 那条扫描错误分支的构造方式。

变异逃逸这次同样是**用例没隔离干净**:拿不到迁移锁、坏 `device_id`、读不出版本号这三条,报的错
都来自另一道闸(SQLite 自己的写失败 / 外键 / 后续语句),把断言收紧到「报错原因必须是这一道」之后
全部抓住。剩一条 `SetRateDefaults` 第一个键失败时提前 commit 是等价变异——那时还没写任何东西;
换成第二、第三个键失败就立刻被抓。

第 13 轮引入了两个可复用的手段,后面几轮都在用:

- **`Options{ReadOnly:true}` / 已 Close 的 store** 两级故障注入。只读库让第一条写语句失败,
  已关库让 `BeginTx` 就失败 —— 两者覆盖的错误分支不同。要验的不变量很朴素:库挂了或只读时
  **没有任何一个 DAL 函数报成功**,也不能把存储故障归一成 `ErrNotFound`(那会让 handler 显示
  「账号不存在」而不是「存储不可写」,排查方向全错)。
- **`RAISE(ABORT)` 触发器**做精准故障注入(`abortOn` 助手)。前两种手段都只能让**第一条**语句
  失败,而最该验的是「事务里第二条失败要整体回滚」:改密的 UPDATE 成了但撤销旧会话的 DELETE
  失败,不回滚就是「密码已改、旧 cookie 仍有效」—— 改密根本没把攻击者踢下线。在 `web_sessions`
  / `web_admin_recovery_codes` 上装 BEFORE DELETE/INSERT 触发器就能精确制造这种失败。
  注意 BEFORE 触发器在**匹配 0 行时不触发**,构造时要确认目标行真的存在。

另外用「往 INTEGER 列写 TEXT」(SQLite 非 STRICT 表允许)模拟手工改库 / 迁移写坏。这类用例
的价值不在覆盖率:`failed_logins` 扫不出来若被静默当成 0,等于把已锁定的账号自动解锁。

第 13 轮的变异逃逸值得记一笔,四条里三条是**用例没隔离干净**——报的错来自另一道闸:
`CreateFirstWebAdmin` 的空用户名撞的是 `ErrSetupClosed`(库里已有 admin)、
`SetWebAdminRoleEnsuringAdmin` 的非法 role 撞的是 `ErrLastAdmin`(只有一个 admin)、
`EnableWebAdminTOTP` 的空恢复码撞的是 CAS 的 `ErrNotFound`(没设过 secret)。
三条都拆成独立用例、先把「别的闸不会响」布置好再断言。**光看行数变亮完全发现不了这类问题。**
唯一的等价变异是 `CreateWebSession` 的 `AdminID<=0`:外键 `REFERENCES web_admins(id)` 兜住了
同样的不变量,DAL 那道判断的价值只是给出一条清楚的错误。

剩下 12 条全是驱动层错误(`Commit()` / `PrepareContext()` / `LastInsertId()` / `RowsAffected()`
失败),用 SQLite 自身的手段构造不出来,要一个会注入故障的 `database/sql/driver` 包装。全包这类
包装只有 7 处,而 `if err := tx.Commit(); err != nil { return err }` 判错的风险极低 —— 性价比低
于去啃别的文件里的语义分支,暂时留着。

第 4 轮的等价变异记一下，省得下次重打一遍：`t < 20` 被 `ihl >= 20 && ihl <= t`
蕴含；`startWSSDataPlaneKeepalive` 自己也挡 `interval <= 0` 和 `missThreshold <= 0`，
调用侧那两处判断拆掉也没有可观察差异。`runLinkTunnel` 门口的 `ValidIPPacket` 与 ACL
对「解不出 tuple」的 fail-closed 互为兜底，拆掉任意一层畸形包都还是进不了 TUN——
门本身的边界钉在 `util` 那侧的用例里。

`runLinkTunnel` 还剩 4 条未覆盖，都是 `interceptExitDNSResponseIfPending` /
`forwardPacketToSubnetRoute` / `forwardPacketToExitNode` / `serverSelfEgressV6FastFail`
的 true 分支，这四个函数各有专门用例，从 readLoop 再走一遍是重复劳动。

### 第 22 轮:`cmd/nanotun-admin`(80.5% → 96.7%)

CLI 的坏法与 handler 不同:它没有 HTTP 状态码,只有**退出码 + 两条流**。所以这一轮的
断言几乎都围绕三件事:

- **退出码不许随环境漂移**。`kick user`(参数敲错)在 server 可达与不可达时都必须是 2。
  此前有几条命令先拨 control socket 再校验参数,于是「用法错」被报成「连不上」(exit 1),
  脚本没法判断。
- **落库 ≠ 生效**。ACL / 限速 / mesh 这些键都缓存在 server 内存快照里,不通知就只是改了行 DB。
  这一轮在 `acl add --json` 上抓到一个真缺陷:`--json` 分支直接 return,把通知 server、
  reload 提示、缺回程告警一并跳过 —— 脚本化加规则拿到一条「已创建」的 JSON,而数据面
  的 ACL 快照从没刷过,规则静默不生效;同一文件里的 `acl del` 反倒一直通知,两条路口径相反。
  修法是把通知/提示移出分叉(它们全走 stderr,不污染 `--json` 的机器可读 stdout)。
- **确定性的输出失败必须发生在落库之前**。`credentials --rotate-psk` 一旦落库,旧 PSK 立刻作废;
  之后才发现 `--output` 的目录不存在 = PSK 已换、明文从未交付,用户当场断连而运维手里也没有新密钥。
  `preflightCredentialsOutput` 的每一条判定都对着这个不变量。

故障注入这一侧新加了两个手法:

- **只挡一个 key 的写**(`abortSettingWrite`)。整表挡 `app_settings` 的 INSERT 会先把
  migration 挡掉 —— 命令在到达被测那行之前就 exit 1,用例照样"通过",但验的其实是
  migration 失败。这正是 `init` 的 `setup_completed` 那条变异逃逸的原因。
- **放宽 NOT NULL 后塞 NULL**(`relaxAppSettingsValue`)。`SettingsGet` 往 `string` 扫会报错,
  这是模拟「真·读故障」的唯一办法 —— 与「这个 key 没设过」(`ok=false`,不是 error)是两回事。
  `route approve` 读不出 mesh 网段时必须**拒**(交叠检查是 fail-closed)就是靠它验的。

为可测性动的生产代码只有一处接缝:`cmd_setting.go` 把 DNS 与 ICMP 探测收进
`probeLookupIPAddr` / `probeDialHost` 两个包级变量。`probe-dial-host` 的价值全在
**结果分类**(DNS 硬错 / 无记录 / 解到不可拨的特殊地址 / ICMP 软失败)上,而真去查网络
会让用例随宿主网络红绿漂移。

`main()` 本体(读 `os.Args`、`os.Exit`)照 `nanotun-web` 的路数用子进程冒烟测试覆盖:
设了 `NANOTUN_SUBPROC_COVERDIR` 就用 `go build -cover` 编,计数落进 `GOCOVERDIR` 并进合并账。

剩下的 98 条基本进不去,分三类:`crypto/rand` / `json.Marshal` 一个固定结构失败这类
「机器已经坏了」的分支;`copyFileAtomic` 的 `Chmod`/`Sync`/`Close` 失败(要一个写满的
文件系统);以及**代码里就走不到的空分支** —— `confirm()` 永远返回 `nil` error、
`openProfileOutput()` 的 error 恒为 `nil`,它们的 `if err != nil` 判断有六七处调用点,
真正该做的是把这两个函数的签名收掉,不是给它们编测试。

唯一一条抓不住的变异是 `writeFileTight` 里 `os.Link` 换成 `os.Rename`:两者只在
「Lstat 与落盘之间被抢建」这个 race 窗口里有区别,没有可移植的确定性测法。它靠注释与 review 守。

第 5 轮为了可测性动了生产代码：`jump_host_firewall.go` 里所有 `exec.Command` 与
`runtime.GOOS` 判断收进 `jumpFWExec` / `jumpFWOnLinux` 两个变量。这段编排只在生产的
Linux 上执行，开发机没有真 iptables、三机 e2e 也没开这个开关，所以「装出来的规则集
长什么样」此前从没被验证过——而它判错既不报错也看不出来。等价变异同样记一下：
`net.IP.String()` 自己就会把 v4-mapped 归一，所以 `To4().String()` 换成 `String()`
没有可观察差异；`teardownImpl` 的非 Linux 判断被 `installed` 标志盖住（非 Linux 上
`installed` 恒为 false）；`Teardown` 的 `sync.Once` 同理。

### 第 22 轮的修复在三机上复核过（2026-07-28）

`acl add/deny --json` 漏通知是单测抓到的，但它的**后果**只在跨进程这一层可见 —— 单测能证明

两条路口径相反,与代码读出来的结论一致。换上 `c8751d4` 的二进制后 stderr 有提示、stdout

随后跑了全量:132 项断言全过,退出码 0,6.5 分钟。这一轮改的产品代码除 `cmd_acl.go` 外都是

### 第 23 轮:`cmd/nanotund` 的「静默出错」那一档

按「补空白的顺序」第 1 条挑的:ACL 快照重建、出口裁决、出口列表。这三处判错都不报错、
不掉线,只表现成用户那头「网怪怪的」，所以优先级排在条数多得多的 `main` 启动编排前面。

真正值得记的是**断言该断在哪**:

- **「读不出设置」与「这个 key 没设过」必须分开。** `reloadACLSnapshotFromStore` 里两者
  的正确行为恰好相反 —— 前者要返回 err 且**原样保留旧快照**,后者落到内置默认 allow。
  只断 `err != nil` 是不够的:一个「先把快照换成空规则 + allow、再返回 err」的实现同样
  满足它,而那正是最坏的结果(default-deny 被一次 DB 抖动翻成全放行,且无告警)。用例断的
  是**快照指针不变** + 旧的 deny 规则仍在拦。
- **fail-closed 兜底只能由手抠 DB 触发。** `acl_default_action` 写路径自己就拒非法值,
  所以用例得直写 SQL 才进得去那条分支 —— 顺手把「写路径确实在拦」也钉成断言,这样两层
  防御各自的责任都写在测试里。
- **「查不动」不是「未批准」。** `resolveApprovedExitDeviceID` /
  `deviceHasApprovedExitRoute` 都返回 `(值, ok)`,ok=false 意味着无法判定。混为一谈的话,
  一次 DB 抖动就会撤销仍然有效的出口绑定,或把用户想避开的 server 自出口静默给他。
  三种入口(无 store、deviceID=0、DB 报错)分别钉。

两次变异逃逸都出在同一种写法上,值得当模板记住:**用例里让同一个对象同时满足正反两边,
去掉判定后结果不变**。第一次是「同一台设备既宣告了 LAN 段又宣告了出口」——去掉
`IsExitDefaultRoute` 过滤照样解析到同一个 device;改成「只批了 192.168 段的设备绝不能
被解析成出口」才抓得住。`buildExitsList` 第 ④ 步那条一模一样。

`isRunningExitConn` 是这一轮唯一动的产品代码:`buildExitsList` 的 ① 快照与 ③ 复核本来
手抄了两遍同一判据,而 ① 还多查一个 `deviceID != 0`,属于随时会漂移的重复。抽成一处之后
判据本身可以直测。

还剩一条变异逃逸,是结构性的:③ 复核守的是「② 查 DB 期间会话状态翻转」那个窗口,
单线程单测开不出来 —— 要么给生产代码加一个纯为开窗存在的钩子。判据抽出来后至少
「判据认不认这几种失效状态」钉住了,调用时序靠 e2e 里出口接管/重登那几条。

后半轮接着补 `route_advertise.go`(49 → 17)与 MagicDNS 一家四个文件
(`magic_dns.go` 93 → 42、`_exit.go` 36 → 19、`_cache.go` 30 → 12、`_intercept.go` 15 → 7),
包覆盖 80.3% → 81.6%。这半轮的教训集中在**「用例形状对不对」**上,变异测试基本全是替我
指出这一点:

- **重名裁决必须绕开去重那道口子才测得到。** `lookupMagicHost` 对同名设备取 device_id
  最小的那台,但 `UpsertDevice` 会给撞名的自动追 `-1`,走它根本造不出两台同名。得直写
  SQL —— 而这恰好也是这段代码真正服务的场景:唯一性强制生效**之前**登记的存量重名。
  断言还要跑多次,因为「取遍历顺序第一个」的实现会随两台机器 last_seen 的更新来回漂移。
- **「返回了 cleanup」证不了「没起 listener」。** `startMagicDNS` 的六条 no-op 路径,
  只断 cleanup 非 nil 的话,一个「非法 listen_addr 照样绑」的实现也能过 —— 而
  `addr.IP=nil` 会被 `ListenUDP` 当成 `0.0.0.0`,把本该只在 TUN 上听的内网 DNS 摆到
  所有网卡,包括公网口。改成调完立刻去 bind 那个端口:绑得上才说明真的没起。
  「未启用」那条还得把端口显式写成探测端口 —— 留空会走默认 53,而「绑 53 需要 root」
  会让「其实起了 listener」的实现**碰巧**也失败,用例就空过了。
- **验「取最小」的用例里,几个值必须不相等。** `parseExitDNSResult` /
  `parseRawDNSMeta` 都取答复区最小 TTL,原来的用例每条答复给同一个 TTL,于是取最大的
  实现结果一样。改成 300/45/90 三条、最小值刻意放中间,顺带排除「取最后一条」。
- **越界检查要在**足够长**的包上验。** `dnsQuestionEnd` 拒绝 question 段里的压缩指针;
  短包里去掉这道检查,`0xc0` 会被当成长度 192、一步跨过包尾,照样落到「越界」那条
  `return false` —— 两种实现结果相同。得给一个 220 字节的包、让指针跳到的位置恰好是
  0 字节,缺检查的实现才会返回一个在界内的**假**偏移。

两条判定为等价、不再追的:`tryResolvePublicViaExit` 里对 fail-closed 哨兵的显式判定
(去掉后 `lookupRunningExitConnByDevice(-1)` 也查不到,结果相同 —— 它是可读性分支,
不是唯一防线),以及拦截路径上关联端口的区间预筛(waiter 只可能登记在区间内,真正的
门是那次 map 查找)。

`route_advertise` 那半轮还暴露了一个**测试自身**的 data race:撤回出口会
fire-and-forget 一条 `broadcastExitsList`,它读 `gatewayInstance`,而子测试的
`t.Cleanup` 同时把值改回去。修法不是加 sleep,而是挂一条只收广播的 exit_allowed 会话、
等那一帧到达 —— 既建立了 happens-before,又顺带把「撤回后必须立刻重算并推送」钉成
断言(否则已撤回的出口要留在别人的下拉里直到它下线)。

### 第 24 轮:两个入站监听器(REALITY / hy2)

原以为这两块「要真握手所以测不了」,实际只有握手本身测不了 —— 外面的启动编排、accept
循环、环回桥接全都能在进程内跑通。`reality_listen.go` 64 → 6、`hysteria.go` 44 → 19,
包覆盖 81.6% → 82.8%,变异 32 项全抓。

能测到这个程度靠两件事。一是既有测试里已经有一份 **WS + smux 回声服务端**的脚手架
(`loopback_smux_test.go`),把它抽成 helper 之后,「桥接到环回数据面」这条主路就能整条
跑起来 —— 而这条路上此前一条断言都没有,失败面倒是钉得挺全。二是把埋在闭包里的
accept 循环抽成 `runRealityAcceptLoop(ln, handle)`,注入假 listener 才能造出 EMFILE。

这一轮钉住的、错了又完全不报错的性质:

- **可恢复的 Accept 错误不能当致命。** fd 耗尽(EMFILE)、客户端在 backlog 里就 RST
  (ECONNABORTED)过几秒就好;当成致命退出循环,整个 REALITY 入口对所有客户端**永久**
  消失 —— 进程还活着、别的入口还在服务,监控大概也不会响。唯一的致命错误是自己
  `Close` 后的 `net.ErrClosed`。
- **退避要归零,而且不能是 0。** 返回 0 会让持续报错变成 hot-spin 吃满 CPU;成功一次
  之后不归零,则一段早已过去的抖动会长期给每次接入加上封顶延迟。后者的断言得量
  「出错到下次 Accept」的实际间隔 —— 只看「循环还活着」是抓不住的。
- **上报的端口必须是真在听的那个。** `listen_addr` 用 `:0` 时内核分配端口,这个值经
  node_login 发给客户端。报错了的现象是「服务一切正常但没人连得上」,服务端日志里
  什么错都没有。断言方式是拿上报的端口去 bind,占不上才算对。
- **失败路径必须把已绑的端口还回去。** hy2 启动的后半段(建 server config / NewServer)
  失败时若不关 packetConn,后续重试会看到「端口已被占用」的假象,排查方向直接被带偏。
- **真实客户端地址必须透传到环回。** hy2 拿不到客户端地址(hysteria 的
  `Outbound.TCP(reqAddr)` 不透出),靠 relay 在 RequestHook→EventLogger→Outbound 三步间
  用一次性 token 传递。传不到不报错,只是**所有** hy2 客户端塌进 127.0.0.1 这一个桶:
  `loginIPLimiter` / `powIPLimiter` 都按 remoteAddr 的 host 分桶,单个滥用者就能把全部
  hy2 用户一起限死,而客户端 `transport=auto` 优先选的正是 hy2。
- **reqAddr 绝不能当 dial 目标。** 这是「hy2 不得退化成任意 TCP 开放代理」的硬约束。
  既有用例只验了「pool 为 nil 时报错」—— 那条路上 reqAddr 压根没机会被使用。新用例在
  reqAddr 里放一个**活着**的诱饵监听:一旦实现拿它去拨,诱饵就会收到连接。
- **握手 deadline 进桥接后必须清掉。** `realityAcceptDeadlineListener` 给每条 conn 套了
  15s,不清的话业务数据一旦有 15s 空闲就被砍 —— 表现成「连上能用一会儿然后莫名断线」。
  断言方式是进桥接前故意套一个 300ms 的短 deadline,再等过它才收发。

两条形状教训(又是变异测试指出来的):**假 listener 报错时也返回 nil conn,那么「返回 c」
与「返回 nil」就无从区分**,得让剧本同时给出 conn 和错误;以及**验「成功后重置」的剧本,
成功之后不能紧接就是关机** —— 那条路径上退避有没有归零看不出来。

剩下的 25 条(reality 6 / hysteria 19)分三类:握手后才走到的桥接调用(归 e2e)、被
`Validate` 挡在前面的防御分支、以及需要 Linux + root 的端口跳跃 iptables 路径。还有两处
是「OpenStream 成功之后、写 PROXY 头之前断链」那个瞬间窗口,单测开不出来。

### 第 25 轮:hy2 与 REALITY 共用的那条环回承载

`loopback_smux.go` 29 → 9,包 82.8% → 83.2%,变异 17 项抓 16(第 17 条等价:拨号失败时
`sess` 恒为 nil,写不写进池没有可观测差异)。这一轮翻出两个真缺陷,都属于「功能完全正常
直到某个配置组合被用上」那类。

**HIGH:启用 `[smux]` + hy2/REALITY 时,所有直连原生客户端都登不进来。**
识别一条入站连接是「环回 smux 承载」还是「直连链路帧」靠 4 字节魔法前缀 `VPN1`,原实现
直接 `br.Peek(4)`。但直连客户端的首帧是 `PoWChallengeReq`,协议明文规定 body 必须为空,
线上恒为 **3 字节**(2 长度 + 1 类型)。于是服务端等第 4 个字节、客户端等 `PoWChallenge`
回复,双方干等到超时 —— 而 `[smux]` 就在发布的 `config.toml` 里,只要同时配了 hy2 或
REALITY 就会触发。三机 e2e 从来没配过这两个入站,所以这个组合一直没被跑到。改成「先看
一个字节,只有它等于 `'V'` 才允许要求看满 4 字节」:链路帧的首字节是长度高位,只有帧长
≥0x5600 时才可能撞上 `'V'`,而那时后续字节早已到齐,不会多等。顺带给识别期加了读超时
(未认证对端一个字节都不发就白占一个 goroutine 和一块读缓冲),并在识别完立刻撤掉 ——
不撤的话每条承载最多活 30s,之后所有多路复用连接一起断。

**MED:环回承载闪断后,新流会连续失败长达半分钟。**
两个事实叠在一起:① smux 只在 keepalive 超时(`DefaultConfig` 30s)后才把会话标记为死,
在那之前 `IsClosed()` 恒 false;② 断线那一刻 `OpenStream` 往往仍然成功(SYN 由 shaper
异步写出),错误要到第一次读写才浮出来。原实现只看 `IsClosed()`,于是这半分钟里每条新
hy2 / REALITY 流都开在同一具尸体上、全部 broken pipe,而重拨一条环回只要几毫秒。修法是
两道:`OpenStream` 报错即摘掉会话并重建(主路),以及给复用出去的 stream 包一层,把承载级
I/O 错误回报给池(兜住 smux 还没察觉的那个窗口)。代价从「半分钟内全灭」收敛成「撞上断线
的那一条流失败」。

包装层的判据是这一轮最需要小心的地方:`io.EOF` / `io.ErrClosedPipe` / deadline /
`smux.ErrTimeout` 都是 **stream 自己的生命周期**,拿它们拆共享承载的话,每条正常结束的
连接都会把别人的隧道一起带走。同理 `retireSession` 只摘不关 —— 判据可能误判,误判的代价
必须是「多出一条承载」,不能是「掐断在跑的流」。这两条都各自有一条反面用例钉住。

方法上有两处值得记:
- **断言要落在「这条连接被当成了什么」上。** 路由走错时连接一样会断、日志也差不多,所以
  最初写的「会话还活着吗」根本区分不了两条路 —— `handleVPNLink` 有 30s 握手期,走错了也
  能撑住。换成「同一份 `PoWChallengeReq`,回复落在裸连接上还是 stream 里」才把两个方向
  同时钉死,而且顺带覆盖了「Peek 过的字节必须原样交下去」。
- **复用有没有生效,只有数「建了几条承载」才看得见。** 退化成每流一条 WSS 时功能完全正常,
  单测不数上游握手次数就永远发现不了;singleflight 失效同理(环回一慢就是 N×15s 串行放大)。

余下 9 条:识别期与拨号的几处防御返回、`smux.Client` 之前写魔法失败那个瞬间窗口,以及
singleflight 里「等到的会话又刚好失效」这条要靠时序凑的分支。

### 第 26 轮:无鉴权控制面的那道门

`control_socket.go` 40 → 8,包 83.2% → 83.7%,变异 21 项抓 20(剩一条等价,下面说)。这个文件
的全部安全性压在一句前提上:**只有能读这个 unix socket 的本地用户才是管理员**。kick / reload /
rate-refresh 都不做任何鉴权,所以「权限没收紧却照样开门」等于本地提权,而除了一行日志之外没有
任何迹象 —— 这一轮主要就是把那几条 fail-closed 分支钉死。

未覆盖的正是它们:chmod 失败、chmod 报成功但实测权限没落到 0600、复核时 Stat 本身失败。第二条
用真实文件系统构造不出来(只在个别容器 overlay 上出现),给那一次 `Stat` 留了个仅测试替换的接缝;
另外把 chmod + 复核那一段抽成 `enforceControlSocketPerm`,于是「失败时不只是不启动,还要关掉监听
并删掉那个文件」可以直接断言 —— 留着一个 group/other 可访问的 socket 挂在那里等人来连,是这里
最坏的形状。

**覆盖率读出了一处死代码。** kick 原本是两个 switch:前一个给 session / device / user 三种形状各
建一个 picker,后一个再挑受害者。但 session 和 user 在后一个 switch 里走的是 O(1) 索引,它们的
picker 从来没被调用过 —— 那两行恒为 0 才看出来。死掉的匹配逻辑是个陷阱:改 kick 语义的人很可能
只改那两行,而真正生效的是索引那一侧。已合并成一个 switch。

**测「命中」和测「拒绝」是两件事。** 既有用例把参数校验(空 id、未知 kind、user 不存在)覆盖得很
全,却没有一条验证过 `kick session <id>` 真的踢到了那条会话 —— 而这是最常用的管理操作。算错目标
不会报错,只会回 200 加一个好看的 `kicked` 计数。现在三种形状各有一条用例钉住「只踢目标、旁站
会话必须还活着」,外加一条「追不到活会话时必须回报 0」。

限速那两个 helper 的回落方向也补上了断言:读不到当前值时必须回落到调用方给的登录快照,**绝不能
回落到 0** —— 0 在 `effectiveLinkRates` 里表示「这一层不限速」,回落成 0 就是把配额悄悄取消,而
限速看起来「生效了」。

余下 8 条:`Serve` 非正常退出那行日志、新建目录 chmod 失败与随后 Stat 失败这两个 TOCTOU 窗口,
以及 kick 里一条前置守卫(by-user 索引的键就是 `c.userID`,所以「索引里捞出来的 conn 解析不出
uid」当前不可达;留着是为了哪天索引改成按数字 id 存时审计不会把处置记到 user 0 名下)。

**变异工具本身修了两个假绿**,这一轮是被它咬了才发现的:
- 它原先每条变异各自读一遍磁盘、再从内存快照还原。一次还原失手就会连环出错:后一条变异的锚点
  在被改过的文件里找不到,报成「锚点失效」(看起来是清单写错,其实是工具漏了),而它随手拍下的
  「原始内容」已经带着上一条变异,一路传下去 —— 最后真把一条变异留在了工作树里,那是会被当成
  真代码提交掉的。改成一律以开跑那一刻的原始内容为基准施加与还原,并在收尾复核每个文件。
- 构建坏掉时,每条变异都因为「go test 返回非 0」被记成抓住。第一次跑出来的 21/21 就是这么来的,
  底下一条断言都没跑。现在开跑前先 `go build` 一遍,并把「编不过」单独分桶,不计入抓住数。

那条等价变异是 cleanup 里的 `os.Remove(path)`:Go 的 `UnixListener.Close()` 自己就会 unlink
(`SetUnlinkOnClose` 默认开),删不删没有可观测差异。生产代码里原来的注释把因果说成「靠这次
Remove 避免下次 bind 撞 EADDRINUSE」,已改准 —— 它只是为「将来换成从 fd 接管的 listener」留的保险。

### 第 27 轮:把历史上所有变异重跑一遍(审计,不加覆盖)

上一轮修掉工具的两个假绿之后,前面二十几轮的成绩单就都不可信了 —— 尤其是那些被记成「锚点失效」
的条目,当时当作清单写错跳过,实际可能是工具自己漏的。这一轮把历史上所有变异合成一份

那 8 条就是历史上的「锚点失效」的真身。它们的写法都会删掉某个标识符或 import 的最后一处引用,
Go 直接拒绝编译 —— 而旧工具只看 `go test` 的退出码,非 0 即算抓住,于是**编译失败被记成了成绩**。
这 8 条里有 5 条是安全关键的校验(出口回包绑定、4via6 的宣告网段校验、截获路径的网关校验、accept

逃逸的那条是**出口回包的完整绑定**:把「TXID 相符」升级为「Response 置位 + question 相符」的那道
检查,整段拿掉也没有测试变红。第二十轮补这道检查时只单测了 `dnsReplyMatches` 这个判定函数本身,
从没有一条用例把「只有 TXID 对」的应答真的沿投递路径喂进 `resolveExitDNS`。这个缺口的形状值得记:
**判定函数有测试,不等于调用点接上了它。** 现在补的用例走完整路径 —— 注入查询、拿到关联端口、以
正主身份投递一份 question 是另一个域名(以及一份 QR=0 的回显)的应答 —— 断言只能换来 SERVFAIL、
不落缓存、计数自增,并以既有的"相符应答"用例作反面对照。

6 条逃逸里另有 5 条是等价变异或清单自身的问题,已在归档清单里逐条标注原因:

- `CreateWebSession` 的 `admin_id <= 0`:`web_sessions.admin_id` 有外键且每条连接都开
  `foreign_keys`,闸门删掉后 SQLite 照样拒。保留它是 schema 之外的第二道防线。

**还有一条真缺口,是一条自称测了竞态的用例。** `writeFileTight` 在没给 `--force` 时用原子

### 第 28 轮:SIGHUP 与登录前的那道闸门

`reload.go` 30 → 11、`pow.go` 29 → 9,包 83.7% → 84.3%,变异 16 项全抓。

**SIGHUP 这条路上,「回报成功」本身就是故障模式。** 它没有返回值,运维唯一的反馈是日志和
applied/deferred 两个列表 —— 所以把一次失败记成 applied,比崩溃更糟:崩溃会被发现。第二十三轮
在跳板机防火墙这条路上修过两处(一处 HIGH、一处 MED),但两处**都没有回归测试**,覆盖率报告里
那几行一直是空的。这轮先把它们钉住:

- 刷 ipset 失败时不许标成已应用,而且**内存里的旧名单不能跟着改**。旧名单一改,下一次同样的
  SIGHUP 会因为「集合相等」整段跳过 —— 受保护端口敞开着,运维手里是一份「已热更新」的成功
  回报,再 reload 多少次都不会重试,一直维持到重启。用例连做两次同样的 SIGHUP,断言第二次
  仍在重试。
- SIGHUP 必须自己重跑 `ValidateJumpHostFirewall`。它走的 `loadConfig` 只做 `Validate()`,不含
  这条启动期校验;于是把名单改成一堆非法项(误写 CIDR / 主机名 / 拼错)之后 reload,runtime 的
  sanitize 会把它们全丢掉,只剩自动补的 127.0.0.1 —— 真跳板机在受保护端口上被静默挡死。同一份
  配置冷启动会直接 Fatal,热更新却悄悄生效。用例额外断言此时**根本没碰过 ipset**:碰了就意味着
  「只剩 127.0.0.1」已经落到内核,人已经进不来了。

写这两条时踩了个坑值得记:一开始自己写了个「一律返回成功」的假 ipset/iptables,结果测试挂死 ——
生产代码里有「`-C` 查得到就继续 `-D`」的删除循环,假命令永远说"查得到"就转不出来。既有的
`fakeIPT` 早就把这件事模型好了(它维护集合/链/规则的状态,注释里也写明了原因),换回复用它即可;
顺手给它补了个 `failOn` 方法,替掉调用处的匿名结构体字面量。

**PoW 这一侧盯的是七道拒绝理由和它们的顺序。** 少一道就是闸门被绕开,而且悄无声息:不查过期 →
一道题永久有效;不防重放 → 一道题算一次能用无限次;签名不校 → 客户端自己给自己出 4-bit 的题。
顺序同样是安全属性 —— 防重放的登记必须在验算 nonce **之后**,否则拿到别人 cid 的人可以反复提交
垃圾 nonce 把对方的题烧光,闸门本身成了拒绝服务的工具。

入口那道「签名/难度/过期时间为空」的闸门单看结果是冗余的(伪造者过不了后面的 HMAC,同样得
`ErrPoWBadSignature`、同样记 `FailBadSig`),第一遍变异因此逃逸。它唯一不冗余的地方是**顺序**:
缺字段要在解 salt 之前被拦下。补了一条「缺字段 + salt 也不合法」的用例钉住这个顺序 —— 这类
「结果相同、只有顺序不同」的判据,是变异测试最容易暴露、而读代码最容易漏掉的一类。

### 第 29 轮:登录的分档,与子网路由的两类闸门

`auth_login.go` 28 → 3、`subnet_route.go` 28 → 13,包 84.3% → 84.8%,变异 24 项抓 23(1 等价)。

**登录那两张 code→文案 / code→action 的表,看着像文案,实际是运维唯一的抓手。** 文件顶部记着
2026-05-21 那次:安装脚本换了 DB 路径没迁用户,所有客户端登录返回 403,而 audit_logs 里只有一行
扁平的 `action=login.fail`,既不能按子类聚合、又不在 ERROR 级别,等用户感知已经 11 小时。修法是
「每个失败原因一个独立 action,全挂在 `login.fail.` 前缀下」——**修完没有任何断言守着它**,14 个码
里当时只测了 5 个。这轮改成整表驱动,并且不止比对字符串,还钉住三条结构性要求:每个码有自己的
action(复制粘贴漏改会让两类失败在报表里并成一类)、失败一律在 `login.fail` 前缀下而成功一律不在
(否则失败率报表把成功也算成失败)、对外文案里不许出现 SQL / 内部标识。

PSK 校验的失败分档同理,而且坏法是双向的:把「用户不存在」报成 500,运维去查服务器而不查用户表;
反过来把内部错误(库读不动)报成 401「用户名或密钥错误」,用户一直重输密码,而真正的故障——数据库
——没有任何人看见。后一条用改表名造出真实的读失败来钉住。

**子网路由这边是两类闸门,此前一条断言都没有。**

一是**载入时的过滤**:转发表从 DB 里 approved 的行重建,但「approved」不等于「可转发」——批准发生
在过去,而校验规则会变严。第十一轮修的那条 MED(放行公网/宽段 CIDR 等于绕过出口闸和出口 ACL,
confused deputy)至今没有回归测试;它不报错、`route list` 里照样显示 approved,只能靠转发表里没有
它来判断。用直写 DB 绕过归一来复现「历史批准 / 手工 SQL」这条真实路径。同批还钉住:DB 读不动时
保留旧表(清空等于所有内网路由同时黑洞,而原因只是一次 DB 抖动)。

二是**表未加载时的方向**。这几个判据在启动瞬间和 reload 窗口里会读到空表,「不属于」和「暂时不
知道」无法区分,于是每处都得显式选一个方向,而且方向不能选反:投递门控 fail-closed(选反 = 撤销
审批后 FRP 仍能打进 LAN),4via6 反源收窄 fail-open(选反 = 每次 reload 抖一下就断掉一批合法回程)。
两个方向相反、各有各的事故形状,现在各有用例。

两条值得记的返工:`deviceID=0 不该匹配任何网段` 第一遍逃逸,因为表里根本没有零值行,断言等于没测;
在表里塞一条 `device_id=0` 才真正钉住(正常 DB 有外键造不出它,但这个函数收的是任意一张表)。另一条
`0/0 与 ::/0 也收进表` 判定为等价——紧随其后的 `PrefixWithinAdvertisable` 同样会挡掉默认路由,两道
闸重叠,无可观测差异。

### 第 30 轮:出口选择与公网端口的拒绝路径

`egress_select.go` 38 → 29、`port_forward.go` 33 → 18,包 84.8% → 85.2%,变异 15 项抓 12(3 等价)。

**出口选择这条路上,「拒绝」有两种写法,差别是安全性的。** 一种是明确拒绝(回 ack、把绑定置成
fail-closed 哨兵,数据面就地丢包),另一种是静默回落 server 自出口。后者曾经真实存在:用户点名经 C
出网、服务器答「不行」,然后把他的公网流量从 server 自己的公网 IP 送出去 —— 三机实测(2026-07-25)
复现到出网 IP 变成 server 的地址,用户侧唯一线索是客户端一行日志。这轮补的是尚无断言的两个分支,
它们方向相反、都不能错:没有出口权限 → 明确拒绝;DB 暂时查不动 → **一个字都不改**、回 try_again
让客户端重试(当成「未批准」就是一次库抖动把人从选定出口踢回 server)。另外钉住「每次重新选择都
复位那两个一次性闸」——不复位的话,换到新出口后它离线不再通知(用户干等),换出口也不再进审计。

**端口转发这边同一个母题:不改现状、不假装成功。** reload 读不到映射表时保留现有监听(清空等于把
所有公网入口一次性关掉);Accept 遇瞬时错误退避重试而不是退出循环(退出就是那个端口从此不接客,而
运行态里它仍是 running,只有用户会发现连不上);解析不出目标就关连接,绝不盲拨陈旧 vIP。

三条判为等价,都值得记下原因:`parsePacketTuple` 失败时一律返回零值 tuple,零地址不可能是公网 v6,
所以 v6 快失败里那道 `!ok` 是防御性冗余(将来它若返回部分结果就不冗余了);`sendEgressSelectAck`
入口的 `safeLinkConn()` 只是 race-free 预筛,写锁内还有一次复核;`resolveDeviceID` 的空 UUID 闸只
省一次 DB 查询。

两条逃逸暴露出**同一个毛病**,跟上一轮 `deviceID=0` 那条一模一样:断言里的表根本不含能触发该闸的
表项,于是断言等于没测。`frpLANReplyFromDevice` 要塞一条 `deviceID=0` 的表项才真正钉住匿名会话那道
闸;reload 的第 ③ 段清理要拿一个 **bind_failed** 的端口才测得到 —— 在跑的映射被删时,停监听那条路
顺手就把状态清了,只有压根没进 active 的失败态才需要这段扫描。这类「断言的前提没建立起来」是变异
测试最常揪出的一类,读代码时几乎看不出来。

还有一次返工是测试自己造的数据竞争:用「拨一下看通不通」证明监听还活着,会催生一个连接 goroutine
去拨那个不可达目标,挂满 10s 拨号超时、活得比用例还久,而它一路读的 `globalContext` 会在 harness
收尾时被还原。改成「试着重新绑同一个端口,绑得上才说明监听被关了」——不催生 goroutine、也更直接。

### 第 31 轮:虚拟 IP 的分配与占用

`alloc.go` 20 → 2、`alloc_lease.go` 21 → 0,包 85.2% → 85.7%,变异 20 项抓 17(3 等价)。

**这一块出错只有一种形状:两台设备拿到同一个地址,或者拿到一个不属于本网段的地址。** 两者都不
报错 —— 登录成功、审计正常、后台一切正常,数据面表现是「其中一台时通时不通」,查到根因通常要很久。
分配器此前只被测过 IPv4 /24 的顺序分配:**v6 整条路径从未跑过**,而配了 `subnets_v6` 的部署走的
就是它;第八轮修掉的那条(前缀长于 /112 时算术把网络位写脏,生成前缀外地址)也一直没有回归测试。

**顺手挖出一个真缺陷,而且是 panic。** `[tun].subnets` 写成 v4-mapped 形态(`::ffff:10.0.0.1/24`)
能过配置校验 —— 地址解析出来是 v4,族检查看不出问题。但分配器里网关做了 `Unmap()`、网络地址是
`Masked()` 的产物(`::ffff` 那几个字节被一起掩掉,退不回 v4),于是族一分岔:走 v4 分支却对 v6 形态
调 `As4()`,**直接 panic**。发作时机是第一个客户端登录,不是启动,所以 `config lint` 和开机自检都
照不出来。两侧都修了:分配器开头显式拒绝族不一致并报清原因,配置校验直接拒掉这种写法(掩码会按
128 位解释、下发成 `0.0.0.0`,地址池一个都分不出来)。

**「偏好 vIP」这条快路一直是缺陷高发区,这轮把它的过滤面钉全了。** 自动分配从主机位 2 起扫,天然
避开网关 / 网络 / 广播地址;而直接采用偏好 vIP 没有那层过滤 —— 管理员把 `fixed_vip` 手钉成网关或
定向广播地址时,网段检查会通过、`used` 里也没有,客户端就拿到一个用不了的地址。前者与 server 网关
撞车整条路由断,后者部分内核直接丢弃以广播为源的报文。两条都是修过的缺陷,现在各有断言。

落 lease 的两类错误也钉住了方向相反的取舍:撞 vIP UNIQUE **必须拒登**(说明 alloc 漏算了库里的
离线 lease,放过去就是两台设备同一个地址),其它 DB 故障只 warn 并**放行**(lease 存不下只影响下次
能不能拿回同一个地址,不值得让人登不进来)。混在一起处理的两种坏法方向也相反:都当致命 → 一次
库抖动全员登不进;都当无害 → 两台设备带同一个 vIP 上线。

三条判为等价,原因值得记:上界夹取与 `prefix.Contains` 兜底**互为冗余防线**,单拆一层另一层就补上,
行为不变 —— 但「两层同时拆掉」的组合变异被精确抓住(报出「第 255 次分配给出 `fd00:80::100`,落在
`/120` 之外」),说明这对防线真实存在而不是两层都空。第三条 `maxIter < 1 → 1` 的夹取则是真正不可
观测:循环从 `i = 2` 起,maxIter 取 -1 / 0 / 1 都是零次迭代。**冗余防线这个母题以后会反复遇到 ——
单拆不可观测不等于没测,要用组合变异证明「至少一层在」。**

还有一次是测试自己写崩:把 `/64`、`/112` 这种 65534 容量的池子整个分光,而分配器每次都线性扫描,
总复杂度 O(n²),四分钟都跑不完。大池子只抽查前几百个 —— 那条修复只在主机位少于 16 的小前缀上才
改变行为,小前缀才需要分光。

另:这轮开工时发现工作树被外部快照回滚了 43 个文件到更旧的版本(含 `session.go` 等生产文件),
HEAD 上的提交是完整的,已 stash 收起备查后恢复。**教训:每轮开工前先 `git status` 确认工作树干净。**

### 第 32 轮:TUN 数据面、双栈登录、连接接管

`server.go` 587 → 486,包 85.7% → 87.2%,变异 32 项全抓(含 7 项配置 / 下线广播)。

`server.go` 一家占了全包未覆盖的 58%,但里头 379 条是 `main` 的守护进程启动编排(只能在真实
进程里跑,由 e2e 插桩那侧补,这也是合并后 92.6% 远高于单测数的原因)。真正的缺口是**数据面两条
循环整个函数一行没跑过**:`tunReadLoop`、`tunWriteLoop` 各 33 条。这两条循环是所有流量的必经
之路,而它们的坏法全是静默的。

**丢包路径不还池子是典型的慢性泄漏。** 队列满时丢包是**有意的**(宁可丢也不阻塞整条上行),但丢
之前必须把 buffer 与包结构还回 `sync.Pool`。不还就是每丢一个漏一个 2KB,一次拥塞几万个 ——
内存一路涨到 OOM,而现场只看得到「丢过一些包」。`drainAndCloseTunChan` 同理:每次 shutdown /
重建队列漏掉队列里那上千个在途包。

**写循环的坏法方向相反:一次写失败就退出循环 = 全服下行静默变黑洞,而所有会话仍显示在线。**
所以写错误只记日志继续跑;而 ctx 取消与队列关闭两条退出路径必须都通,否则 shutdown 挂住。
另外 Linux 的 `IFF_VNET_HDR` 要求写时前留 virtio 头,少留几个字节内核就把包头当 virtio 头解析
—— 每个下行包都被丢弃,链路层看起来完全正常。

**登录侧这轮补的是双栈。** v6 地址池耗尽必须**只降级不拒登**(v4 还能用,拒登等于因为 v6 满了
把整台设备赶下线);重连要能拿回同一个 lease(拿不回就是 MagicDNS / 已装路由全部指向旧地址)。

**接管(takeover)是这轮最值得写的一块:它要在换链路的同时把会话状态整套搬过去。** 漏搬任何一项
都是静默降级 —— 漏限速就是重连后限速消失(白给带宽)、漏出口意图与已宣告路由就是接管后出口静默
失效、漏 vIP 就是登录成功但数据面全黑。secret 必须轮换,且**熵源故障时保守拒绝而不是降级用旧
secret**(降级会静默削弱一次性语义);为了能验这条,给 `generateTakeoverSecret` 加了随机源接缝。

**四条逃逸值得逐条记,因为三条都是「我的输入没触发那道闸」。**

- 两条池化断言(丢包 / 排空不还池)最初用「新建对象数」当观测量,但它数到的其实是别的东西:
  `sync.Pool` 复用是 per-P 的、GC 每轮清空池子、而丢包路径每次都打一条 Warn(几百条日志的分配
  足以反复触发 GC)。压掉这两处噪声后还剩一处压不掉:**`-race` 下 `sync.Pool.Put` 会故意随机丢掉
  四分之一的对象**(race detector 借此暴露 put 之后仍在用的 bug),所以基线本身就有约 25% 的新建。
  门槛因此定在总包数的一半 —— 容得下这 25%,又与「一个都不还」的 100% 分得开(两条变异复验仍抓住)。
- 「偏好 vIP 不做可用性过滤」这条逃逸的原因是我拼的 device UUID 里塞了 `"v6"` / `"v4"` 这种非
  十六进制字符,UUID 校验直接不过 → 设备根本没认出来 → `fixed_vip` 压根没进入这条路径,测试
  通过得毫无意义。修好之后 v4 / v6 两侧的过滤各钉一条变异,都抓住了。
- 「vIP 不继承」那条是变异本身编不过(改完 `oldIPs` 成了未使用变量),改写成保留引用的形式后抓住。

**顺手修掉两处测试自身的缺陷,都是这轮全量 `-race` 才暴露的。** 一是上面那个池化门槛;二是
`TestMeTOTPDisable_WrongRecoveryCodeIsRejected` 用「把真码末位改成 `Z`」造伪造码,而恢复码是
base32 —— 末位本来就有 1/32 的机会正好是 `Z`,那时「伪造码」就是真码,2FA 真被关掉、返回 303,
用例随机翻车。改成挑一个与原字符不同的替换字符。

**另外修正了变异归档的体检口径。** 9 条历史变异被我判成「锚点失效」,实际是归档里本就用 `nth`
字段选第二处出现,而我的体检脚本只数出现次数、没看 `nth`。这轮把这 9 条的锚点补到唯一(前缀取到

### 第 33 轮:MagicDNS 的 ACL 口径、路由批准广播、ACL 裁决与丢包审计

`acl_drop_audit.go` 15 → 1、`acl_runtime.go` 28 → 9、`route_advertise.go` 17 → 9、
`magic_dns.go` 42 → 35,包 87.7% → 88.0%(全包未覆盖 903 → 846),变异 34 项全抓、零逃逸。

到这一轮,剩下的缺口已经很碎:最大的几块(`startEmbeddedHysteria` 16、`startPortForwardManager` 11、
`verifyServerIPv6RoundTrip` 10)都要真监听 / 真网络,归 e2e。所以这轮挑的是三块纯进程内的。

**MagicDNS 的 ACL 口径是一处「五个兜底都必须 fail-open,但最后那一下必须真的拦」的组合。**
这道闸堵的是信息泄漏:ACL 判定 A→B 完全不可达时,A 不该能用 MagicDNS 把 B 的设备名解析成 vIP
(否则等于提供了一个探测对方存在性与地址的接口,尽管数据面随后会丢包)。但它每一处「查不到」都
必须放行 —— 判错方向的代价是**同用户自己的设备名突然解析不出来**,现场只看得到「DNS 挂了」。
所以五条 fail-open(快照未装好 / 查询方 vIP 不在归属表 / 名字查不出归属 / peer 地址畸形 / 同用户
自查)与一条「ACL 真判不可达时必须拦」各有断言,少了后者前面那些兜底就等于把闸拆了。

**应答构造那条与第 31 轮 alloc 里的 panic 同一族问题。** 双栈设备两族地址都有,而一次查询只问
一族。A 查询里遇到 v6 地址若不跳过,就会对它调 `As4()` —— 直接 panic,一次查询打掉整个 DNS
goroutine;AAAA 里塞进 v4-mapped 则答出 `::ffff:10.x`,客户端拿它发 v6 必然不通。

**路由批准广播做的两件事表面无关,漏掉任何一件都不报错。** 一是推 RouteApproveStatus 让宣告方
UI 的「待审批 → 已批准」实时翻转(不推就一直显示 pending,用户以为没批而反复重发声明);二是刷新
会话上的**源地址伪装豁免闸** —— 批准后不刷,宣告方合法的回程流量会被一路丢到它下次重连;撤销后
不刷,则是特权多留了同样久。这两条方向相反,所以「只敢开不敢关」也单独钉了一条变异。

**ACL 裁决这侧最容易写反的是白名单语义。** 整段裁决有个 fast-path:user 规则集为空时跳过引擎 ——
但**跳过引擎不等于放行**。`default=deny` 的语义是白名单,规则集为空意味着「谁都不在白名单里」,
必须全丢。写反的后果完全静默:管理员切到白名单模式、还没加 allow 例外,以为已经全锁,实际全网
互通照旧。同一函数里还有一对方向相反的收敛:快照未装好 → fail-open(不然服务刚起来那一下全网
不通),包解析不出 → fail-closed(它已过 ValidIPPacket 仍解不出,放过去就是绕过整个裁决)。

**端口封锁的分片绕过与源地址反欺骗的优先级,是这轮两条真正的安全属性。** 非首片分片里没有 TCP
头,拿不到端口;若判「规则不匹配」就落 default=allow 放行,而目的端会重组出完整的 22 端口连接 ——
攻击者只要分片就能穿过 `deny tcp:22`,日志上什么都看不到。反欺骗那侧钉的是顺序:「冒充另一在线
会话的 vIP」必须判在「已批准出口 / 子网转发者豁免」**之前**。顺序写反就是可利用的漏洞 —— 出口
宣告方本来被允许用任意非 vIP 源地址(它要中继外网回程),豁免若先判,它就能以另一个客户端的 vIP
作源注入伪造回包,对受害者来说那些包看起来来自它信任的对端。

**丢包审计的失效方式是把服务拖垮,而不是少记一条日志。** 它跑在数据面热路径上,每个
(src,dst,proto,port,kind) 组合一个桶 —— 一次端口扫描就能塞进六万多个,而 flush 周期是 60s。
所以有基数上限,超了折叠进单一 overflow 桶:维度信息丢了(target 变 `<overflow>`),但丢包数目仍
准确,而这种情形本身就说明「有人在扫端口」,细分维度也没有排障价值。另外 `interval <= 0` 的夹取
是防 `time.NewTicker(0)` panic —— 那个值来自配置,不夹取就是一条配置项能带走整个进程。

### 第 34 轮:真实客户端 IP 的透传、闲置租约回收、出口 DNS 解析、子网路由的丢包路径

`loopback_proxyproto.go` 14 → 0、`lease_gc.go` 12 → 2、`magic_dns_cache.go` 12 → 10、
`subnet_route.go` 13 → 4,包 88.0% → 88.6%(全包未覆盖 846 → 810),变异 21 项全抓、零逃逸。

**PROXY 头那块的失效方式是静默退化成 server 自己的 IP。** 它把承载层看到的真实客户端地址透传给
上层,而上层拿这个地址做限流、封禁、审计。`normalizeProxyAddr` 要把 hy2 的 `*net.UDPAddr` 转成
`go-proxyproto` 认的 `*net.TCPAddr`(转不动就整段跳过写头),所以一旦这里认错类型,现象是**所有
QUIC 客户端在风控看来都来自同一个 IP** —— 封一个等于封全部,而日志里的地址字段仍然填得满满的。
反方向那条是安全边界:`isLoopbackConnPeer` 限定只有回环对端能带 PROXY 头,否则任何外部连接都能
自己声明一个源 IP,把封禁与限流一起绕过。

**租约回收的危险不在「没回收」而在「回收了正在用的地址」。** GC 按闲置天数删租约,但一台连着
好几天没断的机器同样「很久没更新过租约」—— 判据写宽一点就会把在线会话的地址收走,回收后它被分给
新设备,两台机器同一个 vIP。所以钉了一条「长会话的地址永远不许被收」。另外两条是配置面的:
`idle_days <= 0` 必须彻底关掉这个循环(不是当成 0 天,那会秒清全部租约),`interval_hours <= 0`
要夹到默认值(防 `NewTicker(0)` panic)。GC 循环还必须能扛住一次 DB 失败继续跑,不然一个瞬时
错误就永久停掉回收。

**出口 DNS 解析这块的观测量是 TTL,写错就是缓存污染的时长。** 一条应答里多个 A/AAAA 记录 TTL 不
同,缓存必须取**最小**那个;取最大就是让已经失效的地址在缓存里多活一段。CNAME 的 TTL 不能参与
(它描述的是别名的有效期,不是地址),NXDOMAIN / NODATA 这两种「没有答案」的应答要按 RCODE 区分
缓存,而畸形 / 截断的应答必须整条拒掉 —— 半条解析出来的答案进了共享缓存,受害面是所有客户端。

**子网路由的丢包路径,「丢」与「不丢」都不能回退。** 这个函数的返回值决定调用方还走不走后面的
出口 / server 链路,所以「按策略丢弃」必须报告已处理:报告未处理意味着一个发往 `192.168.x` 的包
继续往下走,最后从 server 的公网网卡发出去 —— 内网地址与内网访问意图一起泄漏到公网上,而触发条件
是「宣告方队列满」「包超长」这类临时状况,现象间歇、极难查。反过来「不归我管」的两种(nil 会话、
解析不出五元组)必须放回原链路,否则这些包被这条路吞掉。server 主动发起那条另有一道:目的必须落在
宣告方**当前**宣告的前缀集里 —— 库里批准过不等于它现在还在宣告。

顺带修了一处 `tunReadLoop` 里的共享读:ctx watchdog 是分离 goroutine,它与主循环各自去读全局
`globalContext`。两者本该看同一个 ctx,否则「谁关的 dev」与「退出日志算不算预期路径」会参照不同
的 ctx。改成入口一次取定的局部变量(`-race` 下由 TUN 数据面用例报出来的)。

### 第 35 轮:经出口解析的失败分支、ICMPv6 秒回落、端口转发的启动编排

`magic_dns_exit.go` 17 → 4、`port_forward.go` 18 → 3、`egress_select.go` 29 → 24、
`magic_dns.go` 35 → 33,包 88.6% → 89.1%(全包未覆盖 810 → 773),变异 17 项全抓、零逃逸。

**经出口解析这条路的失效方式不是「查不到」,而是悄悄回退成 server 本地上游的答案。** 一个绑了
peer 出口的会话,公网流量全从出口走;DNS 若由 server 本地解析,CDN 会按 server 的地理位置给边缘
节点 —— 那些节点对出口可能是烂路由甚至不可达,而客户端 OS 已经把答案缓存起来,换回直连后还要继续
误导它一段。所以口径是「确定绑了出口就必须由出口作答,出口给不出答案就 SERVFAIL」。这轮把四种
「给不出」逐条钉住:应答的答复区截断(A/AAAA 与 HTTPS 两条路各一份)、server 无 v4 网关构不出注入包、
出口迟迟不答(超时)、以及关联端口耗尽。最后那条尤其要拒不要凑:关联端口是「回包属于哪条在途查询」
的唯一凭据,复用一个已占用的端口会让两条查询的应答互串,而两边看起来都成功了。这些失败都不许落
缓存 —— 缓存是全 egress 共享的,一份解析不出的应答进去,受害面是这台出口上所有客户端。

**HTTPS/SVCB 必须与 A/AAAA 同路。** 浏览器现在对每个站点并发查 A/AAAA 与 HTTPS(65)/SVCB(64),
而 HTTPS RR 里的 ipv4hint/ipv6hint 同样被 CDN 按解析位置就近下发。只把 A/AAAA 引到出口就留了一条
同病的旁路:浏览器优先用 hint 直连,拿到的还是 server 地理的边缘节点。反方向也钉了一条 —— MX 这类
没有「按解析位置就近」语义的类型不该多绕一趟出口(每条最多占位 2s 在途位)。

**那帧 ICMPv6 的作用是让客户端立刻失败,而不是让它通。** server 无 v6 公网出网时,使用方发往公网
v6 的包无处可去;什么都不回,Happy Eyeballs 要等、QUIC 更要等十几秒才回落,用户看到的是「网页转
半分钟」。所以每处细节都是「能不能被内核采纳」:整包必须裁进 IPv6 最小 MTU 1280(超了在路上被丢
等于没回),校验和必须对(错了内核静默丢弃),而构造不出来时绝不能投一段半成品占掉一次下行。

**端口转发的启动这一步做了三件互不相干的事,失效都不报错。** 一是解析 mesh 网段 —— 这是「target_ip
是 mesh vIP 还是节点 LAN 后的设备」唯一判据,v6 那段漏解析会让 v6 vIP 目标进 LAN 精确路由表,数据面
的源反欺骗放行表跟着跑偏;二是清掉上次崩溃残留的放行规则,不清则那些端口一直对公网开着,而 web 上
看不到任何映射;三是把自己发布成全局单例,没发布则之后所有 reload 都是 no-op,表现为「改了映射要
重启才生效」。另外主机路由是按引用计数共享的(同一台 LAN 设备的 80 与 443 共用一条 /32),删映射时
不看计数就删,另一条映射当场断而它自己什么都没改。iptables 那侧则相反 —— 系统命令失败只 Warn:
容器里没 CAP_NET_ADMIN、机器没 ip6tables 都很常见,当成致命错误就是 v4 一切正常的机器整个特性起不来。

### 第 36 轮:PoW 出题限速表、审计回收循环、SIGHUP 延迟字段、账号失效扫描、子网路由列表

运维就不再看它。exit_mode / exit_deny_private / exit_dns_redirect 都有归一化语义(空值、大小写),

### 第 37 轮:上游 DNS 转发、限速连接计数、路由审批细节、ACL 快照构建、管理面定向刷新

而使用方的下拉里看不到这台在线出口 —— 两侧都表现为「批了但用不了」。子网侧还多一个前提:只在路由表
确已加载时才据其改写豁免闸,否则启动初 / reload 瞬间会把一个其实已批准的宣告方的豁免误清成 false。
审批项的时间戳取「宣告」与「批准」里更晚的那个;两个时间戳都是秒级,同一秒落库会相等,所以断言里

**ACL 快照是数据面每个包唯一看的东西,构建时放错桶后面全错,而 `acl list` 显示的仍是库里那份正确配置。**
未知的 default 值必须收敛成 deny —— 方向错了就是整台 server 默认放行,一次配置笔误即可触发。出口规则里
`src_user_id=0` 是「对所有用户生效」的通配写法,落进 by-src[0] 就永远没人命中,管理员配的限制静默失效。

「带端口的规则不压到无端口流量上」这条又是**冗余防线单拆不可观测**的老母题:proto 判断与 `hasL4Ports`
判断各自都足以挡住 ICMP,拆掉任一层另一层就补上。按第 31 轮的做法用一条「两层同拆」的组合变异证明

顺带修了一处我自己写的测试污染:`/reload?what=routes` 会把子网路由表装进全局并留在那儿,不还原的话

显式环境变量作逃生口 —— 曾有运维把它误配成 `0.0.0.0`。另外三种输入各有各的正确行为:空地址是「运维

server 带下去。

不确定。三种读不到的情形(库不存在、文件不是库、库里还没有表)都必须一律按「无偏好」处理并继续启动 ——

顺带钉住了 fixed vIP 掉出网段的**告警去重**。数据面在这种情况下会静默改走自动分配(对的:钉的地址在新网段

### 第 40 轮:panic 兜底、supersede 等待、出口列表推送

`safego.go` 4 → 0、`supersede.go` 4 → 0、`exits_list.go` 4 → 2,包 90.6% → 90.8%,变异 12/12 全抓
(含一条「两层同拆」的组合变异)。

**panic 兜底这一层是「一条连接挂掉」与「整机瞬断」之间唯一的隔离,而它两个方向都不能错。**
per-connection 的 panic 不许升级成进程退出:Go 的默认行为是任一 goroutine panic 直接终止进程,
一个畸形包打崩一条连接的处理 goroutine,全部在线用户同时掉线,而且 `cleanupConnection` 也不会跑 ——
vIP 占用位、`connIDMap`、TunChan 全留在内存里陪进程一起死。反方向:关键全局 goroutine(TUN 读写、
demux、保活)的 panic **必须**升级成 graceful shutdown。只 recover 不做别的更糟 —— 进程还活着、监控
绿着、systemd 不会拉起新实例,而数据面已经停了:客户端连得上、包不通,没有任何一条日志说破。
第三个方向也钉了:正常返回不许触发关机,否则每个正常收尾的后台循环都会顺手把整机带下来。

**supersede 存在的全部意义是「同一台设备重登,vIP 不变」**,为此新连接要等老连接彻底清理完才去分配
地址。这段等待有三条边界:victim 列表里的 `nil` 会在解引用时 panic,而这段跑在登录路径上,炸的是正在
登录的那个用户;重复项会让同一条连接被 close 两次、被等两次;总等待必须硬顶在 `supersedeWaitTimeout`
内 —— 这里曾是「逐条各等 5s」,多条 victim 同时卡在 `takeoverMu` 时退化成 5s×N,新连接的握手响应被拖到
客户端超时,用户看到的是「重连要等半分钟甚至失败」而服务端一切正常。到点未清完要继续登录(退化成
无 supersede:可能换个 vIP)并打 WARN,而不是拒登 —— 拒登比换地址更糟,设备得等那条卡住的老连接自己超时。

为了把等待时间调到几百毫秒,`supersedeWaitTimeout` 从 const 改成 var(生产不改这个值)。

**出口列表是情报**:它告诉对方这个 mesh 里有哪些设备能当出口、此刻谁在线。所以没有 `exit_allowed`
的会话一个字节都不能收。这条闸有两层(初始推送入口 + 单条推送),单拆任一层另一层都补得上,于是单条变异
永远逃逸 —— 这正是第 31 轮记下的「冗余防线」母题。这轮顺手给变异脚本加了 `also` 字段:一条变异可以带
若干附加改动,一次同时拆掉多层,从而证明这对防线真实存在而不是两层都是空的。

推送还必须带写超时并在写完撤掉:这条链路写在持 `exitsBroadcastMu` 期间,一个 TCP 窗口写满的客户端
没有写超时就会一直占着这把锁,拖住**所有**出口列表广播与初始推送 —— 现象是别人的出口下拉长时间不更新。

`exits_list.go` 剩的 2 条是 `MarshalExitsList` 失败与写锁内的 nil 复核,都是不可达兜底。另有一条
「查 DB 按 device 去重」的效率闸没能变异验证:`gatewayState.store` 是具体类型,进程内无法数 DB 调用次数,
而它的效果只体现在开销上(同设备 N 条会话 → 每次广播乘 N 次查询),不改变任何可观测的输出。

### 第 41 轮:server 自身 v6 出网探测、PoW 清扫、非 Linux 桩

### 第 42 轮:DNS 闸的 fail-open、畸形应答、hy2 地址中转、僵尸 smux

`magic_dns.go` 27 → 19、`magic_dns_cache.go` 10 → 1、`loopback_smux.go` 9 → 7、`hysteria_clientaddr.go`
补齐、加上一批小函数(匿名设备索引、isolate 提醒、非 Linux sweep 桩、drain 超时兜底),包 91.0% → 91.4%
(未覆盖 612 条),变异 25/25 全抓(含两条「两层同拆」的组合变异)。

**MagicDNS 的每一道闸都必须 fail-open,因为 fail-close 的表现是「域名解析不了」而不是「拒绝访问」。**
mesh 总开关、ACL、isolate 三道闸都要先认出查询方是谁,而查询方地址可能压根拿不到(nil peer、无 IP、
长度畸形)。这时候拦下来最省事,但 server 本机自查、健康探测同样从这条路进来,拿到的是 NXDOMAIN ——
运维会去查 DNS 配置,而真正的原因是一道安全闸在信息不足时选择了拒绝。同理,4via6 站点映射指向一台
已删除的设备时不能推出一个「无主」的 user id 去比对(那会误判成同用户放行),设备表读不动时也不能当成
「没这台设备」继续往下走 —— 前者是越权,后者是把一次 DB 抖动变成整片名字的 NXDOMAIN。

**畸形应答的唯一正确处置是整条丢掉,不能半条入缓存。** 出口 DNS 结果是**共享**缓存:A/AAAA 的 rdata
被截断、答复区里混进未知类型、question 段的标签越过报文末尾,只要有一处「解析到哪儿算哪儿」,残缺的那
半条就会被后续所有查询命中,直到 TTL 结束。改写不出来时必须 SERVFAIL —— 客户端会重试或回落,而返回一个
自认为「差不多对」的应答等于把错误答案钉死。question 偏移那条还是一对冗余防线(循环顶部的 `pos >= len`
与末尾的 `pos > len`),单拆任一层另一层都接得住,要靠组合变异才能证明它们真在。

**读循环在 in-flight 打满时必须就地丢包并记数,不能排队等位。** 阻塞等位会把内核接收队列堵满,于是
攻击者用几十条慢查询就能让整台 server 的 MagicDNS 停摆;而丢包不记数则让「偶发查不到」永远查不出来。
写这条断言时踩了一次假绿:只断言「池满时没有立即回应」的话,阻塞版本会在腾出位子后把那条查询补答上去,
一样是绿的。给两条查询各一个 txn id、分别在「池满时」和「腾空后」发出,才能区分「丢了」和「晚答了」。

**hy2 真实客户端地址中转表**的 token 撞号被断言抓住了,是个真缺陷:熵源故障时降级用时间戳串,而 macOS
的 `time.Now()` 只有微秒分辨率 —— 同一微秒内的两次调用拿到同一个 token,两个客户端的真实地址互串,
之后限速、IP 失败计数、审计全部记到对方头上。修法是给降级路径挂一个原子单调序号。

**smux 僵尸会话**:承载连接死了而 `Session.IsClosed()` 仍是 false(keepalive 还没到期),这时池子必须靠
`OpenStream` 的失败自己摘掉会话并重建,否则新流会连续失败到 keepalive 超时为止。

顺带把两处 const 改成 var 接缝:`shutdownDrainTimeout`(否则「负超时要回落成默认」这条无法在秒级观察)。

**终于定位到挂了两轮的那条偶发失败,而且两条是同一形状、都在测试侧:**上一个用例 `go handleVPNLink`
派生的 goroutine 还在跑,下一个用例的 setup/cleanup 就已经在写 `sharedTUNGateway` / `globalContext`
了。测试用例自己不会失败在正确的地方 —— 报错落在毫无关系的下一个用例上,所以前两轮都误判成「harness
读超时余量不够」。修法是给 harness 一个 `vpnLinkHandlers` WaitGroup,派生走 `goHandleVPNLink`,
并在 **demux 收尾里**先等 handler 退干净:顺序是硬要求,handler 退出要走 `cleanupConnection`,而那一步

只表现为「换端口就连不上」。装不上时也一样要先把已绑的 UDP 端口还回去,否则 systemd 拉起的新实例撞上

goroutine 里写的,边写边读被 `-race` 抓住 —— 换成带锁的观测 conn;二是 `freePort`/`pickFreeUDPPort`
的「先绑再关、把号交给被测代码稍后重绑」在 `-race` 下撞过一次 `bind: address already in use`
(`TestPortForwardReload_KeepsListenersWhenTheDBIsUnreadable`),因为 `:0` 拿到的号落在临时端口区间,
中间窗口里同进程的任何外发 socket 都可能被分到它。改成在临时端口区间之外随机挑并确认当下能绑。

### 第 44 轮:分发链上的 continue、审计表回收、v6 探测的两段判据

`server.go` 465 → 460、`egress_select.go` 20 → 13、`hysteria.go` 16 → 12、`audit_gc.go` 5 → 2,
包 91.7% → 92.0%(未覆盖 568 条),变异 19/19 全抓。

**「命中即 continue」是一整类看不见的缺陷。** `runLinkTunnel` 的读循环是一条依次表决的链:出口 DNS
回包截获 → 源反欺骗 → 子网路由 → 出口闸 → ACL → peer 出口 → v6 秒回落 → 落到最后才写 server 自己的
TUN。每一道判据返回 true 都意味着「这个包已经有人处理了」,后面必须 continue。漏掉不会报错、不会丢包、
日志上什么都看不出来 —— 只是这个包被**处理两次**,第二次从 server 自己的公网出口再发一遍:内网包从公网
网卡出去、用户选的出口被静默绕过(暴露的是 server 的 IP,而客户端 UI 上出口还是绿的)、已回过 ICMPv6
的 v6 包又进内核黑洞。判据自身的单测覆盖不到这层 —— 它们只验返回值,而「返回 true 之后调用方停没停」
在函数外面。这一轮把四条都钉住了。

**审计表回收接错了同样没人会发现。** 循环本体此前已有用例(进来先跑一次 / DB 失败继续 / ctx 取消退出),
但 `startAuditGC` 交给它的**参数**从没验过:窗口传成 0 → 刚写的审计当场被删,合规要求的 30 天等于没有;
没起这条 goroutine → 表只增不删,而每次登录都要往它写一行,表越大写越慢,最后拖慢的是登录本身。
体积告警也补上了 —— 这条循环故意不做 VACUUM(排他锁风险太大),对「表已经很大」唯一能做的就是出声。

**v6 出网探测的两段判据只有一个方向是危险的。** 判「没有」而实际有,只是退化 v4-only;判「有」而实际
没有,所有公网 v6 流量会被照单写进 TUN 在内核黑洞,客户端没有任何反馈,只能干等超时。所以路由级那段必须
落在 OS 选出的**源地址**上(只看「UDP connect 成功」的话每台有 ::1 的机器都会被判成有 v6 —— connect
只做路由查找,从不发包),端到端那段必须以**真收到回包**为准(这段存在的全部理由就是防「有 GUA、有默认
路由、就是出不去」的假 v6)。把探测目标指到环回,正好是「路由通、地址有、绝不是公网出网」的现成样本。

hy2 那边补了混淆器初始化失败时的回滚(端口 + 跳跃规则),以及开了 `udp_relay` 时 UDP 出口要真给一个可用
socket。前者的触发条件在配置校验里已经拦过一遍,是两套限值分头写死之后的兜底 —— 库升级改了下限而我们的
校验没跟着改时,这条路就是现场唯一会走的路。

两条变异逃逸,都是老母题的再现:一条是「保留窗口接成 0」—— 我拿刚写的记录当对照,而它的时间戳等于 cutoff,
按严格小于判不会被删,于是窗口 0 和窗口 30 天在这条记录上看不出区别(观测点没落在被测那道闸上);另一条是
`sendEgressSelectAck` 的两层 nil 复核互为冗余,得用「两层同拆」的组合变异才证明得了至少一层在。

顺带修掉一处**测试自身**的隐蔽污染:有四处用例往 TunChan 里塞了手工造的在途包(`Buf` 只有 4 字节、甚至
是 nil),而队列里的包最终会被 demux / `drainAndCloseTunChan` **归还池子** —— 池子里于是混进一条短
buffer,之后任何一次 Get 拿到它都只装得下那么多字节。现象落在毫无关系的另一组用例上(出口 DNS 那批报
「注入出口的查询包异常」),而且要特定顺序才复现。生产代码从不这么造包,这是测试独有的失守。

**跑全仓 `-race` 要显式给 `-timeout`。** 这一轮的回归里 `cmd/nanotun-web` 报了一次超时 —— 不是死锁:
那一包在 `-race` 下要 672s,已经越过 `go test` 默认的 10 分钟(它的用例大量走 argon2id,插桩后单条就是
几百毫秒)。改用 `go test ./... -race -count=1 -timeout 30m` 后八包全绿、零竞态。默认超时报出来的是一份
goroutine dump,乍看像挂死,实际只是预算不够 —— 值得记一笔,免得下次照着 dump 去追一个不存在的死锁。

### 第 45 轮:按「修过的缺陷」反查缺测 —— 接管收尾、TUN 批量写、回绕与零散闸门

包 92.0% → 92.2%(未覆盖 568 → 550 条),变异 16/16 全抓。

**这一轮换了挑靶子的方式。** 之前每轮都是「按文件未覆盖条数从多到少」往下扫,剩下的都成了零散防御。
这次改成:把生产代码里所有 `深扫 MED/HIGH/P0` 注解(247 处 —— 每一处都是历史上真出过的缺陷)与覆盖率
profile 对齐,列出「注解之后紧跟着未覆盖语句块」的 42 处。**修过的缺陷长期没有回归测试**,是这个仓库
反复出现的模式(第 11 轮公网 CIDR、第 23 轮跳板机、2026-05-21 登录事故都是),按这条线索找比按条数找
命中率高得多。42 处里 30 处落在 `main()` 启动编排(归 e2e),剩下的正是这一轮做的。

**接管的收尾等待是最值得补的一处。** 接管不换 vIP,新老连接共用同一组 TunChan。老链路的 demux 还没
退出就启动新 demux,两个 demux 会并发从同一条下行队列取包 —— 取到的那一半被写进已经关掉的老链路,直接
丢。现象是热切换后下行断续丢包几十秒,客户端不报错、日志也不报错。所以 handler 先等老链路退出、等不到
就 cancel 它的 tunnel ctx 逼停(demux 可能卡在限速器 `WaitN` 上,那个既不看 deadline 也不看链路已关)、
再等不到才作为最后手段继续。三段逻辑此前一行没跑过。两段等待原本是硬编码 5s / 3s,加了
`takeoverOldTunnelGrace` / `takeoverOldTunnelCancelGrace` 两个接缝(否则每条用例要为它付 8 秒)。

这里也撞上「冗余防线」那道老坎:抢老链路写锁**之前**已经 cancel 过一次(第二十轮深扫 MED),所以单拆
grace 里那次 cancel 时另一层会补上,变异照样逃逸。用两层同拆的组合变异才证明得了这对防线真实存在。
另一条 `time.After` 的变异也逃逸过 —— 因为那条用例里老 demux 一被 cancel 就退出,第一段等待压根不会
超时;把它指到「老链路从不退出」那条用例才落到那道闸上。

**TUN 批量写循环有两处只在边界上才走的分支。** 一是设备报出的批大小直接进 `make([][]byte, 0, n)`:
负数就是 panic,而它在 `tunWriteLoop` 的第一行 —— 崩在这里等于整台服务器的下行从未起来过。二是攒批的
第二步撞上队列关闭时必须先把已经取走的包写下去:直接 return 的话那个包凭空消失,而停机时正是这个时刻。

其余是四个文件里的零散闸门,共同点仍是「坏掉之后没有任何错误路径会响」:`conv_id` 计数器回绕到 0 时
必须跳过(0 是「没有连接」的哨兵值,登录侧和接管侧各有一份实现);已被接管的僵尸会话不许再替 vIP 回答
出口归属与上线时刻;保活的 miss 阈值缺省时要用默认值(真按 0 用则判活窗口也是 0,全站客户端以 ping
间隔为周期集体掉线);`tun_ready` 这个 gauge 起来之后要翻成 1(恒 0 就是每天误报,静音之后真出事没人
看);PoW 限速表的摊销 GC 要真删过期项;出口 DNS 缓存取最小 TTL 的两个分支(A 与 AAAA)各要一份断言。

**变异逃逸的第四种形状:断言的观测串在被测输出的别处也出现。** `tun_ready` 那条我用
`Contains(out, "nanotun_tun_ready 1")` 判,而 Prometheus 的 `# HELP nanotun_tun_ready 1=TUN device
is up` 一行本身就含这个子串 —— 指标恒 0 时断言照过。改成整行匹配(`\nnanotun_tun_ready 1\n`)。
另一条则是**锚点撞了同名代码**:`batchSize := dev.BatchSize()` 的夹取在读、写两个循环里各有一份,
变异默认打在第一个(读循环)上,而用例只跑写循环,于是报逃逸。这类要用 `nth` 定位。

顺带确认了三处**结构上不可达**的防御,不再为它们花时间:`handleVPNLink` 里多 vIP 分配失败的回滚循环
(`localIPsForVPNAllocation` 恒返回 1 个元素,失败时已分配数必为 0);`maskFromGatewayCIDR` 里
「netip 认成 v4、而 net.ParseCIDR 给 16 字节掩码」那一支(两个解析器对 v4 的判定同源);
`loginIPLimiter.SetRatePerMin` 的负值夹取(唯一的读方 `AllowLogin` 自己就按 `<= 0` 短路)。

### 第 46 轮:接管落定后的出口复核、下发给客户端的 DNS 列表、半坏的库

包 92.2% → 92.5%(未覆盖 550 → 534 条),变异 16/16 全抓。沿用第 45 轮那条线索(按历史修复清单反查缺测)。

**接管落定后要补一次出口复核,这一处此前一行没跑过。** admin 撤销出口时,`revalidateExitBindings` 扫的是
当时的 connIDMap;如果它扫到的是**还没标记 takenOver 的老连接**,CAS 就落在那条即将死掉的连接上,真正在跑
的新连接漏掉了。结果是「后台显示已撤销,那台客户端还在从它出网」,直到客户端下次重连。热切换在弱网下是
常规动作,这个窗口不难撞上。

**下发给客户端的那份 DNS 列表,登录和接管各拼一次,两边都要钉。** 开了 Magic DNS 时网关 IP 必须**顶到**
列表最前面:客户端按顺序问,网关不在第一位,`*.lan` 会先被公共 DNS 答成 NXDOMAIN,而客户端拿到否定答案
就不再往后问了。现象是「magic_dns = true、服务端 :53 在听、日志全正常,客户端就是解析不了内网名字」,
从两侧任何一处都看不出问题。反过来,`listen_port != 53` 时**不能** prepend —— 客户端 stub 只打 :53,顶上去
就是每次解析先白等一轮超时。接管那侧还漏了 v6 解析器的断言:那份列表是重新拼的,不是从老会话抄的,漏掉
哪一族,客户端热切换之后那一族的解析就整体不见了。

**「已经回过 SERVFAIL」不等于「到此为止」。** 绑定出口的会话查公网名走 fail-closed(2026-07-17 起):
出口兑现不了就回 SERVFAIL,绝不回落 server 本地上游 —— server 与出口常隔着半个地球,CDN 按「谁来问」
就近调度,用 server 地理的答案填客户端 OS 缓存,拿到的边缘节点对出口是烂路由甚至不可达(实测经重庆出口
约 27% 连接失败),而缓存要等 TTL 到期才自己好。判定本身有一组用例,但**调用点有没有真的 return** 没人验过:
少一个 return,SERVFAIL 照发、紧接着又向上游发一份查询,客户端(先到先用)很可能采信后到的那份。所以这条
用例的观测量是「本地上游一次都没被问过」,而不是「客户端收到的是 SERVFAIL」。

其余四处:hy2 的 `listen_addr` 端口位允许写并集,所以拆 `host:port` 那步对 `443x` 是放过的 —— 只有并集解析
认得出来,这道闸没拦住主端口就落成 0,交给内核就是随便给个临时端口,于是 hy2 听在一个谁都不知道的号上,
`node_login` 上报的也是那个号,客户端全连不上而日志一片正常(`:0` 是刻意支持的,不在此列)。SIGHUP 的限速表
diff 必须比值不能只比键,否则运维改一个数值会被判成「没改动」,reload 返回成功而限速还是老的。用户失效扫描
的 by-user 索引要跳过两类坏表项:nil 值(取字段当场 panic,这一轮剩下的用户全部漏扫,下一 tick 还会撞上同一
条 → 永久漏扫)和解不出 user 的键(空 userID 的会话落在这里,不跳过就按「账号已删」被连坐踢下线)。子网路由
重建一次干两张表,4via6 那半边查不动时普通子网路由必须照常装上、已生效的 site 映射也不许清空 —— 否则每次
批准/撤销触发的 reload 都会因为一个辅助表把所有跨网段互访打断。

**这一轮有两条变异逃逸,根因都是「输入压根没走到那道闸」**(第 30 轮记下的那个母题又来了):用户失效扫描
那两条,我造的坏键用了 `"999999"`,而这个仓库里 userID 的线上形状是 `"u<id>"` —— `parseUserIDStr` 直接判 0,
坏表项被**前一道**闸(uid<=0)拦掉了,后面那道 nil 判定根本没机会跑。`initAuthBackend` 那条同理:我用一个
写了乱码的文件当 db_path,以为它「能打开、建表失败」,实际 `store.Open` 自己带 ping,当场就报
`file is not a database` —— 测的是上一道闸。改成先建一个合法库、在里面用 view 占住 `users` 这个名字,才真的
落到建表那一步。教训是同一句话的第三种说法:**写守卫测试时先自问「我这组输入真的能走到那道闸吗」**,而
不只是「去掉那道闸会不会变色」。

hysteria 剩下的两处经确认**进程内不可达**,不再花时间:`udpPortFromPacketConn` 要求
`net.ListenPacket("udp")` 返回非 `*net.UDPAddr` 的本地地址;`hyserver.NewServer` 会拒的每个维度,

### 第 47 轮:`--json` 的键名契约(一族命令两套形状)

`cmd/nanotun-admin` 96.8%(与上次持平 —— 这一轮改的是行为不是覆盖面),变异 10/10 全抓。这一条是第 22 轮
留下的待定项,e2e 阶段 20 当时明确写了「此处按现状钉」。

**四条命令的 `--json` 打的是裸 store 结构体。** `acl allow` / `acl deny` / `lease set` / `device list` 直接
`printJSON` 了 `store.ACLPair` / `store.Lease` / `[]*store.Device`,而这三个类型没有 json tag,于是键落成 Go
风格的 `Action` / `DstPortLo` / `DeviceUUID` / `RateUploadBPS`;同族的 `acl list` / `lease list` 是手写的
snake_case。**同一命令族两套形状,而失败模式是无声的**:`device list --json | jq '.[].device_uuid'` 拿到的是
`null` 而不是报错,CI 里 `null` 往下传通常一路无声 —— 编排工具于是把一台刚建好的设备当成「没有 UUID」写进
下游配置。`acl deny --json` 更险一点:端口是这条命令**唯一只能从 JSON 拿到**的信息(人类那行是 `formatACLPort`
拼好的字符串),键名对不上就等于「加了一条规则,但脚本读不出它管的是哪个端口」。

改法是三个 CLI 本地视图类型(`aclPairView` / `leaseView` / `deviceView`),沿用本包已有的 `userView` 与
`acl list` 的手写 `row` 同一套路子 —— **不动 `store` 的类型**:那三个类型在 web 侧被 go template 直接引用
(template 按字段名取值,不看 json tag),加 tag 虽然当下无害,但把一个 CLI 的展示口径钉进了共享层。
`acl list` / `lease list` 里原本的局部 `row` 提成包级,两条命令共用同一个类型,形状对不上会编不过而不是
在运行时错开。

顺带补齐了同族 list 才有的关联列:`acl add/deny` 给 `src_username` / `dst_username`(命令行传的就是用户名,
本来就知道),`lease set` 给 `device_uuid` / `user_id` / `username`。少了它们,脚本「钉完地址立刻记一条审计」
得再查一次库。补这几列时**查不动库不能让命令失败** —— 租约在补列之前就已经落库了,为一个纯展示字段判失败,
调用方会去重试一个已经成功的写,而 `UpsertManualLeasePreservingEmpty` 只保留「命令行没传的那一族」:重试时
参数拼得不完全一样(编排工具重试常常只带上次失败的那个字段)就会改掉 manual 标记。`device list` 另给
`display_name`(设了 alias 用别名,否则回落 `device_name`),否则调用方得自己重实现这个回落,而漏掉回落的脚本
会在没设别名的设备上打出空名字 —— 一张设备清单里凭空少掉一列,它自己不报错。

守卫测试的观测量选的是**键集合本身**(`json_shape_guards_test.go`):不逐个比键名(各自的用例已经在验),
而是钉住「同族两条命令的顶层键集合一致」+「顶层没有大写开头的键」。理由是往回退化的方式几乎总是同一个 ——
新写的命令直接 `printJSON` 了 store 结构体,而那一步的结果恰好就是键集合整体错开。

这是一次**破坏性变更**,已在 `cmd/nanotun-admin/README.md` 的全局 flag 一节写明,e2e 阶段 20 的断言同步改成
读 `action` / `proto` / `dst_port_lo`(顺带把端口一起断言,此前只读了 action)。

同一轮清掉了两处恒为 nil 的 error 返回值(第 22 轮记下的待办),包 96.8% → **97.1%**,变异 7/7:

- `confirm()` 的 error 恒为 nil ——「读不到 stdin」在危险操作上唯一安全的降级就是当作没确认,没有第二种
  处置。九个调用点里五个本来就写 `ok, _ :=` 把它丢了,剩下四个的 `if err != nil { return err }` 是死代码。
  两种写法并存反而让人以为「取消」和「读不到输入」是两回事。
- `openProfileOutput()` 的 error 同理:含密产物先攒在内存里,真正碰磁盘的是 closer 里那次
  `writeFileTight` ——「打开」这一步压根没有会失败的动作。留着那个返回值会让人以为「路径不可写」在这里
  就能发现,而实际上要到 closer 才知道(那已经是写完 stdout 之后了)。

### 第 48 轮:SIGHUP 的 deferred 清单漏了五个字段(按配置开关反查)

这一轮的入口不是覆盖率，而是「**e2e 只跑一套服务端配置**」——`client_isolate` / `jump_host_firewall` /
`forward_block_bt` / `login_rate_limit_per_min` / `udp_relay_enabled` 这些开关的另一个取值只有单测碰过。
在盘这几个开关的语义时先撞上了一个更基础的问题:改了它们发 SIGHUP，**既不生效、也不告诉你没生效**。

`classifyDeferredFields` 的自我定位是「有意不完整，只覆盖运维最常改的几项，避免 noise」，所以「某字段不在里面」
本身不算缺陷。判定这五个是漏的，靠的是**同族兄弟已被覆盖**这条更硬的判据:

- `tun.forward_block_bt` / `forward_block_tracker_6969` / `forward_block_smtp_25`:在 `server.go:1175`
  那一次 `SetupIptables` 调用里，它们和 `ResolveExitMode()` / `ExitDNSRedirect` / `ExitDenyPrivate`
  **是相邻的实参**。后三个早就进了 deferred（`exit_dns_redirect` 那条的注释还专门记着「此前漏进 deferred
  列表 → 运维改了 reload 后无任何提示，误以为已生效」），前三个一直漏着。后果是「开 BT/SMTP 封堵治滥用 →
  SIGHUP → 日志一切正常」，而滥用还在继续。
- `server.jump_host_protected_ports`:同族另两项都已覆盖（开关本身进 deferred、名单是热更且为它修过两轮
  深扫）。唯独「保护哪些端口」只在启动时读一次 —— 运维加个端口、SIGHUP、看到 `applied` 里有
  `jump_host_allowed_ips`，合理地以为新端口也一起受保护了，而它仍对全网敞开。这与跳板机那两次
  fail-open 事故同类。
- `hysteria.udp_relay_enabled`:同段 `password` / `listen_addr` 都在。危险方向是**关** —— 为收紧而改
  `false`、SIGHUP、无任何提示，于是认为已经关了，而进程仍在转发任意 UDP 到下次重启。

`protected_ports` 是列表，比字符串会制造常年噪声（解析器大小写不敏感、`-` 与 `:` 同义、`end<start`
自动交换、非法条目跳过、顺序也不影响落链），而这个测试文件开头就写明「deferred 里一旦有噪声运维就不再看它」。
所以按**效果**比:归一化全部借道真实链路上那两步（解析 + `newJumpHostFirewallWithSpecs` 的清洗），不另写
一份字符串规整 —— 区间反写的自动交换只在后者里做，单看解析器看不到，我第一版就是这么写错的，被反向用例抓住。
为此把解析拆成不打日志的 `parseJumpHostProtectedPortsQuiet` + 打日志的外壳:diff 要把 old/new 各解析一遍，
若用会打日志的版本，每次 SIGHUP 都会为**旧**配置里的错条目再警告一次，而那份配置正要被替换掉。

变异 11/11。其中两条专钉反向（比字符串、不排序 → 等价改写被误报），一条钉住那层新外壳不能被当成纯转发删掉
——「敲错一行只 Warn 不拒服」是有意的，所以那行告警是运维唯一能发现 `tcp/8O8O`（字母 O）的信号，而它此前
没有任何断言，属重构引入的新风险。

`config` 段仍有大量字段两头不沾（hy2 的 QUIC 窗口那一批、`tun.subnets`、`device_name` 等），但它们不满足
「同族兄弟已覆盖」这条判据，按该函数自己声明的口径属于有意省略，这轮没动。

### 第 49 轮:登录归因落在真实客户端 IP 上（三机断言，钉 2026-07-25 那次修复）

按「修过的问题往往没有自动回归」这条线（待办 45）继续查。`loopback_proxyproto.go` 的注释里记着一次
实打实的事故:hy2 会话的审计 actor 曾经全是 `127.0.0.1`,当时靠**双机手工实测**发现，修完之后一直没有
任何自动断言钉住它。

坏掉时的症状恰好是「什么都不红」:隧道照通、会话照在，只有归因悄悄退化成环回地址。后果按严重度排:
per-IP 登录限速退化成全局限速（一个客户端能把所有人锁死）、按 IP 追爆破/扫描直接失效（全是同一个
地址）、PoW 按 IP 累进也一起失效。

这台环境两个客户端都不直连:C 走 hy2（QUIC），A 走 REALITY，都经本机环回 smux 承载再进
`handleVPNLink`，真实地址靠一个 PROXY v2 头带过去。hy2 那条尤其脆——客户端地址来自 QUIC，是
`*net.UDPAddr`，而 go-proxyproto 要求 src 与 dst 同类型，不归一就整个头静默退化成 LOCAL（无源）。

新增两条断言（阶段 5）:各自踢一次线制造全新登录，再断言那条 `login.success` 的 actor 是客户端公网 IP。
关键是**用服务端时钟做起点、只认这次踢线之后的记录**，否则会读到上一轮跑留下的旧记录，归因坏了也照样绿。

正反两向都在三机上核过:
- 正向 36/36 全过。
- 反向注入真实故障（让 `normalizeProxyAddr` 对 `*net.UDPAddr` 返回 nil，复现当年那条路径）:
  `FAIL hy2 登录归因... 期望 [149.28.145.50],实际 [127.0.0.1]` —— 精确复现历史症状，且
  **REALITY 那条保持绿**，说明断言是按承载区分的，不是碰巧过。

顺带查清一件与单测有关的事:直接**删掉** `normalizeProxyAddr` 的 `*net.UDPAddr` 分支并不会让纯 IPv4
的用例变红——下面还有一层 `SplitHostPort(a.String())` 字符串兜底会把它救回来。真正钉住这个分支的是
「IPv6 zone 不能丢」那个子用例，而那是为另一个原因写的。也就是说:分支的**主要用途**没有被直接钉住，
钉住它的是一个次要性质。不构成现实风险（兜底确实有效），但属于「冗余防线让单拆不可观测」这个母题
（待办 49）的又一例，记在这里备查。

### 第 50 轮:按族撤销并不取消出口资格 —— 钉住告警**所声称的那个数据面事实**

继续按「只靠手工/实机验证过的修复」反查（这类按定义就没有自动回归）。全仓扫 `实测` / `双机` /
`三机` 注解，逐条查覆盖。这里记两个结论，一正一反:

**已覆盖、不用再补的**:限速跨层覆盖（`freshUserBW` / `freshDeviceRates`，2026-07-26 三机实测
「user 512 KB/s 生效后改 device 为 1.5 MB/s，吞吐升到 1.19 MB/s」）单测和 e2e 都钉了
（e2e 那条叫「限速 · 放宽设备层不复活旧快照（Bug 11 回归）」）。

**检索教训**:按函数名 / i18n 键名去 grep 测试文件会漏掉走 CLI 表面、断言输出文案的测试。我一度据此
判定 `warnExitStillApprovedOtherFamily` 无测试，实际 `TestCmdRouteReject_WarnsWhenOtherExitFamilyStillApproved`
一直在。

真正的空白在另一侧:出口资格是**按 device** 判定的，只撤 C 的 `0.0.0.0/0`、留着 `::/0`，C 仍是合法出口，
A 的 v4 流量照样经它出网（2026-07-25 三机实测坐实）。当时补的是一条 CLI 告警，告警本身有单测，但它
**声称的那个数据面事实**没有任何自动断言。撤掉 v4 之后有三种可能结局，只有一种是当前行为，而另外两种
都不会让任何现有断言变红:

- 仍经 C 出网 —— 当前行为，也正是告警告诉运维的那件事；
- 回落到服务端出口 —— 用户以为流量走 C，实际暴露在服务端 IP 上，就是阶段 1 开头说的「网还能上、
  不会有任何报错」那类最难发现的静默泄露；
- 整个阻断 —— 与告警文案矛盾，运维会照着一个错的心智模型操作。

新增断言（阶段 1）两条:CLI 确实告警 + 数据面确实仍经 C。**刻意不用 `wait_until`**——它证明的是
「某一刻等于 C」，而这条要钉的是「不得回落」；行为若退化成过一会儿才翻走，轮询会在第一次取样就通过。
改成等过渡态（`notifyExitsChanged` 的踢回/重绑）走完后隔 8 秒采两次。

**反向验证踩了一刀空的，值得记**:第一次注入改的是 `resolveApprovedExitDeviceID`，结果 29/29 照旧全绿。
差点据此认定断言没牙 —— 实际是**这一刀砍错了闸**:决定「已有会话是否继续经 C 出网」的是
`revalidateExitBindings` 用的 `deviceHasApprovedExitRoute`。改砍后立刻变红且只红这一条:
`期望两次取样都是 149.28.145.50,实测 [] / []`（退化成 fail-closed）。

这是母题 70／77 的镜像:那两条说的是**断言**的观测点没落在闸上，这次是**变异**没落在断言观测的那道闸上。
两种都会得出「测试没抓住」的结论，但补救方向完全相反 —— 前者要改断言，后者要改变异。

### 第 51 轮:还原守卫的第二道闸 —— 被第一道闸永久遮住的那半边

先把上一轮欠的补跑做完:全套 **145/145**（第 50 轮新增 4 条，从 141 涨上来），阶段 1 的新断言与后续阶段无互干。

本轮继续反查「只手工验过的修复」，命中 `store/file_identity.go` 那条注解:`nanotund` 与 `nanotun-web`
是两个进程、共享同一个 SQLite 文件，而 restore 换的是 **inode**。按文档流程「stop nanotun → restore →
start nanotun」走完，web 没人停，会继续持有那个已被 unlink 的旧文件 —— 此后后台建用户照样回 303、
照样把一次性 PSK 发给终端用户，数据却写进无人可读的孤儿 inode，全程零报错。这个失败正好发生在灾难恢复
之后，最不容易被察觉的时刻。

修复有两层:`cmd_backup.go` 里 restore 前按 `/proc` 扫真实持有者并拒绝（第一道防线），以及两个进程各自
15 秒轮询 `CheckFileIdentity`、确认被掉包就 `Fatal` 退出、由 `Restart=on-failure` 拉起以打开新文件（兜底）。

**空白在哪**:e2e 早就有两条「服务运行中拒绝还原」，但它们命中的是**另一道闸** —— `serverIsRunning`
探 control socket，只代表 `nanotund`。nanotund 一直在跑，第一道先拦下，`/proc` 扫描那道**永远走不到**。
也就是说当初为 web 补的这道闸，实机上一次都没被执行过。单测（`TestCmdRestore_RefusesWhenOtherProcessHoldsDB`）
用的是合成文件 + 假持有者，钉不住它在生产布局下**认不认得出** `nanotun-web`:`/proc/<pid>/fd` 的软链给的是
解析过符号链接的真实路径，而命令侧是 `filepath.Abs(--db-path)`，**不**解析符号链接 —— 库目录哪天成了软链，
这道闸就静默失效，而这种事只有真机能发现。

新增断言（阶段 5）六条:真的把 nanotund 停掉再敲 restore，断言输出点名 `nanotun-web`、说明后果、给出处置，
外加两条**反证**——输出里不能出现第一道闸的 `control socket`（否则说明 stop 没生效、短路在第一道，这组断言
测的是别的东西却照样绿），也不能出现源校验的 `not a SQLite database`（那道排在持有者之后，赢了就说明顺序被挪过）。

**源刻意用垃圾文件而不是真备份**，这是本轮设计上最值得记的一点。持有者检查排在源校验之前，所以闸在的时候
赢的必须是持有者那条消息；闸没了则退到源校验，垃圾文件被拒、实时库不动。于是:

- 哪天这道闸真被删了，用例变红的同时**不会**顺手把实时库盖掉。用真备份做源时，删掉闸就等于让测试自己执行
  一次真还原 —— 一个失败时会连带毁掉环境的测试，运维不会敢留着它跑；
- 钉的力度反而更强:它同时钉住了**顺序**。顺序一旦被挪到源校验之后，删掉闸就会从「变红」退化成「静默覆盖」。

反向验证:把 `processesHoldingFile` 那道闸短路掉重新部署（md5 核过是故障件），恰好 5 条变红、其余 38 条不动，
输出是 `refusing to restore: ... not a SQLite database ... The live DB was left untouched` —— 连反向验证本身都没碰实时库。
回滚二进制后 43/43 复绿。顺带一条:`拦下它的确实不是 control socket 那道闸` 在故障件下**仍然绿**，这是对的，
它是补充反证而非主断言。

### 第 52 轮:推上去让 CI 说话 —— 首跑就红，且工作树被外部改过

失败时把 `testdata/fuzz` 下的崩溃输入捞成 artifact —— 否则 runner 工作区跑完就没了。

**四、`login_rate_limit_per_min` 的实机断言(阶段 2 新增五条)。**
这是「被人暴破 PSK」时运维会敲的第一个开关,此前完全没有实机验证。难点是**怎么造出登录尝试**:
限速这道闸排在 PoW **之后**,拿 curl / nc 打不进去。办法是用客户端自己发 —— 导出不含凭据的节点链接
(`profile show --format url`),配一份**用户名不存在**的假凭据,每次尝试都正常解 PoW、消耗一个令牌,
然后倒在鉴权上。实测形状教科书级:401 / 401 / 401(突发额度 3)、然后 429 / 429 / 429。

断言的形状比「出现 429」更要紧:
- 前三次必须是 401。若实现把 burst 当成 0,测试同样看得到 429,但那是另一种缺陷(正常用户重按
  一次登录就被拒),不该算这条通过;
- 关掉限速后必须**立刻**回到 401。此时桶还是空的,所以这条才是真判别器:429 若来自别的原因,
  改配置不会让它消失。

三处刻意的选择:不复用 A 上保存的凭据(传错 `--cred` 有覆盖风险,而 A 的凭据一坏整个环境起不来);
`--no-default-route` + 独立 tun-name(登录失败本来走不到建 TUN,但万一走到了默认行为是接管默认路由,
当场打断 SSH 与真实隧道);串行而非并发(客户端即使失败也会存/恢复 `resolv.conf`,并发会互相踩)。

反向验证短路掉 `AllowLogin` 的配置判定后恰好 2 条红、其余 31 条不动。**并且顺带抓出一个我自己的
缺陷:断言的失败分支写了 `$E2E_A_HOST）`,全角括号被 bash 并进变量名,`set -u` 下当场打断整个阶段。**
正向跑走的是 `_pass` 分支,这行从没被执行过 —— 这就是反向验证的价值:**断言的失败路径本身也是
没被测过的代码**。而这个坑仓库里已经踩过两次、`selftest.sh` 里早有静态检查,我的问题是改完 e2e
脚本没跑它。规矩补上:改 `scripts/e2e/` 下任何脚本后先跑 `./selftest.sh`。

### 第 53 轮:跳板机防火墙的 fail-closed，以及一次「污染变成粘性」的事故

**一、`jump_host_firewall` 在 ipset 不可用时必须拒绝启动(阶段 5 新增六条)。**
钉的是第 23 轮深扫那条 HIGH:在那之前 `jumpFW.Replace` 失败只打一行红字,启动照常继续,
reload 还照样把它记成「已热更新」并回报成功 —— 运维据配置认为入口已限制到跳板机名单,实际
对全网敞开。代码注释把 `ipset 未装` 列在触发条件第一位,而这台服务器**恰好就没装 ipset**
(iptables 有),等于生产条件现成,不需要构造任何故障。

断言取「服务起不来 + 退出码是 `ExitConfigSemantic`(11) + 日志明说受保护端口未受限」,并配一条
反向断言:名单必须填**合法非空**的 IPv4。留空会被更早的 `ValidateJumpHostFirewall` 拦下
(「留空等于全网开放」),Fatal 照样发生、断言照样绿,但测到的是另一道闸 —— 第 51 轮刚在还原
守卫上踩过同一个坑。ipset 哪天被装上,这条会**跳过并说清原因**,而不是静默变成永远绿的空断言。

反向验证把那处 Fatal 退回成「只打日志、继续启动」:恰好两条变红(服务仍 active、退出码 0),
而**「日志明说未受限」那条在故障件下仍然绿** —— 因为旧行为也照样打那行红字。这恰好演示了
第 23 轮修的是什么:日志从来不是防线。写守卫断言时别把日志当主断言。

**二、一次事故:断言的失败分支把安全开关留在了开启状态,而快照式还原让污染变成粘性。**
第 52 轮那个全角括号 bug(裸变量引用后紧跟全角右括号,`set -u` 下当场中断)发生在
`login_rate_limit` 用例的**失败分支**里。中断点在「开限速」之后、「还原」之前,于是限速被留在
开启状态。而当时的还原写法是「进函数时把 config 备份、出函数时拷回去」——**于是污染变成粘性的**:
之后每一轮都把这份脏状态备份下来、又忠实地还原回去。连着三轮的红都指着错方向(我一度以为是
自适应 PoW 累积升难度,量了一下单次尝试只要 1 秒,才回头查配置)。

两条通用规矩:
- **安全开关的还原要写死已知的安全默认值,不要还原「进来时的样子」**。快照式还原会把上一轮的
  脏状态一路传下去,而且越传越像「环境本来就这样」。
- **进函数时先断言起始状态**。不是形式主义:它是唯一能把「上一轮留了脏东西」和「产品坏了」
  分开的地方。现在起始值不是 0 就报 ENV 并停下,而不是带着不可信的前提往下跑。

顺带一条:`sleep` 猜 SIGHUP 生效被换成等那行「已热更」日志(它打在 `SetRatePerMin` 之后,看见
它就说明新速率已生效)。这也是全套里那条红最初的表象 —— 但表象和真因是两回事,真因是上面那个。

### 第 54 轮:`exit_mode=isolate` —— 一个「全都不通」的开关，怎么证明它坏没坏

这是配置开关反查名单上风险最大的一项，所以留到最后。难点不在于让它变红，而在于
**isolate 打开后一切都不通，于是任何单看「不通」的断言都无法区分两件事**:

- 它按设计只掐客户端**之间**的转发(正确);
- 规则装错把整个数据面打死(缺陷)。

阶段 1 尾部新增十二条，核心是那条**判别器**:「A 与服务器自身仍可达」。isolate 装的是
FORWARD 链 `-i tun -o tun DROP`，而客户端发往服务器自己 vIP 的包走 INPUT 不走 FORWARD，
所以它必须仍通。没有这一条，前面三条「mesh 断 / LAN 断 / 出口断」在两种局面下表现完全一样。
服务器 mesh 地址是运行时查的，不按 A 的 vIP 猜网关 —— 猜错的表现是判别器恒为「不通」，
于是它悄悄失去判别能力；而且切过去之前先自证它现在是通的，否则这条断言毫无意义。

另两条钉的是**沉默的错配**:库里那些 approved 的出口/子网记录在 isolate 下是哑弹，
`route list` 却照样显示 approved。启动期那条 WARN 是运维唯一的线索，所以要求它存在，
并且要求它里面 `exit_devices=1` —— C 同时批了 `0.0.0.0/0` 和 `::/0`，那是**一台**机器
而不是两条，按条计会让人以为自己有两台出口机。这条 `check_contains` 特意**不**拿「WARN 存在」
当前置条件:那样一旦 WARN 整条消失，它会静默不执行 —— 消失的断言比红的断言危险，它在汇总里看不见。

反向验证同时注入两处(拆掉 `handleEgressSelectFrame` 里的 isolate 拒绝块；把出口设备计数
改成按条计)，**恰好两条变红，且各自对应一处故障**，其余十条全绿。其中最说明问题的是:
拆掉拒绝逻辑后，**「A 经出口出网被拒（fail-closed）」仍然是绿的** —— 因为流量改走黑洞，
从外面看一模一样。那条日志断言不是装饰，它是唯一能把「当场拒绝」和「静默黑洞」分开的断言。

**另外修了一次同形状的脚手架事故。** 单独跑阶段 1 时开头五条集体红(MagicDNS 的
A/AAAA/上游转发、公网 UDP DNS、2MB 下载、DF 边界)，收尾还多报一条残留。真因是开跑时
device 31 的 `0.0.0.0/0` 整行不在库里 —— 那五条全都要经 C 出网，而跑到中段
`exit designate` 把该行建出来之后，后面的断言又全绿了。**一次开跑状态问题，伪装成了
六条互不相干的产品缺陷。** 基线因此补了一条 `_check_c_is_an_approved_exit`，与第 51 轮
那条子网断言并列，同样只断言不自动 designate:自动补会让「这行为什么会没了」永远查不出来。

### 第 55 轮:配置开关清单收尾 —— `forward_block_bt` 与 `udp_relay_enabled`

这两个是那份五开关名单里最后两项。它们此前只被「SIGHUP 会报它需重启」覆盖 —— 也就是说
只验了「会提醒你重启」,重启之后到底生效没有,没人验。

**一、`forward_block_bt`:测「配置 → 内核规则」,而不是硬造端到端流量断言。**
规则挂在 FORWARD 链 `-i tun0 --dport 6881:6889`,唯一能碰到它的路径是「客户端经服务器自身
NAT 出网」(链里那条 `-i tun0 -o enp1s0 ACCEPT`)。而本套件里 A 固定选 C 当出口,去程是用户态
直投给 C 的会话、压根不碰 tun0,子网路由同理 —— **当前拓扑下没有任何流量路径能打中这条规则**,
硬写一条端到端断言只会得到一个无论规则在不在都恒绿的假断言。

能测且值得测的是那一环真有可错的地方:`SetupIptables(..., blockBT, blockTracker6969, blockSMTP25, ...)`
是三个相邻的同类型 bool 实参,串位编译器完全看不出来,而这段是 Linux-only 的无单测代码 ——
纯函数 `tunForwardPortDropRules` 的单测测的是函数本身,测不到调用点。所以八条断言里配了反面的
一条:只开 BT 时 6969 与 25 不许出现。udp 那半同理,代码注释自己点了「只挡 tcp 的话 uTP / DHT
走 udp 照样能把出口跑满」。

反向验证把调用点上 `ForwardBlockBT` 与 `ForwardBlockTracker6969` 对调:恰好五条变红,反面那条的
失败文案直接点名串位,而**套件其余 54 条全绿** —— 实参串位在别处没有任何可观测后果,这正是它
需要一条专属断言的理由。

**第一版的设计错误(值得记):三个开关必须各自单独打开。** 第一版只测了 `forward_block_bt`,
后来补另两个时本想「把 tracker 与 smtp 一起打开、断言两条规则都在」—— 那样是错的:两个开关
同时为 true 时,无论实参怎么对调,装出来的规则集**一模一样**,于是串位在那种测法下完全不可见。
改成三档、每档只开一个、并断言另两个的端口不出现之后,反向验证把 `ForwardBlockTracker6969`
与 `ForwardBlockSMTP25` 对调:恰好六条变红(tracker 档三条、SMTP 档三条),BT 档不受影响,
而**纯函数单测在这个故障下仍然是绿的** —— 它测的是函数本身,测不到调用点。
协议形状也各自钉住:BT 要 tcp+udp,tracker 与 SMTP 只该有 tcp(多装一条 udp 会挡掉与这两个
开关无关的服务)。

顺带一次:`selftest.sh` 的静态检查又抓到一处 `$bad（` —— 裸变量紧跟全角括号,`set -u` 下当场
中断,而且只在**失败分支**里触发。第 52 轮那次「污染变成粘性」的事故就是这个形状,这次在提交前
就被拦下了。

**二、`udp_relay_enabled`:用仓库自己的依赖写了个 hy2 探针,真的去发一次 UDP。**
这是个纯安全开关:关着时服务端设 `DisableUDP`,hy2 只承担 nanotun 自己的隧道流量;开着时任何
**通过认证的** hy2 客户端都能借它发任意 UDP(DNS 放大、内网横移)。误开之后隧道照常工作,
从外面看不出任何异样。

`scripts/e2e/remote/hy2udpprobe` 用的是 hysteria 客户端库 —— 它本来就是本仓库的依赖,于是不必在
被测机器上装第三方软件。探针以合法客户端身份完成握手(mTLS,服务端是 `RequireAndVerifyClientCert`;
salamander 混淆;hy2 口令,三样缺一样都连不上),然后向公网 DNS 发查询并等应答。实测关着时得到
`udp_disabled`,开着时真收到 61 字节 DNS 应答。

正面那半是这组的**判别器**:只有反面那半的话,探针连不上、口令取错、混淆没配这些脚手架问题
全都表现为 `udp_disabled`,于是断言恒绿而什么都没测到。探针与证书都做成自备(缺二进制就本地
交叉编译推上去,缺证书就用服务端那把客户端 CA 现签),而不是「缺了就 skip」—— skip 在汇总里
是一行灰字,换个环境跑就会永远灰着,而这组测的是安全开关,静默不测比红更糟。

反向验证把 `DisableUDP` 写死 false:恰好两条变红(关着时那条、关回去那条),正面那条仍绿。
顺带印证这里其实是**两道闸** —— 拆掉 `DisableUDP` 之后 `Outbound` 那层仍然拒转发,所以探针
拿到了 UDP 会话但转不通。断言钉的是外层那道,没有被内层遮住。

**踩到的两个取值坑**(都属于「错误长得像结论」那一类,值得记):
- `tls_client_ca_file` 在配置里是**相对路径**(相对 `/etc/nanotun`),而远端命令的 cwd 是登录目录,
  直接 `test -f` 永远说找不到 → 这组静默退化成 ENV。
- `password` / `listen_addr` 这类键名在 config.toml 里**多个段都有**(server / hysteria / reality / web)。
  按全文 grep 再 `head -1` 是碰运气:实测 `listen_addr` 有四条,拼起来变成端口 `44384438443`,
  而那个错误的表象是「探针连不上」。改成段感知的 awk 取值。

### 第 56 轮:出口私网守卫的 INPUT 那一半,以及一个「线上从没跑过」的开关

**一、C 的默认路由静置消失:查不出因,改为现场取证。**
第 54 轮记的那个悬案(阶段 1 开头五条集体红,根因是 `0.0.0.0/0` 的 approved 记录不见了)这轮做了收尾。
能排除的都排除了:

- **服务端自身没有任何能删掉 approved 路由的代码路径。** store 层只有两个删除函数,
  `DeleteAdvertisedRoutesForDevice` 只删 `status='pending'`,`DeleteRoute` 只被 admin CLI 与 web 调用;
- **审计里那段窗口没有未被还原的删除。** `exit_revoke` / `route_delete` 都有审计,窗口内每次删除后面
  都紧跟一次 `exit designate`(那是第 50 轮「按族撤销」用例自己的删与复原),复原断言当时是绿的;
- **阶段 5 的还原用例从不真的还原库。** 它只验「运行中拒绝还原」和「垃圾文件被拒且实时库未被改动」,
  所以整库被换回旧状态这条路也不成立;
- 自基线加上 `_check_c_is_an_approved_exit` 之后,8 次以上跑动一次都没复现。

证据不足以定因,所以不编一个。改的是**取证**:那条基线断言失败时现在会一次抓齐三样 ——
该设备全部路由(区分「行不存在」与「状态不对」)、审计尾部(唯一能指出谁删的东西)、库文件的
inode/mtime 与 WAL(库文件被换过的话,进程还握着旧 inode 写、CLI 读的是新文件,表现恰好就是
「行凭空消失」)。下次复现时定案所需的东西就都在失败输出里了,而不是又一次事后无从查起。

**二、`exit_deny_private`:重点在 INPUT 那一半,而它在任何流量断言里都看不见。**
这个守卫装两处规则,分工不同:FORWARD 那条拦「借服务器出网访问内网邻居 / 云元数据」,
INPUT 那条拦「服务器自己挂在私网卡上的地址」—— 代码注释把后者写得很直白:
「不装这条的话内部管理面服务照样对 VPN 用户敞开」。**FORWARD 装上了、INPUT 漏了**
是一个真实的暴露面缺陷,而当前拓扑下没有任何流量能打中它。

为什么这组同样只能测「配置 → 内核规则」:实测客户端 A 访问云元数据 `169.254.169.254` 时,
A 自己的路由表把它送出 A 的 WAN(`via <A 的网关> dev enp1s0`)—— **压根不进隧道**;
加上 A 固定选 C 当出口(去程用户态直投、不碰服务端 tun0),两条路都够不到服务端这两条规则。
顺带这也是一个否定结论:这条路径上没有「借出口节点碰到云元数据」的暴露。

15 条断言覆盖三档状态(默认 auto → 关掉 → 还原 auto)× 两条链 × 双栈,外加:
FORWARD 那半必须带 `-o <wan>`(少了它会连 tun→tun 一起拦,把已批准子网路由也打掉);
mesh 网段不许进拦截列表(真进了会把整个 mesh 打死,而那种失败表现为「所有 mesh 断言一起红」,
没人会想到根因在这个守卫上);启动日志必须点明档位与实际拦了哪些网段(运维唯一的可见处)。
出网网卡名运行时取,不写死 —— 写死之后换机器的表现是「规则没装」,一个指向错误方向的红。

反向验证两次,各恰好四条变红、另一半保持绿:注掉 INPUT 那段 → 四条 INPUT 断言红;
去掉 FORWARD 的 `-o <wan>` → 四条 FORWARD 断言红。

**三、`data_plane_ping_*`:参考部署里两个键一个都没配,这套机制线上从没跑过。**
所以第一件要钉的不是「卡死能不能检出」,而是**打开它会不会把健康会话也一起杀掉**:
客户端若压根不回 Pong,这个开关就是个地雷 —— 每 N×interval 把所有正常会话杀一遍,
表现为全员周期性掉线,而运维只会看到「网不稳」。实测(5s / 2 次,判活窗口 10s)客户端确实回 Pong,
健康会话在 4 个判活窗口内零告警、conn_id 不变。

造「卡死」用 SIGSTOP 冻客户端:进程停了但 TCP 还在,正是这套心跳存在的理由 ——
拔网线那种断法底层 read 直接报错,走不到判活逻辑。实测 ~20s 检出,日志带
`last_pong=14.8s miss_window=10s ping_seq=25 user_id=u2 remote=<A 的公网 IP>`,
会话被关掉且**只关那一条**(C 的会话 age 照常增长,没被连坐),解冻后 A 自行重连、vIP 租约保留。
关掉开关后同样的卡死不再被检出,证明上面几条是这个开关驱动的。

反向验证两个,各自被设计给它的断言精确接住:把 Pong 的时间戳更新注掉(最贴近真实的退化形状)
→ 「健康会话被误杀」+「conn_id 变了」两条红,失败文案直接点出真因;把判活条件废掉
→ 「卡死会话被判定为僵尸并关闭」红。

**这一轮踩的两个坑都在脚手架自己身上,而且都属于「测不准自己声称的东西」:**

- **`pkill -f 'nanotun connect'` 会把远端执行这条命令的 bash 自己一起匹配上**,于是 SSH 当场挂死,
  客户端和我自己的 shell 一起被冻住。改成按进程名精确匹配(`pgrep -x nanotun`)。
- **用会话年龄判「有没有被杀掉又重连」是错的。** 年龄要跟一个绝对阈值比,而阈值同时受本用例自己的
  重启节奏和 SSH 往返耗时影响,实测出过「零告警但年龄偏小」的自相矛盾结果。改成对比窗口前后的
  `conn_id`(被杀过必然换号)。**而修的时候又埋了第二个**:判「服务端有没有中途重启」时拿 `uptime`
  字符串比相等 —— 它是个时长,同一进程里每次读都不一样,于是「conn_id 变了」会永远被归成环境问题,
  真缺陷被静默降级,比没有这条断言更糟。实测里 `33s → 1m34s` 明显是同一进程却报了环境问题,
  才把它揪出来。改成按秒解析、用增量判断。**教训:改完断言必须把变异重打一遍** ——
  这个 bug 正是在「变异验证之后才改断言」的缝里长出来的。

**当时未测到的 `max_sessions_per_user`**:语义先读清了 —— 超限不是拒登,而是踢掉最老的会话
(`evictOldestSessionsLocked`),新登录照样成功。但三机里 A 与 C 分属两个账号(`testcli` / `u4`),
同一账号只有一个会话,超限压根不会发生。当时判断要测它得写一个登录探针(hy2 握手 + smux + PoW + 保活),
先做了更划算的几项。**第 60 轮用挂载命名空间绕开了这个前提,已补齐。**

### 第 57 轮:平台限速 —— 一条自己写的断言,恒绿了两轮才被变异抓住

`[server].rate_limit_by_platform` 是四层限速里的**第 3 层**。前面那组(第 30 轮)只覆盖了
设备 / 全局 / 用户三层,这一层此前完全没有实机断言。它与那三层有两处结构性差别,都值得单独钉:

- **它在登录期读一次**(`linkRatesForPlatform` 只在建限流器时调用),所以热更**不回改现役会话**。
  reload 日志明写「仅对未来登录生效」—— 这句声称没人验过。若哪天实现改成也回改现役会话,
  照着这句话做容量规划的人就全错了(以为改了要等重连,实际立刻生效)。
- **它按 platform 键匹配**。写成「有任何一个条目就套到所有会话」的话,给 android 配的限速会把
  linux 客户端一起限住,表现是「莫名其妙变慢」而配置文件里明明没写 linux。

11 条断言覆盖三档(只配 android → 只配 linux → 归零),含实测吞吐的**单边**校验
(限值以下多慢都算过 —— 公网抖动只会让它更慢;只有跑出远超限值的速度才说明限流器没装上)。
实测 134 KB/s 对 150 KB/s 限值,而同一台机器在 1 MB/s 限值下跑到 754 KB/s,量级对得上。

**这一轮真正的收获是:那条判别器断言恒绿了两轮,是变异验证把它挖出来的。**
两个独立原因叠在一起,任何一个单独存在都足以让它测不到东西:

1. **参考配置里本来就带着一段被注释掉的 android 示例**(`# [server.rate_limit_by_platform.android]`)。
   我用 `grep -F` 判段是否存在 —— 子串匹配把注释行也算成「段已存在」,于是没有真的建段;
   接着 `tomlset` 找不到真段、退出 1,而我把它的错误 `>/dev/null` 吞掉了。**android 那一档的限速
   从头到尾没写进去**,断言于是恒绿:没配限速,当然「不影响别的平台」。
   坐实它的是热更日志里的 `platform_count=1` —— 服务端只载入了一个条目。
2. 改完上面那个之后它**仍然**恒绿,根因在设计上:我为了让还原不依赖快照,选择「段一直存在、值置零」。
   可零值条目让 `m["linux"]` 永远命中,**「键匹配写错」这一类故障压根走不到那条代码**。
   而且真实部署的形状恰恰是「只写要限的那个平台」,我的测试永远覆盖不到那个形状。

两处都改了:段的存在性判断改成整行精确匹配;写入失败改成 `env_error` 报出来;还原方式改成
**哨兵行 + 追加到文件末尾**,还原就是「删掉哨兵行到文件末尾」—— 既不依赖内容快照(快照式还原会把
污染一路传下去,见第 53 轮那次事故),又能精确控制「哪些平台表存在」。追加必须在**文件末尾**:
段头会终止上一个表,插在中间会把 `[server]` 后面的键全切进子表里,那是个「TOML 仍然合法但语义全变」
的改动,`tomlset` 的自证也拦不住。同时补了一条**正面对照**断言:先确认服务端真的载入了预期数量的
平台条目,再判「不影响别的平台」—— 没有它,「写入没成功」永远伪装成通过。

**教训(与第 56 轮那条同源):恒绿的断言比没有断言更坏,而唯一能发现它的手段是变异。**
这次的判别器写得没问题、失败文案也准,坏的是它下面的脚手架和它依赖的配置形状 ——
只看「跑出来是绿的」永远发现不了。变异验证的对象不该只是产品代码,还有断言自己。

### 第 58 轮:`lease_gc` —— 查出一处「注释和它下面两行代码互相矛盾」

`[server].lease_gc_idle_days` 此前 e2e 零命中。它两个方向都会安静地伤人:不回收则 leases 表
堆满「设备半年没上线」的 vIP 占位,新设备拿不到地址(IPv4 私网池尤其);回收错则把还在用的地址
收走,设备重连换 IP —— 按 vIP 钉的 ACL / 端口转发就此指向空处。

触发点选**启动那一次**(定时器周期以小时计,e2e 等不到;而 lease_gc 启动时会先跑一次)。
观测量用 `lease_gc_total` 而不是 grep 日志:它是进程内计数器、重启归零,所以「这次启动回收了
几条」能精确断言成 1 或 0;日志只在 n>0 时打 INFO(n==0 走 Debug,默认级别看不见),只靠 grep
的话「没回收」和「日志没打出来」分辨不开。

**发现的缺陷:文档写的「0 = 关闭」根本不存在。** 三处注释(`config.go` / `server.go` / `lease_gc.go`)
都写着 `<=0 关闭定时回收`,而 `server.go` 里是:

```go
leaseGCIdleDays := gw.cfg.Server.LeaseGCIdleDays
if leaseGCIdleDays == 0 {
    leaseGCIdleDays = defaultLeaseGCIdleDays   // 0 → 30,不是关闭
}
```

照文档写 `lease_gc_idle_days = 0` 的运维以为关掉了回收,实际仍按 30 天在收;而
`startLeaseGCLoop` 里那条「已通过 <=0 显式关闭」的 INFO **从配置这条路永远打不出来**,
所以他也无从发现。只有负数才真的关闭。

**修的是文档,不是 0 的行为**:`int` 的零值分不出「没配这个键」和「显式写了 0」,把 0 解释成关闭
会让所有从没配过它的部署统统静默停掉回收 —— 正好造成这个功能本来要防的 vIP 池耗尽。所以三处
注释统一改成「不写 / 写 0 都是默认 30,要关闭写负数」,并**补了一条启用侧的启动日志**
(`[lease-gc] 定时回收已启用 idle=720h interval=24h`)。这个矛盾能活到今天,缺的就是这条 ——
启用侧此前一个字都不打,只有真删到东西时才有 INFO,于是「正按 30 天在回收」在日志里完全不可见。
测试里把真语义钉住了:写 0 必须表现为「按默认 30 天回收」,谁照旧注释「修」成 0=关闭就会报红。

15 条断言覆盖五档:过期的非手动租约被收 → 未过期的不被收 → 手动租约永不被收 → 负值关闭 →
写 0 等于默认。反向验证两次:cutoff 方向翻转(`<` 写成 `>`)→ 5 条红;两道手动保护**同时**去掉
→ 恰好手动那 2 条红。手动保护为什么必须同时改:`manual=0` 与「vip 正是该设备 fixed_vip 就不收」
是刻意的纵深防御(代码注释明说,防的是历史行 manual 漂移),单改一处会被另一处挡住。

**这一轮又抓到两条恒绿的自家断言,手法和第 57 轮同源:**

- **「不许连坐」那条依赖库里恰好存在一条「非手动 + 无固定地址 + 未过期」的租约。** 而它在上一次
  反向验证中被变异版吃掉了(部署变异版时那次 `systemctl start` 的启动 GC 就按错的谓词收了一轮),
  之后库里只剩手动租约 —— 它们因**另一个**原因免疫,于是这条断言恒绿。改成用自己管的靶子设备
  另开一档「未过期」对照,不再靠别人的固定件。**顺带一课:反向验证本身会改变环境,
  被它破坏的状态要认出来并修回去**(那条租约已按原值还原)。
- **手动那一档的 `lease_gc_total == 0` 有歧义:GC 压根没跑也是 0**(配置没写进去、循环没起来都会
  这样)。补了正面对照 —— 启动日志必须出现「定时回收已启用」,那个 0 才是「跑了但没动手动租约」。

另外注意第一档:变异版收走的是**别人**那条、数目恰好也是 1,于是计数断言反而通过了 ——
**计数说不出收错了哪一行,行级断言才能**。两者都得有。

### 第 59 轮:补上 `lease_gc` 首轮回收绕过防误伤的那个洞

第 58 轮记下但没改的那个观察,这一轮修了。

**缺陷**:回收前有一段防误伤(E1,2026-05-22)——「先把在线会话持有的 device 的 `last_seen_at`
顶到 now」,因为回收看的是 `devices.last_seen_at`,而它**只在登录时刷**,长会话期间一直是登录
那一刻的值。但这道防御依赖当前会话快照,而**首轮回收就跑在进程启动那一瞬间**,那时一条会话都
还没重连上来,快照必然是空的 —— 防御在首轮完全空转。后果:一台连续在线超过 idle 天数、期间没
重新登录的设备,每次重启都会被收掉粘性租约。

**修法**:首轮延后到客户端重连之后再跑(`[server].lease_gc_startup_grace_sec`,默认 120s,
零值约定与它的兄弟键一致 —— 不写 / 写 0 是默认,负数才是不延后)。天级的清扫任务晚两分钟
没有任何代价;120s 的取法是客户端重连退避上限 30s 的两倍余量。等待期间看 ctx,不能拖住关机。

**怎么在三机上证明它**:需要一台**在线**且租约是**非手动**的设备。A 与 C 的租约都是 `manual=1`
(管理员钉过固定地址),天然免疫、打不中这个缺陷 —— 所以用例临时把 A 的租约改成非手动、清掉
fixed_vip,测完原样钉回去(vIP 本身自始至终没变)。靶子设备留着当**探针**:它是可回收的,
所以计数器从 0 变 1 的那一刻,就是首轮真的跑了的那一刻。

反向验证(去掉宽限期)时,三条断言变红,其中一条的形状值得记下来:**「A 仍持有租约」是绿的,
而「A 的地址没变」是红的** —— 租约被收走后设备重连会立刻拿到一条新的,条数照样是 1,变的是
地址。真实伤害正是这个:设备悄悄换 IP,按 vIP 钉的 ACL / 端口转发一起落空。两条断言的措辞
已经按这个区别改准,免得未来有人看着那句绿的「扛过了重启」以为没事。

**这一轮又修掉两条自己写的、证明不了自己声称的断言:**

- 「首轮回收在宽限期后才执行」原本用「A 的 `last_seen_at` 变新了」当判据 —— 而**重新登录本身
  就会刷它**,跟首轮扫没扫过毫无关系,所以它 1 秒就绿了(宽限期是 45s)。换成探针 + 计数器。
- 「宽限期过后首轮确实执行了」原本等「计数恰好为 1」。首轮若连坐了在线设备,计数是 2,这个等待
  永远等不到 → 整组以 env_error 中止 —— **真缺陷被降级成脚手架问题,后面最关键的那条断言根本
  跑不到**。改成等「至少 1」,再把「恰好 1」单独判一条。**教训:等待条件写成「恰好」,
  会在「比预期更糟」的情形下把红变成超时。**

单测两条:宽限期内不回收、且会话在期内挂上来之后不再被误收;以及宽限期必须看 ctx
(否则 SIGTERM 之后这条 goroutine 还挂 120s,systemd 等到超时就 SIGKILL,而那正是
「硬杀不走清理路径」那一类问题的来源)。两个变异各被对应的那条精确接住。

### 第 60 轮:`max_sessions_per_user` —— 用挂载命名空间造出「同账号第二条会话」

第 56 轮记着「测不到,不假装覆盖」的那一条,这一轮测到了。挡路的一直是环境而不是逻辑:
三台机只有两个账号,而这个开关**按账号计数**,同账号凑不出第二条会话就完全触发不了。

**绕开的办法比原计划(手写登录探针)便宜得多**:客户端的身份就是 `/etc/nanotun/device_id` 一个文件。
复制一份配置目录、换掉里面的 uuid,再用 `unshare -m` 起一个私有挂载命名空间把副本 bind 回原路径,
就得到一条身份独立、tun 独立的会话,而 A 自己的客户端毫发无损。加 `--no-default-route` 不许它抢
A 的默认路由 —— 抢了的话后面所有走隧道的断言都会跑偏,而且表现成「出口坏了」这种指向完全错误的假故障。

18 条断言覆盖三个语义,每一个错了都很难被发现:

- **超限不拒登**:超了要挤掉老的、放新的进来。写反成「拒绝新登录」的话,用户换台设备就再也上不来,
  而老会话还挂着 —— 报障时看到的是「账号能用但新手机连不上」;
- **踢最老**:按 `createdAt` 升序挑。挑错方向就变成「刚登录的立刻被自己挤掉」,新设备连上一秒又断;
- **不回踢现役**:上限只在**登录那一刻**判。要是改成 reload 后按新上限回收,运维把上限调小的瞬间
  会批量踢线 —— 一次配置改动打断所有人。这一条的顺序是刻意的:**先把会话堆到超限,再改上限**。
  反过来(先改上限再登录)走的是登录那条判定路径,根本碰不到「回踢」这个问题。

顺带把两级叠加的优先级钉住了:全局明写「限 1」而账号级是 `-1`,该账号仍能开到第三条。

受害者必然是 A(全场最老),这是**设计**而不是巧合 —— 受害者是真客户端,「被踢方收到 406 终态关闭」
这条就能用真实客户端的日志来钉。代价是收尾要把 A 重新拉起来,已并入还原。

三个变异各被接住:排序方向反过来(踢最新)→ 5 条红;`total := len(all) + 1` 去掉那个 `+ 1`
(经典 off-by-one)→ 会话数停在 4、比上限多一条;账号级 `-1` 不再表示不限 → 「压过全局」那条红。

**这一轮的三个坑,全都是「断言测的不是它自己声称的东西」,而且每一个都先以绿色出现过:**

- **拿「总数等于 3」当淘汰完成的信号 —— 而登录之前总数本来就是 3。** 淘汰是登录之后异步关老连接,
  于是等待条件在「什么都还没发生」的那一瞬就成立,后面每条断言都跑在一张空快照上。诊断线索是
  `wait_until` 报的耗时:1 秒。改成等「有一条 `created_at` 晚于探针启动时刻的新会话出现」——
  这个信号同时也是「超限不拒登」的证据,被拒的话它永远等不到。
- **按 `conn_id` 判「幸存者没被连坐」是错的。** A 被挤掉会带走隧道默认路由,带 `--auto-reconnect`
  的探针随即触发「换网」重连,`conn_id` 就换了号 —— 于是一次正常重连被误报成「幸存者也被踢了」。
  改成按 `device_id` 判在线(被挤下线是 406 终态、客户端不会重连,设备也就不会再出现),
  另加一条「幸存者的日志里没有 406」堵死「被踢了又回来」这种可能。
- **`journalctl -u nt-p1` 不带时间窗,数到了上一轮的旧记录。** 全套跑出来红的正是这条,
  而产品侧一切正常 —— 早些时候反向验证那轮,探针本来就该被踢,406 留在 journal 里跨轮存活
  (瞬时 unit 会被回收,它的日志不会)。加 `--since` 之后计数从 4 回到 2,恰好只剩本轮那两条。
  **这个坑本仓库第二次踩**(第一次在 deferred 字段那组),已在断言旁写明缘由。

**教训延续第 59 轮那条:改完断言必须把变异重打一遍。** 上面第三个坑是在变异验证**之后**修的,
所以又单独重放了一次变异一,确认计数从 4 变 2、断言仍然接得住 —— 否则等于把它改哑了。

### 第 61 轮:每虚拟 IP 并发上限 —— 出过两次事故的开关,e2e 零覆盖

把 `config.go` 里 80 个 toml 键与 e2e 脚本对了一遍,56 个从没被提过。绝大多数是 KCP/QUIC/smux
调参,但 `tcp_connlimit_per_ip` / `udp_connlimit_per_ip` 不是 —— 它**已经出过两次事故**,
（这里的「56 个」口径不准:用的是子串匹配,而且没区分「有没有读取点」。第 63 轮重新清点过,
其中 15 个压根是死配置。）
两次都记在 `network_setup_linux.go` 的注释里,两次都极难现场定位:

- 规则漏 `-o <wan>`:xt_connlimit 按 conntrack 原始方向的源地址归类,于是「某客户端公网连接数
  超标」会把它的 mesh 互访、子网路由、出口回程**一起打死**;
- 规则装在 `-i tun -o wan ACCEPT` **之后**:两者都用 `-I FORWARD 1`,后插入的更靠前,于是
  ACCEPT 盖在 connlimit 上方,限流**整条静默失效**,而 `iptables -S` 里两条规则一应俱全。

**先查出一处同族缺陷。** 这两个键在 `main()` 里读、只由启动那一次 `SetupIptables` 落链,
但它们不在 SIGHUP 的 deferred 名单里 —— 而**同一次调用的相邻实参** `forward_block_bt` /
`tracker_6969` / `smtp_25` 三个都在(第 48 轮补的,当时漏了这两个)。后果比端口封堵更贴近应急:
某客户端把机器打满、运维当场把上限从 40 收到 5、SIGHUP、日志一切正常没有任何提示,于是认为
已经摁住了,而内核里那条规则仍然写着 40。补进名单,并把「≤0 按 40」抽成 `ResolveTCPConnlimitPerIP`,
让落链的那一处和判断 deferred 的那一处看到同一个数 —— 直接比原始值的话,`0` 改成 `40` 这种
效果完全没变的改写会被报成需要重启,而 deferred 一旦有噪声运维就不再看它了。

**拓扑上先要造出被测路径。** connlimit 只管 `-i tun0 -o <wan>`,而本套件里 A 固定拿 C 当出口,
公网流量是 tun→tun 直投给 C 的,压根碰不到这条规则(那条 tun→wan ACCEPT 的计数器长期为 0 就是
证据)。所以这一组先把 A 的客户端**去掉 `--exit`** 重启,让它改从服务器 NAT 出网,测完原样恢复。
不做这一步,规则在不在、次序对不对,并发都能全成 —— 又一个恒绿的假断言。靶子选 C 的 22 端口:
这条路径要求靶子从**服务器的公网侧**可达(服务器 SNAT 之后才连过去),而 C 的 ufw 只放行了 22,
8088 那个靶站在这里用不了。

19 条断言分三层:规则的**形状**(`-o wan` / `-s subnet` / saddr /32 / 上限取自配置)、规则的
**次序**(排在 tun→wan ACCEPT 之前)、以及**真流量**(试 7 条只成 3 条、超限的包真的落在这条规则上、
放开上限后同样的并发全成)。三层缺一不可:形状对次序对也可能因为掩码或模块问题根本不生效;
而只测行为的话,「限住了」不能区分是 connlimit 干的还是别的什么挡的。

三个变异各被接住,其中两个**复现了事故的原始指纹**:

- 去掉 `-o wan` → 3 条红,行为层的形状正是注释里记的那次:**mesh 的 TCP 握手失败、ICMP 却照通**。
  我把 ping 与 TCP 拆成两条断言就是为了这个 —— 只测 ping 的话这次事故完全测不出来;
- 把 connlimit 挪到 ACCEPT 之前装 → 3 条红,包括注释点名的那个判据「计数器长期为 0」,
  以及「上限 3 却开出 7 条」(当年是上限 40 开出 60 条);
- 去掉 `-s subnet` → 2 条红。

**这一轮自己踩的坑:期望值是从被测对象身上取的。** 网段原本用 sed 从 connlimit 规则里反推,
于是规则少了 `-s` 时 sed 匹配不上、把整行当成「期望网段」—— 断言变成「这一行包含它自己」,
既永远比不出问题,失败信息还是一坨乱码。改成从 `[tun] device_name` 加 `ip -4 addr` 算出网段,
期望值与被测对象彻底脱钩,改完把变异三重打了一遍确认没改哑。

另外两处脚手架细节值得记:这台机器的 `iptables` 会往 **stderr** 打一行 legacy 警告,不 `2>/dev/null`
就会混进取值;`iptables -vnL` 的详细格式把这个 match 渲染成 `#conn src/32 > 3`,整行里**没有**
"connlimit" 三个字(只有 `-S` 的形式里才有),按 `connlimit` 过滤会一条都匹配不到、计数恒为空 ——
而失败文案恰好指向「规则被盖住了」,能把人引向一个完全不存在的产品缺陷。

### 第 62 轮:`exit_mode` 的第三档 `off` —— 一个只在「没人查账单」时才安全的缺陷

`exit_mode` 三档,mesh 与 isolate 都有用例,`off` 一直空着。它是个**容纳性保证**:纯组网部署
(合规、计费、防滥用)靠它承诺「没有流量经本机出公网」。这类保证坏掉的样子和别的缺陷都不一样 ——
不报错、不断连、流量照样出得去,一切看起来都正常,直到某天有人去查账单或出口日志。

拓扑上的前提与上一轮相同:默认 A 拿 C 当出口,公网流量 tun→tun 直投给 C,压根不碰服务器的
`-i tun -o wan`。所以先把 A 切成「不指定出口」。这个动作两轮都要用,已提到 `fixtures.sh` 里的
`client_a_start_no_exit`。判别器是 **mesh 与子网仍通**:没有它就分不清「off 只掐出网(正确)」
和「规则装错把整个数据面打死(缺陷)」—— 两者在「出不去了」这一条上表现完全一样。

顺带把一条**容易被误读的语义**写死:off 只关「经本机 WAN 出网」,不关「经 peer 中转出网」。
A 带 `--exit` 时仍能从 C 出去(那条路是 tun→tun 转发 + C 自己的 WAN)。选 off 的运维若以为
「没人能上网了」会判断失误,`egress_select.go` 里也确实只对 isolate 有拒绝逻辑。

**这一轮三个坑,全是「断言绿着,但绿的理由不是它声称的那个」:**

- **两条「残留已清掉」是装饰品。** 原本用 `systemctl restart` 切档,而优雅退出会在 defer 里
  teardown 掉全部 `nanotun_main` 规则 —— 新进程启动时**压根不存在残留**,断言恒绿,跟清理
  逻辑毫无关系。发现它靠的是变异:禁掉启动期 sweep,14 条一条都没红。改成「先写配置、
  再 SIGKILL 让 systemd 拉起」才留得下残留,而「mesh 档崩了、运维改成 off 再拉起来」本身
  就是个真实场景。改完再打同一个变异,SNAT 那条如期红了 —— off 分支自己只删 ACCEPT 不删
  SNAT,那一条是启动期 sweep 在 nat 表上的唯一哨兵。ACCEPT 是双重防御(sweep + off 分支
  自己的删除循环),两道一起拆掉才红,属于本仓库反复出现的「冗余防御互相遮蔽」。
- **「有显式 tun→wan DROP」匹到了别人的规则。** 用的是子串,而出口私网守卫那条
  `-d 169.254.0.0/16 -i tun0 -o <wan> ... -j DROP` 把同样的子串整个包住了 —— 于是 off 档
  一条 DROP 都没装时这句照样绿。改成整行锚定(off 装的那条不带任何 `-s`/`-d` 限定)。
- **「启动日志点明已生效」grep 的是配置字段。** `exit_mode=off` 是结构化日志原样回显的配置值,
  策略生没生效它都会打。改成匹配 off 分支独有的那句「已 DROP FORWARD device->WAN」。

后两个是同一个变异(把 `exitModePolicy` 的 off 退化成 mesh)抓出来的:第一次跑只红 3 条,
修完假绿后同一个变异红 5 条。**这就是为什么每条断言都得亲眼见它红过一次。**

顺带修正一处**我自己写错的因果**:注释原本说残留的 ACCEPT 会让 off「静默泄漏」。实测不会 ——
新装的 DROP 用 `-I FORWARD 1` 排在链首,残留 ACCEPT 在它后面,包先命中 DROP(组合变异那轮
残留 ACCEPT 确实在,而「出网被封死」仍是绿的)。真实危害是**可审计性**:链上同时挂着一条
ACCEPT 和一条相反的 DROP,排查的人极易据此判断「出网是开着的」;一旦将来插入位置变了,
它才会从误导变成真泄漏。错误的因果说明比没有说明更糟,所以按实测改了。

**外部快照工具第二次改脏工作树**(第一次见第 52 轮)。明确还原过的两个变异后来又出现在
`git diff` 里,而中间那次「干净」构建正好夹在当中。此后凡是部署前都比对本地与远端的
sha256 —— 这一轮最后那次两边都是 `1813d13c`,才敢认。

### 第 63 轮:凭据轮换 —— 「换掉了」和「旧的失效了」之间隔着一整个启动路径

本轮起点是一次**清点**,而不是挑某个开关:把 `config.go` 里所有 toml 键逐个判定「e2e 有没有
碰过」「代码里到底有没有读取点」。这件事之前一直按「还剩 56 个键没测」的口径记,而那个数是错的。

**先说清点本身的结论,它改了后面几轮该往哪走:**

- **15 个键是死配置** —— `[kcp]` / `[tcp]` 两段的遗留项(`sndwnd`、`sockbuf`、`crypt`、
  `data_shards`、`token_ttl_sec`、`max_plaintext_record` 等),在 config 包之外**没有任何读取点**。
  它们不是「缺测」,是压根不适用。其中 `[tcp].upload_rate` / `download_rate` 最容易骗人:
  `Validate` 还专门给它们做了取值合法性校验,于是看起来像个活旋钮 —— 而限速一侧永远读不到它。
  `[kcp].upload_rate` / `download_rate` 反倒是活的(`[server]` 未配限速时的回退值)。
- 剩下真正「活着但 e2e 没碰」的项里,大部分是 hy2 / smux / QUIC 的调参(窗口、缓冲、超时),
  改错了表现为性能而不是正确性,e2e 这种黑盒断言接不住,继续留给单测和压测。

清点脚本本身踩了两个坑,都值得记,因为它们让我先后拿到过两份**完全错误**的清单:

- **`rg` 不给路径参数时会从 stdin 读。** 放在 `while read` 循环体里,它一口把剩下的输入全吃了,
  循环第一轮就结束 —— 于是「112 个键」只判了 1 个,而输出看上去是一份正常的短清单。
  给显式路径 + `</dev/null` 才对。
- **「e2e 提过这个键吗」用子串匹配会几乎全命中。** 21 万字符的脚本里 `level`、`stream`、`salt`、
  `key` 这类短键名到处都是。这个坑没有单独修 —— 它只影响清点口径,判死活那一侧是精确匹配的。

**产品侧发现:又两个字段漏在 SIGHUP 的 deferred 名单外**(第 48 轮五个、第 61 轮两个之后的第三次)。
这次这一族的性质和前几次不同,前几次是「改了不生效」,这一族是**为安全而轮换**的凭据,漏报的后果
是**双向**的:

| 字段 | 只 reload 不重启的后果 |
|---|---|
| `hysteria.obfs_salamander_password` | 旧混淆口令仍然有效(以为的轮换没发生);而照配置新签的客户端配置连不上 |
| `hysteria.tls_client_ca_file` | 旧客户端 CA 仍被信任;新 CA 签出来的客户端证书一律被拒 |
| `server.vpn_websocket_path` | 进程仍服务旧路径,而 admin 新签出的 profile 写的是新路径 → 新客户端连不上,老客户端照常 |

这三个都和早已在名单里的 `hysteria.password`、`server.tls_cert_file/tls_key_file` 是同族、
同一次启动期构建里读的。**第二列右半那个后果是这一族独有的**:运维轮换凭据时通常会同时重签
客户端配置,于是故障表现为「新客户端认证失败 / 证书不受信」—— 报错指向的方向和真因
(服务端没重启)完全无关,而老客户端一切正常,更没人会怀疑服务端。

比较口径要跟各字段**自己的读取语义**对齐,否则等价改写会被误报,而 deferred 里一有噪声运维就
不再看它了(第 48 轮已经把这条写成原则):混淆口令在读取点是 `TrimSpace` 后用的,按 trim 比;
`tls_client_ca_file` 是原样当文件名开的,前后空格会真的改变行为,按原值比;WS 路径的
「留空→内置默认」「缺前导斜杠→补斜杠」两条归一化都在启动路径上,按归一化后比。
三条都用变异验过(退回原值比较 → 三条「等价改写不许报」如期全红)。

**行为层这一组测的是 deferred 那行日志本身证明不了的事**:日志说的是「需重启」,不是
「重启之后旧口令真的没用了」。两者之间隔着整个 hy2 服务端的构建路径。用现成的
`hy2udpprobe`(第 55 轮为 `udp_relay_enabled` 写的)按三段走:

1. 用当前口令握手成功 —— **判别器**。混淆口令不对的表现就是 `handshake_failed`,而探针坏了、
   口令取错、证书没签上,表现**一模一样**。没有这一步,后面每条「旧口令失效」都可能是假绿。
2. 改配置 + 重启:旧口令握不上手,新口令可用。第二条同样是判别器 —— 只有第一条的话,
   「服务起崩了」也能让它绿。
3. 只发 SIGHUP 不重启:上报 deferred、新写的口令没生效、**上一把口令仍然有效**。
   最后这条把 deferred 警告的代价变成了可观测的事实,也就是这个字段为什么必须上报。

变异(让 hy2 无视配置、永远用原口令,模拟「轮换开关没接到服务端构建上」)被 3 条断言抓住,
且基线判别器仍然通过 —— 所以这组正确地报成产品 FAIL 而不是 ENV。

顺带给 deferred 那组加了一条**收尾保险**:确认 WS 路径已还原。这组为了触发上报会把它改成假值,
它不热更所以组内无害,但只要留在配置里,下一次有人重启服务,进程就去服务那条假路径,而所有
客户端 profile 写的还是真路径 —— 全体连不上。同一类污染上一次(`login_rate_limit`)就是靠快照
机制一路传染到后续整轮的。同组的 `tls_client_ca_file` 也刻意指向真 CA 的一份**副本**而不是
不存在的路径:万一它哪天真生效了,hy2 入口仍验得动客户端证书,不会把数据面连带打死。

### 第 64 轮:PoW 自适应难度 —— 一张全表错位一档、而且没有任何观测面的曲线

接着第 63 轮的清点往下走,挑中 PoW 那一族(6 个旋钮)的理由是:它是登录侧**唯一按 IP 累进**的
防爆破闸门,而 e2e 只是顺带解题,曲线本身零断言;`cmd/nanotund` 这侧的单测也只钉了「难度不越出
协议窗口」。曲线是「安全强度」和「正常用户成本」的分界线,这种东西没有断言就等于没有。

**查出一个影响每个部署的缺陷:`failures_enable` 漏了零值默认替换。**

`ComputeDifficulty` 的判据是 `failures < failuresEnable`。这个字段是 6 个里**唯一**没有
「==0 视作未配 → 用默认」的,于是取 0 时那个条件恒假、永远走 ramp 分支,`base_difficulty` 完全
不可达。参考配置与线上都没有 `[server.pow]` 段(全零),所以这就是所有部署的实际行为:

| 失败次数 | 实际 | 文档承诺 |
|---:|---:|---:|
| 0 | **14** | 8 |
| 3 | **20** | 14 |
| 4 | **22**(已封顶) | 16 |
| 7 | 22 | 22 |

三个后果一个都不会报错、不会断连,所以没人会去查:

- `base_difficulty` 是死配置,调它没有任何效果;
- 每次正常登录多付 64 倍哈希(8→14 bit);
- **封顶只需 4 次失败**而不是设计的 7 次 —— 普通用户连输错 4 次密码,之后 5 分钟内每次尝试
  都要解 22-bit,而配置注释自己写的是「~10s 客户端 / iPhone 15s」。伤的主要是正常用户:
  攻击者反正会被推到封顶,只有正常用户在意 base 那一档。

**修法只有一行,但确认它是「原意」花的功夫更多**:三处文档(`pow.go` 顶部的设计说明、
`ComputeDifficulty` 的曲线表、`config.go` 的字段注释)描述的都是 `failures_enable=3` 的语义,
补上默认值之后三处**同时变真** —— 这比任何单处注释都更能说明原本要的是什么。而
「第 1 次失败就 ramp」并没有因此失去表达方式:那正是 `failures_enable=1`。
这是**安全参数**变更(前 3 次尝试从 14-bit 降到 8-bit),所以先把两种改法的代价摆出来问了一次,
没有自行决定。

顺手把这一族的默认值收进 `config` 包做单一事实来源。**缺陷能藏住的直接原因就是它们只存在于
`NewPoWService` 内部**:读 `config.go` 的人看不到默认值,自然看不出 `failures_enable` 少了一条。
`reload` 侧也跟着改成按**生效值**比较 —— 否则「未配」改成「显式写默认值」会被误报成 deferred,
而 deferred 一有噪声运维就不看它了(第 63 轮定下的原则)。

**顺带查出:整个 PoW 子系统在生产里没有观测面。** `/status` 里一个字段都没有,而 `/metrics`
挂在 health endpoint 上、**默认不开**(这台就没配 `health_listen_addr`)。于是两件事都看不见:
真被爆破时判断不了闸门在不在起作用;`ComputeDifficulty` 回归也不留任何痕迹 —— 本轮这个缺陷
存活这么久,缺观测面是一部分原因。按 `src_spoof_drops` 那一族当年搬家的同一理由,往 `/status`
加了 `pow` 段(issued / ramped / ip_failures_tracked),`/metrics` 同步加 `challenges_ramped`。
三个量刻意按「上游 → 下游」排,红的时候能一眼看出断在哪一段:issued 不涨 = 压根没人登录(判别器);
ip_failures_tracked 涨而 ramped 不涨 = 失败记下了但分档没生效。

部署后第一次读 `/status` 就顺便验证了修复:两个真实客户端重连,`challenges_ramped` 是 0
(base 档)—— 修复前这两次必然都是 ramped。

**e2e 这组测的是单测证不了的那半**:真实登录失败会不会被记到发起方 IP 上、并让下一次出题换档。
这条链子跨三段(失败分支调 `MarkFailure` → 出题前 `Count(ip)` → `ComputeDifficulty` 分档),
任何一段断开,曲线单测照样全绿而线上闸门实际是平的。复用第 51 轮那套假凭据客户端造失败登录。

**「阈值以下不许加压」这一条是本组唯一承重的断言**,而这件事是变异告诉我的:把缺陷注回去重跑,
「失败累计过阈值后换到 ramp 档」照样绿(+2)—— 一个恒定高难度的实现能通过它。只有下界那条
当场红。少了它,这组就退化成「难度会涨」,而那对一个把所有人都按在高难度上的实现同样成立。

失败次数刻意停在 4 次(→16-bit,零点几秒),而不是打到封顶:A 的真实客户端与这些尝试同源 IP,
后续阶段若重启它就要按当时的档解题 —— 22-bit 会让后面每次重连都慢十秒。窗口 5 分钟,且成功
登录一次会把失败数减半,残留会自愈。同理这组必须排在登录限速**之前**:后者要打空令牌桶,
会连带堆一串失败,而本组进门就要求失败表干净。

变异验证 6/6:单测侧 5 个(退回缺陷本身、阈值边界 `<`→`<=`、去掉 ceiling 钳位、Resolve 与服务端
默认漂移、ramped 计数口径 `>`→`>=`),e2e 侧 1 个(退回缺陷本身)。其中**去掉 ceiling 钳位只被
「显式旋钮」那条抓到**:默认 `adaptive_ceiling` 恰好等于协议上限 `PoWMaxDifficulty`(都是 22),
默认配置下这条钳位被协议钳位完全遮蔽 —— 又一例「冗余防御互相遮蔽」,也是那条用例把 ceiling
取成 17 的原因。

### 第 65 轮:剩下 688 条里,哪些是「没测」、哪些是「不可达」

07-31 重采留下 688 条两侧都没覆盖的语句。问题不是「怎么把它清零」,而是**先分清这 688 条
各自是什么**。按文件拆完,形状很清楚:

- `cmd/nanotund/server.go` 134 条(其中 88 条在 `main`)+ `network_setup_linux.go` 91 条
  = 225 条,占三分之一。前者是启动编排,后者要真 WAN 网卡和特定内核配置。这两块**坏起来是响的**
  —— 启动失败会 `FatalExit` 带退出码,systemd 拉不起来,一眼可见。为它们补测要么把 `main`
  拆成可注入的步骤(改动最大、回报最小的那种重构),要么造硬件环境。
- 散落各处的 `if rwCtx == nil` / `if c == nil` / `if pkt == nil` —— 按构造到不了的防御分支。
  写测试得导出内部符号或用反射伪造不可能的状态,买不到东西。
- 剩下三个文件性质完全不同:纯函数、写起来便宜、**坏了不报错**,而且正是本文档开头
  那句「e2e 扫不到报文畸形…却正是攻击面所在」说的那一类。本轮补的就是这三个。

**`util/protocol.go`(21 条 → 100%)。** `ParseLoginReqLinkPayload` 的十二条字段长度上限,
校验发生在**鉴权之前**,解析的是任何能连上端口的人送来的第一帧。删掉其中一条、或把 `>` 写成 `>=`,
都不会有东西变红。每条都测两侧:恰好等于上限必须放行(只测「超长被拒」的话 `>`→`>=` 照样绿,
而那会让 name 正好 128 字符的用户从此登不上),上限 +1 必须拒绝且错误里点名字段。
**逐字段一条用例**是关键 —— 合成一个大 payload 测的话,十二条互相遮蔽,任一条存活整体都报错。

**`util/tcp_record.go`(18 条 → 98.6%)。** 原有测试全是「自己写自己读」的往返,读路径上
三道防线一次都没执行过,而读路径的字节**完全由对端控制**:

| 防线 | 拆掉之后 |
|---|---|
| 帧长校验 | `make([]byte, frameLen)` 就在下一行 —— 四字节头换 4 GB 分配 |
| nonce 方向前缀 | 把服务端自己发出的帧原样打回去会被当成合法入站帧(反射) |
| nonce 序号比对 | 录一帧反复重放都能过 AEAD 验签(nonce 没变,密文当然解得开)—— **AEAD 本身拦不住重放,这是唯一防线** |

测法是手工构造敌意帧灌进 `net.Pipe`,而不是靠往返。序号回绕(`seq==0 → 1`)读写两侧各钉一条:
两侧必须**同样**跳过 0,否则回绕那一刻双方错位一格,此后每帧都不符 —— 且只在跑满 2^64 帧后出现,
现场无法复现。

**`auth/psk.go`(28 条 → 92.8%,全仓最低升到中位)。** `DecodePSK` 解析的是**来自数据库**的
字符串,会被手改、被老迁移写坏、被第三方导入塞进来。这些拒绝分支之前一条没执行过 ——
已有用例走的要么是合法编码、要么整体畸形(`parts != 5`),恰好都在第一个检查就返回,后面全被遮住。
其中 `m` 的**下限**那条最要紧:`m=1024`(1 MiB)是合法 argon2 参数,解得开、验得过,只是弱到
可暴破。能写库的攻击者把 m 改小就等于摘掉 PSK 保护,而一切照常工作。

顺带把 `computeArgon2Capacity` 里的钳位抽成 `clampArgon2Capacity(numCPU)`。原先钳位内联、
直接读 `runtime.NumCPU()`,**上下限能不能触发全看跑测试的机器有几个核** —— 上限那条在 32 核
以下的机器上永远执行不到。这不是为覆盖率改代码:那两个边界一个挡「1c2g 小机型算出 cap=2
把生产堵死」,一个挡「128 核算出 256 slot × 64 MiB = 16 GiB 压在登录上」,都是承重的。

**变异验证 46/46 全抓**(protocol 9、tcp_record 13、psk 20、冗余防线 4)。两件事值得记:

**一、「删掉一个检查」不一定编得过。** 拆掉 AEAD 帧长判断会让 `minFrame`/`maxFrame` 变成未使用
变量,`go test` 直接编译失败 —— 那不算「被抓住」。改成把 `||` 写成 `&&`(条件恒假)既能编过,
也是更真实的手误形态。**编不过的变异等于没验证过**,`mutate.py` 会单列出来,别当成绿。

**二、psk.go 剩下的 10 条不是「没测」,是不可达。** 逐条查完:1 条是 `crypto/rand` 失败
(实际不会发生),7 条是被外层检查完全遮蔽的冗余防线(`DecodePSK` 解码后的长度兜底被 b64 预检
遮住;参数上限兜底被 `parseArgonParams` 的 int 域预检遮住;`VerifyPSK` 里那两条被 `DecodePSK`
遮住),2 条是 `t`/`p` 的下限 —— `minArgonTime` 和 `minArgonThreads` 都等于 1,而它们之前已有
`if time == 0 || threads == 0`,「< 1」等价于「== 0」,永远轮不到。

对这些**不伪造覆盖**,改用两种诚实的处理:

- 冗余防线用 `mutate.py` 的 `also` **成对拆除**来证明它真实存在。单拆任一层都会被另一层挡住
  (看起来像「没测」,其实是「测了但被遮蔽」),同时拆光才失败。最有说服力的是短 hash 那条:
  两层长度下限一起拆掉之后,`ConstantTimeCompare(empty, empty) == 1` —— **任意密码都能登**。
  这比一个覆盖率数字更能说明那两行在干什么。
- 死分支立**绊线**:`TestParseArgonParams_TimeAndThreadFloorsAreCurrentlyUnreachable` 断言
  `minArgonTime <= 1 && minArgonThreads <= 1`。哪天有人把下限提上去,这两条就变成可达且承重的,
  绊线会失败并要求补用例。让绊线响,好过让两条新生效的安全校验无人验证。

**另外修了一条既有的概率性失败。** 本轮全量跑撞上 `TestVerifyPoWProof_.../nonce 不满足难度`
报「want pow: hash does not meet difficulty, got \<nil\>」,看着像 PoW 回归,其实是用例自己掷骰子:
它把解出的 nonce 加 1 后断言「不满足难度」,而 `nonce+1` 有 1/2^difficulty(本例 1/256)的概率
**也**满足。改成显式搜一个确定不满足的 nonce。这种约每 256 次挂一次的用例最坏 —— 平时全绿,
偶尔红一次,而红的时候你会先去查生产代码。

超过 `go test` 默认的 10 分钟 timeout。用 `go test ./... -race -timeout 25m`，
否则会看到一个纯粹由 timeout 造成的假失败。
